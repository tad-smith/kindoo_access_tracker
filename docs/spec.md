## 1. Context

The Church of Jesus Christ of Latter-day Saints organizes members into **stakes**, each containing multiple **wards** (individual congregations). This app is built for a single stake; the schema is parameterized on `{stakeId}` from day one (per F15) so a future second stake is a routing change rather than a data refactor.

**Kindoo** is a door-access system licensed per seat. The stake receives a global pool of seats and allocates them across its own stake-level pool and its wards.

There are three seat types:

| Type | How it's assigned | Lifecycle |
| --- | --- | --- |
| **Automatic** | Tied to callings (church roles) assigned in LCR (the church's membership system). | Managed via the Chrome extension's Sync feature, which reads the operator's live Kindoo session (Kindoo itself ingests LCR via Church Access Automation). See §8. |
| **Manual** | Assigned to an individual. | Held until explicitly removed. |
| **Temporary** | Assigned with a start and end date. | Held through the end date. Kindoo (authoritative) expires the access; the extension's Sync then removes the now-orphaned SBA seat as `sba-only`. See §7, §8. |

The Stake Presidency submits requests for manual/temp seats against the stake pool. Bishoprics (Bishop + two counselors; one Bishopric per ward) do the same for their ward. One or more **Kindoo Managers** process those requests by manually mirroring changes into Kindoo (which has no API), then marking the requests complete.

## 2. Stack

- **Identity:** Firebase Authentication. The auth token (refreshed automatically by the Firebase JS SDK) carries custom claims that drive role resolution; see §4. Two providers are enabled at the Firebase Console level — Google and Email-link (passwordless) — and the SPA UI surfaces both (Google popup CTA above the magic-link form) while the Chrome extension uses only Google; see §4.1.
- **Authorization:** Firestore Security Rules consult `request.auth.token.stakes[stakeId]` for role checks. Custom claims are the only authoritative role source — there are no per-request Firestore lookups for role resolution from rules. See `firebase-schema.md` §6.
- **Database:** Firestore in Native mode (`us-central1`), single-stake project at `kindoo-prod`. All collections are parameterized under `stakes/{stakeId}/...` with three top-level collections (`userIndex`, `platformSuperadmins`, `platformAuditLog`) for cross-stake plumbing. Schema authoritative in `firebase-schema.md`.
- **Client:** React 19 + TypeScript + Vite SPA, served from Firebase Hosting. Reads Firestore directly through the JS SDK; writes go through Firestore transactions or `setDoc`/`updateDoc` with rules enforcing field-level invariants. TanStack Router for routing, TanStack Query as the cache substrate, with a small DIY hooks layer at `apps/web/src/lib/data/` (per architecture D11) that pushes `onSnapshot` results into the query cache.
- **Server compute:** Cloud Functions (2nd gen, Node 22) only — no Cloud Run, no Express, no per-request server-side path. Functions cover: email send (Resend), audit-log fan-in, custom-claims sync, FCM push fanout, callable endpoints for manager- and superadmin-triggered actions (request completion, Sync fix application, stake creation), and a nightly audit-gap reconciliation. Auto-seat creation and temp-seat removal both run entirely through the extension's Sync feature — see §7 and §8. Function inventory: `firebase-schema.md` §7.
- **Email:** [Resend](https://resend.com) on the free tier (100/day, 3000/month). Domain verification on `mail.stakebuildingaccess.org` per F17. Wrapper at `functions/src/lib/resend.ts`; typed sender per notification type at `functions/src/services/EmailService.ts`. See §9.
- **Push notifications:** FCM Web Push, additive-opt-in on a per-device basis. Per-user `notificationPrefs` and per-device `fcmTokens` live on `userIndex/{canonical}`. Service worker at `apps/web/public/firebase-messaging-sw.js` handles background pushes. Phase 10.5 ships only "new request → managers"; the four-other-types expansion is Phase 10.6, deferred.
- **Scheduling:** the only scheduled job is `reconcileAuditGaps` (nightly audit-gap reconciliation — `firebase-schema.md` §7). It is single-loop: one Cloud Scheduler job invokes one Function which iterates over every stake.
- **Hosting / domain:** Firebase Hosting on `kindoo-prod` serves the SPA build at both `stakebuildingaccess.org` (the F17 brand apex, live 2026-05-13) and the legacy `kindoo.csnorth.org` (live since Phase 11 cutover 2026-05-03). Both hostnames have auto-provisioned Let's Encrypt certs. Dual-hosting is the chosen final state — no redirect, no takedown of the legacy hostname.
- **PWA:** `vite-plugin-pwa` configures the service worker (cache-first for static assets, network-first for `index.html`, never cache Firestore traffic) and manifest. App is installable on iOS, Android, and desktop. **Silent auto-update:** registered in `autoUpdate` mode (`registerType: 'autoUpdate'`) — there is no update prompt. When a deploy ships a new bundle, the newly-installed worker skip-waits (`skipWaiting`) and claims clients (`clientsClaim`), and the registration (vite-plugin-pwa's `registerSW()` from `virtual:pwa-register`, called once from `main.tsx`) reloads the page on the new worker's activation. The reload fires on the Workbox `activated`/`isUpdate` event, which fires whenever the new worker activates — not on `controllerchange`, the event the former prompt path waited on that never fired for uncontrolled desktop tabs. Firebase Hosting serves `index.html` and `sw.js` with no-cache headers so the browser/CDN always revalidate the shell and worker, ensuring a fresh deploy's SW is actually discovered. **When an open tab picks up a deploy:** the SW update check runs on registration and Workbox re-checks `sw.js` on load and navigation (frequent in this app), so an open tab adopts a new deploy on its next navigation or reload — typically within seconds. There is no aggressive short-interval `registration.update()` poll, which avoids reloading a user mid-form.
- **Local dev:** Firebase emulator suite (Firestore, Auth, Functions, Hosting). `pnpm dev` runs emulators + Vite + Functions in parallel.

### 2.1 Active stake

A user can hold roles on more than one stake simultaneously (per F18 / `architecture.md` D15). The SPA carries an **active-stake selector** that picks which stake's data the current tab is reading and writing. The selector's behaviour is fully specified here because it spans URL, per-tab session, and cross-tab sticky storage; the implementation lives in `apps/web/src/lib/activeStake.ts` (or equivalent, established in Phase 12's 12.4 PR).

**Resolution priority**, top wins. The chain fires on first render AND on every subsequent URL change that carries a new `?stake=X` param — necessary because the service-worker `notificationclick` handler reuses an existing window via `clients.matchAll` → `postMessage` → router navigation (see `apps/web/src/firebase-messaging-sw.template.js:70-92`), so a push tap on an already-open tab arrives mid-lifecycle, not at mount. 12.4 implementation must subscribe to the router-history navigation event (or equivalent) and re-run the validate-then-strip step on every `?stake=X` arrival.

1. URL `?stake=X` — read on first render and on every router navigation that carries the param, then `history.replaceState` strips it so the URL bar stays clean from then on. When the URL value resolves successfully (passes the validation step below), the SPA writes the value to both `sessionStorage` AND `localStorage` — same symmetric write as the switcher click handler — so subsequent reads in the same tab and fresh tabs see the deep-linked stake as sticky. Used by push-notification deep links (`click_action: https://<host>/<path>?stake=X`) and operator-shared URLs that need to target a specific stake.
2. `sessionStorage['kindoo.activeStake']` — per-tab. Switching the active stake in tab A does not retarget tab B.
3. `localStorage['kindoo.activeStake']` — sticky default. Fresh tabs that have no `sessionStorage` entry fall through to the last stake the user switched to in any tab.
4. Principal-derived first stake — deterministic sort across the union of `managerStakes ∪ stakeMemberStakes ∪ Object.keys(bishopricWards)`. The "first stake" tiebreaker is alphabetical on the stake's doc ID. This claim-derived union always wins when non-empty — even for a principal who is also a bootstrap admin elsewhere — so an existing manager isn't auto-switched into someone else's wizard on every sign-in. This branch fires for a user's first-ever sign-in (no `localStorage` entry yet) and for a fresh tab whose `localStorage` was cleared. When the union is empty AND the principal is not a platform superadmin, tier 4 falls back to `principal.bootstrapStakes` (same alphabetical tiebreaker) instead of returning `null` — see "Pre-claim bootstrap admin" below.

**Switcher click handler** writes both `sessionStorage` AND `localStorage` and invalidates TanStack Query's per-stake reads so the SPA refetches against the newly-selected stake. The URL does not change. **Picking a stake also dismisses the menu** and returns focus to the chevron trigger — including when the already-active stake is re-picked, which is a no-op switch but still a dismissal. Escape and an outside click dismiss without switching. The dismissal is explicit, not incidental: the switch neither navigates nor remounts the switcher, so nothing would close the menu on its own.

**Sign-out does not clear storage.** `signOut()` (`apps/web/src/features/auth/signOut.ts`) is a thin wrapper around the Firebase Auth SDK's `signOut()` call only — it does not touch `sessionStorage['kindoo.activeStake']` or `localStorage['kindoo.activeStake']`. Sticky-stake persistence survives a sign-out/sign-in cycle for the SAME user: re-signing-in resumes the prior selection (tier 2 or 3) rather than re-resolving from claims. This is deliberate, not an oversight: an earlier revision of this behaviour cleared both storage tiers on sign-out, on the reasoning that a stale value could otherwise survive sign-out and permanently shadow a live `bootstrap` claim on the next sign-in, or leak one user's stake selection into the next user's session on a shared browser. The first concern is fully covered by the storage-tier narrowing above (a stale value loses to both claim-derived stakes and a populated `bootstrapStakes`, falling through to tier 4, whether or not it survived sign-out) — clearing on sign-out bought nothing there. The second — a shared-browser sign-out/sign-in inheriting the previous signer's stake selection when the new signer is themselves a zero-role bootstrap candidate with no `bootstrapStakes` of their own — was judged not worth trading away sticky-stake persistence for every multi-stake user to close. It remains a known, accepted limitation. See `docs/architecture.md` D29.

**Stake switcher dropdown** in the brand bar surfaces a drop-down immediately to the **right** of the current stake name — the chevron reads as an affordance on the name it trails, and the pair stays together in the brand group at every breakpoint rather than splitting to opposite ends of a wide header. The chevron never shrinks, so a stake name too long for the viewport truncates with an ellipsis and the chevron stays in frame directly after it. It appears when the union of `managerStakes ∪ stakeMemberStakes ∪ Object.keys(bishopricWards) ∪ bootstrapStakes` has ≥ 2 entries. Hidden entirely when the user has access to only one stake. Visible to all role types — managers, Stake Presidency members, Bishopric — anyone who holds a role on more than one stake, plus anyone who is additionally the bootstrap admin of a not-yet-setup stake. An entry for a stake the principal holds no claim-derived role on (they're only its designated bootstrap admin) carries a **"Setup needed"** badge, so e.g. a manager of stake A who is separately named bootstrap admin of new stake B can find and switch into B's wizard.

**Middle-click / new-tab caveat.** A tab opened via middle-click on an in-SPA link starts with an empty `sessionStorage` and falls through to `localStorage`. That's acceptable: `localStorage` is almost always the right stake, and there is no `?stake=X` stamping on `<Link>` `href`s — the URL stays clean. If the user opens a new tab into a stake they weren't last on, they switch with the dropdown.

**No URL pollution.** Path-prefixed (`/{stakeId}/...`) URLs and on-every-link `?stake=X` query params were both considered and rejected. The query param is an entry-boundary signal only — push deep links and operator-shared URLs carry it; the SPA reads it once, persists it, and strips it.

**Invalid `?stake=X` or stale storage value.** The URL and both storage tiers (sessionStorage, localStorage) can name a stake the principal no longer has access to (shared link to a foreign stake, stale push tap after role revocation, hand-typed URL, last-active stake whose role was rotated away). The principal-derived branch (priority 4) is valid by construction; tiers 1, 2, and 3 must each validate-and-fall-through. On first render the SPA validates each tier's value against the principal's accessible set (`managerStakes ∪ stakeMemberStakes ∪ Object.keys(bishopricWards) ∪ bootstrapStakes` plus `isPlatformSuperadmin === true`, which can access any stake's `/superadmin/...` routes but not per-stake data). If a tier's value is invalid, the SPA ignores it, falls through to the next tier, and surfaces a one-time toast "This notification was for a stake you no longer have access to." (or "Your last-active stake is no longer available; switched to <new stake>." for the storage-tier case). The `history.replaceState` strip still runs on the URL so a bad param doesn't survive in the URL bar; an invalid storage entry is overwritten with the resolved-active stake.

**Zero-role platform superadmin.** A platform superadmin with no manager / stake / bishopric roles on any stake (the first-run state immediately after the operator seeds the first superadmin) has no accessible stake to render against. `useActiveStake()` returns `null` in this state — downstream consumers (TanStack Query keys, the `stakes/{activeStake}/…` path builder, the StakeSwitcher dropdown) must skip per-stake reads when the value is `null`. The brand bar shows no stake name (just the product mark). The post-sign-in landing route is `/superadmin/stakes` instead of the role-default per §5. The same first-run state applies to a superadmin who has created stakes but is not a member of any of them — they manage the platform via the Superadmin section without ever entering a per-stake page.

**Pre-claim bootstrap admin.** An authenticated user named as `bootstrap_admin_email` on a newly-created stake (`setup_complete === false`) whose wizard has not yet run has no role docs anywhere: `managerStakes`, `stakeMemberStakes`, and `bishopricWards` are all empty. The wizard's auto-add writes the `kindooManagers` grant as part of completing setup; until then the claim-sync triggers have nothing role-derived to mint a claim from.

Discoverability rides the auth token, not a network round-trip. `StakeClaims.bootstrap` (`firebase-schema.md` §2) is a per-stake custom-claim marker, present-and-true iff the user is that stake's `bootstrap_admin_email` AND that stake's `setup_complete === false`. It grants no Firestore access and is deliberately excluded from `hasAnyRole` / `isAuthenticated` (`principalFromClaims`, `packages/shared/src/principal.ts`) — a bootstrap-only principal still reads as unauthenticated everywhere else in the app. It exists purely to make the stake *discoverable* before any real role exists. `principalFromClaims` collects every stake carrying the marker into `Principal.bootstrapStakes: string[]`.

The marker is synced by `syncBootstrapClaims`, a Firestore trigger on `stakes/{stakeId}` writes (`firebase-schema.md` §7), so it's usually present before the admin ever signs in. For a stake created before its admin had a Firebase Auth account — the common case, since `createStake` mints no Auth user — `seedClaimsFromRoleData` seeds the same marker at that admin's first sign-in instead.

With `bootstrapStakes` available synchronously alongside every other claim, tiers 1-3 validate a bootstrap admin's own stake exactly like any other accessible stake — the validation set folds `bootstrapStakes` in alongside the claim-derived union (see above), and that is the primary path a bootstrap admin resolves through.

A second, more permissive fallback sits underneath it and is retained deliberately: an authenticated, non-superadmin principal whose claim-derived accessible set is empty resolves an otherwise-unrecognised tier 1 (URL) value with no validation against the accessible set and no invalidation toast — a bootstrap stake or otherwise — regardless of whether `bootstrapStakes` is populated. Tiers 2 and 3 (sessionStorage, localStorage) share this permissiveness only while `bootstrapStakes` is ALSO empty: once it's populated, tier 4 has a validated answer to fall back on, so an unrecognised storage value must invalidate and fall through to it instead of winning outright — otherwise a stale entry naming an old, now-inaccessible stake would permanently shadow the correct tier-4 resolution (the B-19 storage-narrowing addendum; `docs/architecture.md` D29). Resolution itself is correct immediately either way — `resolveActiveStake` is pure and re-derives the answer fresh from principal + storage on every render — but the stale entry's storage write-back lags for a bootstrap-only principal specifically: the overwrite-and-toast effect that rewrites it sits behind the same principal-settling gate as the URL-tier consume (below), and that gate never clears for a bootstrap-only identity, so the stale entry lingers in storage — harmlessly, since resolution ignores it on every render — until the wizard's auto-add grants a real role and `isAuthenticated` flips true. The URL tier keeps the wider permissiveness on purpose: a `?stake=X` value is explicit, present-tense intent for the current navigation — a fresh invite/notification link, a Stake-List click — not stale residue from a prior session. Its lifetime in-tab is bounded, though, not single-shot: `stripStakeParamFromUrl()` cleans `?stake=X` out of the address bar via `history.replaceState`, so a reload doesn't re-read it, and `markUrlStakeParamConsumed()` (`apps/web/src/lib/useActiveStake.ts`) marks the module-scoped URL-tier slot eligible to clear — but neither call clears the slot itself. The slot clears only in `refreshModuleUrlStakeParamFromUrl()`, run on mount, on `popstate`, and on the `router.history.subscribe` callback `main.tsx` wires to a post-navigation notification; `history.replaceState` alone does not fire that subscription. So a principal who lands on a URL-tier hit and then never navigates again in that tab — a bootstrap-only principal parked on the setup wizard is exactly this shape, since their "settling" state never ends and the wizard is the only page they can reach — keeps the value live in module scope, shadowing whatever tier would otherwise win, for the rest of that tab's life. A router navigation (including the wizard's own escape bar) or a fresh page load ends it: the address bar was already cleaned, so a reload reads no `?stake=` param to reseed from. The strip and consume steps do run for a permanently-settling bootstrap-only principal — independently of the storage-writing side effects (persisting to `sessionStorage`/`localStorage`, the invalidation toast), which stay deferred until the principal is fully settled — because `urlConsumeAllowedWhileSettling` reopens just that pair once `bootstrapStakes` is populated, even though the principal's "settling" state (`principal.firebaseAuthSignedIn && !principal.isAuthenticated`) never otherwise ends for this identity, since `bootstrap` doesn't count toward `isAuthenticated`. `bootstrapStakes` only reads non-empty after a real token read completes — during the transient claims-loading window it is always `[]` — so this cannot misfire during that flicker, only once a genuine bootstrap-only identity is confirmed. That keeps the address bar clean and stops a reload from reseeding the bad value; it does not make the value single-shot in a tab that never navigates — the bound above still applies there. Narrowing the URL tier's validation the same way storage is narrowed was considered and rejected — a `?stake=X` is present-tense intent for the current navigation, not stale residue, and narrowing it would break a setup-invite link for someone who happens to also be a bootstrap admin elsewhere. This is not a residual gap. `syncBootstrapClaims` runs asynchronously off the same stake-doc write that made the admin a bootstrap candidate, so it's possible for the admin to arrive on a deep link before their own `bootstrap` marker has synced onto the token; without this fallback, that propagation race would invalidate-and-toast them off their own wizard. The fallback predates the storage-tier narrowing — it was introduced in Phase 12.4 for the same identity shape — and it does not widen what the client can actually do with the resolved stake ID: see the gate discussion below. Two asymmetries exist in this chain: the storage-vs-URL permissiveness split just described, and tier 4's own rule — claim-derived stakes always win; `bootstrapStakes[0]` (alphabetical) is the tier-4 fallback only when the claim-derived union is empty AND the principal is not a platform superadmin.

This closes a bug where a fresh stake's bootstrap admin landed on Not Authorized instead of the wizard: previously tier 4 had no bootstrap fallback at all and returned `null` for a principal with zero role claims, so `useActiveStake()` returned `null`, the stake-doc subscription never opened, and `apps/web/src/lib/setupGate.ts` hung on `pending` before dropping to `not-authorized`. See `docs/BUGS.md` B-19 and `docs/architecture.md` D28.

The mechanism is a routing accommodation only — it does not loosen any per-stake-data rule, and this holds regardless of whether the primary (validated) or permissive-fallback path above produced the stake ID. The downstream gate (`apps/web/src/lib/setupGate.ts`) still decides whether to render the wizard by canonicalising the principal's token email and comparing it to the stake doc's `bootstrap_admin_email`; only the named bootstrap admin sees `'wizard'`. Anyone else who resolves onto that stake ID (e.g. a manager elsewhere who deep-links `?stake=X` for a stake they aren't the bootstrap admin of, or a zero-claim principal who rode the permissive fallback onto a stake they have no claim on at all) is dropped to `'setup-in-progress'` (or `'not-authorized'` once setup completes) by the gate. Firestore rules are unaffected — `isBootstrapAdmin(stakeId)` (`firebase-schema.md` §6.1) already authorised the wizard's reads and writes once the client knows the stake ID, and it did not change; per-stake data reads outside the wizard's own collections still require `isAnyMember(stakeId)`.

An unauthenticated visitor (`principal.firebaseAuthSignedIn === false`) has no claims at all, so `bootstrapStakes` is empty for them by construction — there is no special case to carve out. A zero-role platform superadmin is excluded explicitly (see tier 4 above): they belong on `/superadmin/stakes`, not on a single-stake landing, even if they happen to be named as some stake's bootstrap admin. See §10 for the bootstrap wizard's user-facing flow, including how the admin reaches it.

## 3. Data model

The authoritative schema reference is [`firebase-schema.md`](firebase-schema.md). This section names the collections and gives the role-resolution invariants; field-by-field shapes live in the schema doc.

### 3.1 Top-level collections

- **`userIndex/{canonicalEmail}`** — bridge between canonical-email-keyed role data and Firebase Auth's uid. Carries the FCM device-token map and per-category notification preferences. Written by `onAuthUserCreate` and by the user themselves (subscribing to push); claim-sync triggers translate canonical email → uid through this. See `firebase-schema.md` §3.1.
- **`platformSuperadmins/{canonicalEmail}`** — active source of truth for the platform-superadmin role (Phase 12). The `syncSuperadminClaims` trigger reads writes here and mints / revokes the `isPlatformSuperadmin: true` claim. Writes are console-only — there is no in-app management UI.
- **`platformAuditLog/{auditId}`** — cross-stake audit trail. The Phase 12 `createStake` callable writes `action='create_stake'` rows here; future cross-stake actions (e.g. superadmin add/remove triggers) append the same way.
- **`remoteApply/{canonicalEmail}`** — the remote-apply mailbox (§16, `architecture.md` D27). The parent doc carries the profile-wide opt-in alone; `desktops/{siteKey}` holds one liveness doc per Kindoo site the manager has a live tab on, and `jobs/{jobId}` holds one doc per phone-initiated apply. Top-level rather than per-stake because the doc key is the manager's canonical email and the stake is a **field** — the desktop resolves its own stake from whichever Kindoo site its session is in. Written only by the manager themself (their extension publishes presence and drives jobs; their phone creates them); rules gate every path on `authedCanonical()`, and the two subcollections additionally on the manager claim for the doc's `stake_id`. See `firebase-schema.md` §3.4.

### 3.2 Per-stake collections

All under `stakes/{stakeId}/`. Schema authoritative in `firebase-schema.md` §4.

- **`stakes/{stakeId}` (parent doc)** — collapses what was the legacy `Config` tab: stake_name, bootstrap_admin_email, setup_complete, stake_seat_cap, timezone, notifications_enabled, eq_president_app_access, last_over_caps_json, etc. `eq_president_app_access` is the stake's app-access opt-in (§8) — optional, and **absent means off**. `stake_seat_cap` is the home-site stake seat cap specifically — foreign-site wards (§15) draw against their own Kindoo site's pool, not this number. The `callings_sheet_id`, `import_day`, `import_hour`, `last_import_at`, `last_import_summary`, and `last_import_triggered_by` fields are deprecated — see `firebase-schema.md` §4.1.
- **`stakes/{stakeId}/wards/{wardCode}`** — the doc ID is the immutable `ward_code` and is the `scope` value used elsewhere. The code is **not a user input**: on create it is derived once from `ward_name` via `buildingSlug()` (`'Maple Ward'` → `'maple-ward'`) and pinned as the doc ID; it is never re-derived on edit and never shown in the UI. Legacy wards keep their original 2-letter codes (e.g. `CO`, matching the old LCR tab name) as immutable doc IDs — those are not regenerated. A ward references its building **id-first**: `building_id` (the immutable building slug) is the preferred FK; `building_name` is the legacy display-name FK, still required + populated during the additive transition so stale bundles keep resolving. Resolution prefers the id and falls back to the name (`resolveWardBuilding` / `resolveWardSite` in `packages/shared`, both taking the `buildings` array). A ward does **not** store a `kindoo_site_id`; its Kindoo site (§15) is derived from its assigned building (`null` / absent = home), via `resolveWardSite()`.
- **`stakes/{stakeId}/buildings/{buildingId}`** — slug-keyed (`Maple Building` → `maple-building`). The slug (`= building_id`) is **immutable post-create**: building edit writes the same doc on the frozen slug and never re-slugs a renamed building. The display name is mutable and must be unique across the stake (enforced by the Buildings UI). Carries `kindoo_site_id: string | null` (Kindoo Sites — §15); `null` / absent means the home site. The building is the single source of a ward's site.
- **`stakes/{stakeId}/kindooSites/{kindooSiteId}`** — foreign-Kindoo-site directory (§15). Manager-chosen slug as doc ID. Empty when the stake operates only its home Kindoo site.
- **`stakes/{stakeId}/organizations/{orgId}`** — stake-scope seat pools. A named pool (`name`) with its own display-only `seat_cap`, manager-managed via the Configuration → Organizations tab (§5.3). Doc ID is an immutable slug derived from `name` via `buildingSlug()`. Seats and stake-scope requests reference an organization by this slug (`organization_id`), not by name — renames resolve id → name at render time, so they need no reference cascade. Meaningful only at stake scope; `null` / absent = "No Organization". See `firebase-schema.md` §4.12.
- **`stakes/{stakeId}/kindooManagers/{canonicalEmail}`** — the manager allow-list. Doc existence + `active=true` defines the manager set.
- **`stakes/{stakeId}/access/{canonicalEmail}`** — per-user role-grant doc. Splits `importer_callings` (server-managed; Admin SDK only — written by Sync via the `syncApplyFix` callable and by the `backfillEqPresidentAccess` callable, populated from the churchwide app-access calling list plus the stake's Elders Quorum President opt-in — see §8) and `manual_grants` (manager-managed, via the manager Access page). A third, server-only `importer_limited_callings` map records which of a scope's `importer_callings` confer **limited** rather than full access (`architecture.md` D26); absent means full. Composite-key uniqueness on (canonical_email, scope, calling) is *structurally absent* — the two maps cannot collide. F7. Doc-level `sort_order` (Phase 10.3) denormalizes the lowest canonical `callingSortOrder` priority across `importer_callings`. The `importer_callings` field name is historical (predates the LCR Sheet importer removal — see `architecture.md` D14); rename is out of scope.
- **`stakes/{stakeId}/seats/{canonicalEmail}`** — one doc per (stake, member). Multi-calling people get `callings: [...]`; the rare cross-scope collision lands the secondary grant in `duplicate_grants[]` and is informational, not counted in utilization. F5, F6. `sort_order` denormalizes the MIN canonical `callingSortOrder` priority across `callings[]` — **vestigial; the web no longer reads it** (roster sort is computed at render time from the same compiled calling-order table — see §8 "Roster sort order" and `firebase-schema.md` §4.6 "Sort order"). Carries an optional `organization_id` (the org slug FK; §4.12) on the primary grant and on each `duplicate_grants[]` entry, meaningful only on stake-scope grants; `null` / absent = "No Organization".
- **`stakes/{stakeId}/requests/{requestId}`** — UUID-keyed because a member can submit many requests over time. Carries the `urgent` flag (Phase 10.3; field name unchanged, surfaced to users as the "Emergency" label/badge) and the denormalized `seat_member_canonical` for remove-request completion. F19. Stake-scope add/edit requests may carry an optional `organization_id` (the org slug picked in the request form); it is carried onto the seat on completion (§6.1). Ward-scope and `remove` / `edit_auto` requests never carry one.
- **`stakes/{stakeId}/auditLog/{auditId}`** — flat, server-written audit collection. One row per write to seats, requests, access, kindooManagers, or the stake parent doc, fanned by the `auditTrigger` Cloud Function (F8). Doc IDs are deterministic from `(collection, docId, writeTime)` so retries are idempotent. 365-day Firestore TTL.

### 3.3 Naming and key conventions

- **Canonical email** is `lowercase + Gmail dot/+suffix strip + googlemail.com → gmail.com`. Computed in `packages/shared/canonicalEmail.ts` and applied at every input boundary. The canonical form is the doc-ID for `userIndex`, `kindooManagers`, `access`, and `seats` — there is no separate canonical column.
- **Typed-form email** (preserve case, dots, `+suffix`) is stored alongside in `member_email` / `typedEmail` for display and any future mail surface. The audit log carries both `actor_email` (typed) and `actor_canonical`.
- **Automated actors** use literal strings as the audit `actor_email` / `actor_canonical`: `"RemoveTrigger"` (request-completion seat-side trigger fan-out), `"OutOfBand"` (writes not attributed to a specific trigger — see `auditTrigger` actor-resolution), `"Migration"` (one-shot backfills), and `"SyncActor:<code>"` (Sync's `syncApplyFix` writes, where `<code>` is the fix code that produced the row). Legacy `"Importer"` rows remain in the audit log from the pre-Sync era.
- **Building** doc IDs are slugs of `building_name`, derived once on create and immutable thereafter (building edit never re-slugs); the display name is preserved in the `building_name` field. Two distinct kinds of cross-collection reference: the **ward → building** FK references the building by its `building_id` slug (preferred, id-first; legacy `building_name` fallback during the transition — §3.2). Grant-array references (`seat.building_names` / `request.building_names: string[]`) are **display-name arrays** — they carry `building_name` values, not slugs, and are unchanged by the id-first ward FK.
- **Ward** doc IDs are the `ward_code`; also the value used in `seats.scope`, `access.importer_callings` keys, and `requests.scope`. The code is a `buildingSlug()`-derived slug pinned at create (legacy wards retain their original 2-letter codes); it is never shown in any user-facing surface and never typed by an operator. Wherever a scope is **shown to a user** (chips, tables, inline text, filters, selectors, the Configuration → Wards admin list and edit dialog), the UI renders the ward **name** (`ward.ward_name`) — `'stake'` → `"Stake"`; a resolvable ward_code → its `ward_name`; an unresolved code falls back to the raw code. Stored/submitted values stay the code. The shared resolver is the pure `scopeLabel(scope, wards)` in `@kindoo/shared`; the web app re-exports it (and layers a Firestore-backed `useScopeLabel` hook on top in `apps/web/src/lib/scopeLabel.ts`) and the Chrome extension panel (the queue's request cards + reject dialog, and the Sync drift report) follows the same convention against the wards from its loaded config bundle. Exactly one surface keeps the raw code by design: the web audit-log value renderer, where the stored value itself is what the row documents.

## 4. Role resolution

The auth token's custom claims (set by Cloud Function triggers on `userIndex`, `access`, and `kindooManagers` writes) are the only authoritative role source. The token carries:

```typescript
{
  canonical: string;              // canonical email; trusted in rules
  isPlatformSuperadmin?: boolean;
  stakes?: {
    [stakeId: string]: {
      manager: boolean;           // active=true row in stakes/{stakeId}/kindooManagers/{canonical}
      stake: boolean;             // any non-empty grant in stakes/{stakeId}/access/{canonical} with scope='stake'
      wards: string[];            // ward_codes for which the user has any non-empty grant in scopes != 'stake'
      limited?: boolean;          // present-and-true => LIMITED app access in this stake; ABSENT => full
    };
  };
}
```

Roles per stake:

- `stakes[stakeId].manager === true` → **Kindoo Manager** for that stake.
- `stakes[stakeId].stake === true` → **Stake Presidency** (or other stake-scope grant).
- A non-empty `stakes[stakeId].wards` → **Bishopric** for each listed ward.
- `isPlatformSuperadmin === true` → **Platform Superadmin** (cross-stake). Sourced from the `platformSuperadmins/{canonical}` allow-list via the `syncSuperadminClaims` trigger. Carries the Superadmin nav section in the SPA (see §5.4). Console-only management — no in-app UI for adding/removing superadmins.
- None of the above and not a superadmin → "not authorized".

A user can hold multiple roles per stake; the UI shows the union. A user can hold roles on multiple stakes simultaneously; the active stake (per §2.1) picks which stake the SPA is reading and writing against, and `usePrincipal()` (web) / `request.auth.token.stakes[stakeId]` (rules) consult that stake's claim sub-object.

The web app reads the principal via `usePrincipal()` from `apps/web/src/lib/principal.ts`, which derives the principal shape from the Firebase Auth token's custom claims. Rules read the same claims via `request.auth.token.stakes[stakeId]`. There is no second source of truth.

**Limited app access** (`architecture.md` D25)**.** `stakes[stakeId].limited === true` narrows what an existing role may do in that stake. It is not a role of its own: a limited principal still needs the `stake` claim or a ward in `wards` to reach any surface at all, and holding `limited` without one of those grants nothing. What the flag removes is authority over durable seats. A limited user may create only `add_temp` requests, edit only `temp` seats, remove only temp grants, and may request a temp window no longer than 90 days; at ward scope the request is additionally locked to that ward's own building. The full surface is described in §6.1. `principalFromClaims` collects the flagged stake IDs into `principal.limitedStakes`, and every web-side gate goes through `isLimitedInStake(principal, stakeId)` (`apps/web/src/features/requests/scopeOptions.ts`) rather than reading the array.

`computeStakeClaims` (`functions/src/lib/seedClaims.ts`) writes `limited: true` when three conditions hold together: the user has at least one non-empty grant in the stake, **every** grant across every scope in `access/{canonical}` is limited, and the user is **not** an active Kindoo Manager. One full grant anywhere in the doc — or an active `kindooManagers` row — makes the whole stake block full; a manager is never limited, because the manager row is a full-trust role the rules' manager carve-outs already assume. A grant counts as limited only on positive evidence: `manual_grants[scope][].level === 'limited'`, or an importer calling listed in the same doc's `importer_limited_callings[scope]`. A missing `level`, the string `'full'`, wrong casing, a malformed entry, or a missing / malformed `importer_limited_callings` all read as **full** — garbage data fails toward more access, never less.

**A calling's tier is stored, never inferred from its name** (`architecture.md` D26). `importer_limited_callings` (§3.2, `firebase-schema.md` §4.5) is stamped by whichever writer inserts the calling, in the same write; the read side does no name matching, and `isLimitedAccessCalling()` no longer exists. **Elders Quorum President is the one calling that carries the limited tier** — see §8 for the stake opt-in that admits it in the first place.

The last fold — limited-and-not-an-active-manager — is `isLimitedTier` in the same file, and the active-manager read is `isActiveManagerDoc` (the `kindooManagers` doc plus `active === true`, never the claim, which can be an hour stale on an idle session). Both are exported because the claim minter is no longer the only caller: the app-access welcome email branches its copy on the same tier (§9) and calls the same helpers, so a member told their access is limited is exactly a member whose claim says so.

**Absent means full.** The key is omitted rather than written `false`, so every existing full user's claim block stays byte-identical and the rollout churns no refresh tokens. The rules read it through an `isLimited(stakeId)` helper that guards on `'limited' in …` before comparing, because a bare field read would error on every full user's write. Deleting a user's last full grant flips them to limited on the next claim sync; the transition lands inside the ordinary staleness envelope below.

**Claim staleness.** When underlying role data changes (a manager toggles `active`, Sync adjusts `access.importer_callings` via `syncApplyFix`, etc.), the relevant sync trigger calls `setCustomUserClaims` then `revokeRefreshTokens` so the next request from that user picks up fresh claims. Worst-case staleness on revocation: ~1 hour for an idle session, <2 seconds for an active one (the SDK auto-refreshes on any 401).

**Bishopric lag.** A newly-called Bishopric member can't sign in until Sync runs against the latest Kindoo data (which itself reflects Church Access Automation's LCR pull) and populates `access.importer_callings`. Accepted for v1.

### 4.1 Sign-in providers

Firebase Auth identifies the user; it does not authorize them. Authorization is keyed by canonical email and resolved exclusively from custom claims (§4). The provider that minted the Firebase user is irrelevant to authorization — Google and magic-link sign-ins for the same email resolve to the same `userIndex/{canonical}` doc and the same claim set.

**Surfaces.**

- **SPA (`apps/web/`):** Both providers visible. A "Continue with Google" button (calls `signInWithPopup` with `GoogleAuthProvider`) sits above the email magic-link form (email input + "Send me a sign-in link" submit). Both end at the same Firebase Auth UID for the same email when "Link accounts that use the same email" is enabled (Firebase Console → Authentication → Settings → User account linking — confirmed enabled 2026-05-18). No password field.
- **Chrome extension:** Google only, via `chrome.identity.getAuthToken` → Firebase credential exchange. Unchanged.

**Firebase Console provider config.** Both Google and Email/Password (with the Email-link sub-toggle on, password sub-toggle off) are enabled at the project level. Both are also surfaced in the SPA UI. Disabling either provider in Console would break the corresponding SPA affordance (and disabling Google would additionally break the extension).

**Google popup round-trip.** User visits `/` while signed out, clicks "Continue with Google" in the hero, and completes the Firebase Auth popup flow. On success the SPA force-refreshes the ID token (bounded-poll mitigation for B-4 — see `apps/web/src/features/auth/signIn.ts` module comment) and `gateDecision()` in `apps/web/src/routes/index.tsx` runs unchanged. The Google flow does NOT use `actionCodeSettings` / authorized continue URIs.

**Magic link round-trip.**

1. User visits `/` while signed out. Enters their email and clicks "Send me a sign-in link."
2. SPA calls `sendSignInLinkToEmail(auth, email, actionCodeSettings)` and stashes the typed email in `localStorage` for the return trip.
3. SPA renders a "Check your email" confirmation state on the same page.
4. User opens the email and clicks the link. The link lands on the SPA's action-handler route (path chosen by the implementer; the route is unauthed since the user is not yet signed in).
5. The handler route:
   - Reads the email from `localStorage`.
   - If absent (cross-device — link opened on a different device than where it was requested): prompts the user to enter the email address the link was sent to.
   - Calls `signInWithEmailLink(auth, email, window.location.href)`.
   - On success: clears the stashed email and redirects to `/`, where `gateDecision()` runs as it does today.
   - On error (expired link, malformed URL, email mismatch, network failure): renders a clear error message and offers a re-send affordance back to the sign-in flow.

**`actionCodeSettings`.** `url` is the full SPA action-handler URL (must include the host) and the host must be on Firebase Auth's Authorized Domains list (Console → Authentication → Settings → Authorized domains). **This is a separate Console-level list from the Firebase Hosting custom-domain config referenced in §12** — a host showing up under Hosting does NOT imply it's on the Auth Authorized Domains list. Adding a new authorized SPA host (or verifying an existing one is present) is a deployment prerequisite, not a runtime concern; a missing entry surfaces at runtime as `auth/unauthorized-continue-uri` on the `sendSignInLinkToEmail` call. `handleCodeInApp: true`. Verify before T-44 ships that the Auth Authorized Domains list contains `stakebuildingaccess.org`, `kindoo.csnorth.org`, and the project's default `kindoo-prod.firebaseapp.com` auth-domain entry.

**Authorization gate (unchanged).** A successful magic-link sign-in produces a Firebase user but does not by itself grant any role. A signed-in user with no `access` / `kindooManagers` / `superadmins` doc keyed to their canonical email lands on the existing `NotAuthorized` page exactly as a Google sign-in would. The sign-in page surfaces a short explanatory sentence so new users understand that creating an account does not immediately grant access — e.g., "New sign-ins land in pending authorization until a stake manager adds your email. Contact your stake manager if you can't reach the next screen."

**`userIndex` + claims sync (unchanged).** The `onAuthUserCreate` trigger writes a `userIndex/{canonical}` doc on first sign-in regardless of provider. Claim-sync triggers on `access` / `kindooManagers` / `superadmins` are keyed by canonical email, not by provider or uid. No backend changes ship with the SPA UI provider switch.

**Provider auto-linking — LOAD-BEARING ASSUMPTION.** Firebase Auth's project setting **"one account per email address"** (Console → Authentication → Settings → User account linking) auto-links the Google and Email-link providers for the same email under a single Firebase UID. **This is the Console default; verify it is still ON before T-44 ships.** An existing Google-signed-in user (e.g., the operator) who signs in via magic link to the same address keeps their UID, their `userIndex/{canonical}` doc, and every canonical-email-keyed role doc unchanged. If this setting were flipped to "multiple accounts per email," the same address would mint a second Firebase user the first time it signed in via magic link, breaking every UID-keyed assumption in the system. Future code must not branch on `firebase.auth().currentUser.providerData[0].providerId`.

**Deployment prerequisites** (must hold before T-44 ships):

- The Firebase Auth Authorized Domains list contains `stakebuildingaccess.org`, `kindoo.csnorth.org`, and `kindoo-prod.firebaseapp.com` (Console → Authentication → Settings → Authorized domains — separate from Hosting custom-domain config, see §12).
- The Firebase Auth user-account-linking setting is **"one account per email address"** (Console → Authentication → Settings → User account linking).
- The Email/Password provider is enabled at the Firebase Console level with the Email-link sub-toggle ON and the password sub-toggle OFF (Console → Authentication → Sign-in method).
- The Google provider remains enabled at the Firebase Console level (the Chrome extension depends on it).

**Out of scope.** Email/password (password sub-toggle stays off). Other OAuth providers (Apple, Microsoft, LDS Church Account). Self-service authorization or onboarding flows. Changes to the extension's Google-only auth path.

## 5. Page map

The SPA is built on TanStack Router with file-based routes under `apps/web/src/routes/`. Page components live under `apps/web/src/features/{feature}/pages/`. Navigation is the Phase-10.1 left-rail + sectioned-nav design (hamburger drawer on phone, icon-only rail on tablet, full rail on desktop); components live under `apps/web/src/components/layout/`. Spec in [`navigation-redesign.md`](navigation-redesign.md).

**Route gating.** Each route declares its role requirement; non-managers deep-linking to a manager page is currently inconsistently gated (T-31 — most manager routes rely on the nav not exposing them; only `/notifications` has an explicit redirect). `holdsAnyRole` (`apps/web/src/lib/useRequireRole.ts`) treats two roles as implicit supersets: a platform superadmin passes every per-stake gate, and a Kindoo Manager in the active stake passes the `stake` and `bishopric` gates without literally holding those claims — so `/stake/roster` and `/stake/wards` are reachable by a manager who holds no stake claim. Server-side enforcement is via Firestore rules regardless of client-side gating.

**Default landing rule.** Multi-role principals resolve via priority — manager > stake > bishopric — and land on the most-privileged role's default page. Per-role defaults: manager → `/manager/dashboard`; stake → `/stake/roster`; bishopric → `/bishopric/roster`. Non-Kindoo-Manager roles intentionally land on the Roster (not the leftmost nav tab) so the first surface those users see is the current seat list for their scope. The bishopric Roster, Stake Roster, and Ward Rosters pages each carry a "New Request" button in the page header that opens the New Request form in an in-page modal (form plus Cancel / Submit), gated by request authority for the page's scope and locked to that scope (§5.1, §5.2). Because the modal is always launched from a scoped roster context, it shows the scope as a fixed label ("Requesting for: …") with no scope picker. **These roster-page modals are the sole entry point for creating a request** — there is no nav "New Request" link and no standalone New Request page. A Kindoo Manager holds request authority in every scope without an `access` row of their own (§6.1), so the affordance appears for them on the Stake Roster and on every ward in Ward Rosters. It does not appear on the Bishopric Roster: that page draws its ward list from `principal.bishopricWards`, so a manager holding no bishopric claim sees no ward to render there. Ward Rosters is the manager's cross-ward surface.

The stake bar is home-site only — foreign-site wards do not contribute on either side of the calculation (§15, §244). Per-ward bars are unchanged regardless of site. Reads are per-card live subscriptions through the DIY Firestore hooks.

Displays the pending requests sectioned (Phase 10.3) into Emergency / Outstanding / Future by computed `comparison_date` (start_date for `add_temp`, requested_at otherwise) with a today+7 cutoff at user-local midnight. (The "Emergency" section heads the `urgent`-flagged requests — field name `urgent`, displayed label "Emergency".) Each section heading shows the open-request count in parentheses, e.g., `Outstanding Requests (9)`. Sections with zero open requests are hidden. Pending sorts oldest-first (FIFO). Cards render request metadata (type/scope badges, member, calling/removal reason, dates, buildings, comment, requester, submitted-at) but carry **no direct action affordances** — completing and rejecting a request happen **only in the Chrome extension** (see "Extension queue panel — request-queue parity" in §15), which is where the manager's Kindoo-side work already lives. The one per-card control is **Apply via extension** (§16), and it does not act here either: it hands the request to the manager's own desktop extension, renders what that desktop reports on the card, and raises a dialog the manager has to dismiss once the outcome is terminal. It is gated **per card, not per manager** — it appears only while a live Kindoo tab is sitting in the site this particular request must be provisioned on (derived from scope → ward → building, never read off the request), only once the manager's job mailbox has resolved, and never on a card already showing a blocking duplicate-seat or missing-edit-target error — offering to run a provision that is known to fail is worse than offering nothing. A card whose site isn't covered says which site to open instead. The **requester line** reads `Requester: {Name} ({Calling})`, not the raw email. It is **live-derived** at render from the requester's `access/{requester_canonical}` doc (§3.2) for the request's `scope` — nothing is captured on the request document at submit time. Name is the access doc's `member_name`; calling is the requester's calling(s) for the scope (`importer_callings[scope]`, joined by ", "), falling back to their `manual_grants[scope][].reason` when no calling applies. Because a Kindoo Manager may submit in any scope with no `access` row at all (§6.1), the requester's `kindooManagers/{requester_canonical}` doc (§3.2) backstops both fields: it supplies the name when the access doc has none and the literal calling **"Kindoo Manager"** when no calling resolves for the scope, so a manager-submitted request renders as `{Name} (Kindoo Manager)`. Only an `active === true` manager doc contributes, and the access doc wins on each field independently — a manager who also holds an access row with a calling for that scope still shows that calling. It degrades gracefully — name-only when no calling applies, and the raw email while the docs load, when both are absent, or when neither carries a name. The derivation is the shared `deriveRequesterDisplay` / `formatRequesterLabel` pair in `@kindoo/shared`, consumed identically by the extension card (§15) and the manager emails (§9). Managers may read any `access` and `kindooManagers` doc (rules gate both collections on `isManager`), so no rule change was needed. A muted top-of-queue note reads "Requests are completed and rejected in the Chrome extension on your computer. With Kindoo open there, you can apply them from here." and links to the extension's Web Store listing. It is deliberately vague about *which* requests, because that is per Kindoo site; the plain-language line directly beneath it names the covered sites and says what to do when there are none (§16). The sectioning / sort logic lives in `@kindoo/shared`'s `partitionPendingRequests`, whose `requestedAtMs` reader handles both a live Firestore `Timestamp` (the web's shape) and the callable's serialised `{ seconds }` / `{ _seconds }` wire shape (the extension's shape), and is consumed by both the web queue and the extension's queue panel (see "Extension queue panel — request-queue parity" in §15). For an **add** request whose member already has a seat, the card shows a blocking **error** chip (completing would collide with the one-per-member seat doc) — **with one carve-out**: a `scope: 'stake'` **`add_manual`** for a member whose seat holds no stake-scope grant is not blocked, because `markRequestComplete` → `planAddMerge` appends a cross-scope stake grant onto that seat rather than colliding with it (§15, "Add for an existing user → Reject-only (with one carve-out)"). That is the exact shape All Seats' own **"Give Access To Stake Buildings"** button produces, so blocking it would have the app tell a manager to reject the request it just told them to file. The chip is add-only — edit and remove cards never show it (their completions modify or target an existing seat, so a pre-existing seat is expected, not a duplicate). **The chip and the withheld Apply via extension button are one decision, not two**: `addBlockedByExistingSeat` in `@kindoo/shared` (`packages/shared/src/existingSeatGate.ts`) is the single definition, so a card can never both say "reject it" and offer to apply. The edit-side analog: for an **`edit_*`** request whose target seat no longer exists (the member's seat subscription has resolved to no document), the card shows an informational **error** chip reading "This request edits a seat that no longer exists." — same `.kd-queue-card-error` styling as the duplicate chip, display-only, no action affordance. The chip gates on the subscription having *resolved* absent (not merely still-loading), so it never flashes during the seat read. A push-notification deep-link (`?focus=<rid>`) scrolls + highlights the matching card on first render, then strips the param from the URL. Self-approval policy (a manager who is also a bishopric/stake member may complete or reject requests they themselves submitted; the audit records both submitter and completer) applies wherever the completion runs — now the extension.
- **All Seats** — full roster across every scope; filter by scope/building/type. When the scope filter is "All" and `stake.stake_seat_cap` is set, a full-width "Seat utilization" bar renders between the filters and the per-scope summary cards (Phase 10.3 — contextual `<UtilizationBar>` follows the current scope filter). The "All" and Stake-scope bars are home-site only — foreign-site ward seats / caps are excluded from both sides (§15, §244). Per-ward bars are unchanged. **All Seats has no edit affordance** — there is no Edit button on any row. Editing a seat flows entirely through the roster pages' `EditSeatDialog` request flow (§6.1), which validates a non-empty building set and creates an audited edit request; no edit dialog writes the seat doc directly. The only mutating action on this page is **Remove**, which generates a `remove` request (it does not delete the seat directly). `member_name`, `reason`, `building_names`, `scope`, `type`, `member_email`, and the canonical-email doc-ID are all immutable from All Seats. The one additional affordance is the manager-only **"Give Access To Stake Buildings"** button on a foreign-site-only member's row — it does not mutate the seat directly either; it opens `GrantStakeAccessDialog` and submits an `add_manual` / `scope: 'stake'` request (§6.1 "Manager-granted stake access for foreign-site-only members").
- **Configuration** — tabs in fixed order: **Config** (the keys `stake_seat_cap`, `timezone`, `notifications_enabled`, `eq_president_app_access`, etc.), **Managers** (KindooManagers), **Kindoo Sites** (§15), **Buildings**, **Wards**, **Organizations**. Buildings come **before** Wards because a ward must reference an existing building: the "Add Ward" button is disabled with an "Add a building first." hint until at least one building exists. **Organizations** sits **last** — a free-standing stake-scope seat pool (`organizations` collection, §3.2 / `firebase-schema.md` §4.12) with no dependency on the other tables. The Organizations tab is full CRUD over `name` + `seat_cap`; `organization_id` (the slug) is not a form field — it is derived from `name` via `buildingSlug()` once at create and **never re-slugged** on edit, so a rename targets the same doc and orphans no seat / request reference. Two client-side guards: **unique display name** (case-insensitive, trimmed; `duplicateOrganizationNameBlocker`), and a **delete guard** that blocks removal while any seat references the org via its primary `organization_id` OR any `duplicate_grants[].organization_id` (`organizationDeleteBlocker`, run against the live seats snapshot — rules can't iterate siblings; seat-only by design — a pending request referencing a deleted org is an accepted gap, the resulting seat resolves to "No Organization" and the operator reassigns). Because seats reference the immutable slug, not the name, renames need no rename-time ref-guard (unlike Buildings — §5.3 building rename block). There are no calling-template tabs — app access comes from the churchwide calling list (§8). The Config tab's **Elders Quorum Presidents Get App Access** switch (`eq_president_app_access`) is the one per-stake app-access control; a save that **flips** it opens the backfill / un-backfill confirm dialog described in §8, and the save lands whichever way the dialog is answered. A building carries an optional Kindoo-site selector (Home / a configured Kindoo Site); a ward has none — its site is derived from its building (§3.2, §15). **Building edit never re-slugs:** the form carries the original `building_id` and the write targets the same doc, so renaming a building does not orphan it or any ward / seat reference. **Building display names must be unique** across the stake — the Buildings UI blocks a save (create or edit) when another building already uses the chosen name (case-insensitive, trimmed). **Renaming a building is blocked while active seats or pending requests still reference its current display name** — the same prevent-reference mental model as the building Delete guard. Because `seat.building_names`, `seat.duplicate_grants[].building_names` (duplicate-site grants — §15 / T-43), and `request.building_names` are display-name snapshots (§3.2), a rename would leave those arrays pointing at the old name; rather than cascade-rewrite them, the Buildings UI blocks the rename with a message naming the counts (e.g. `Can't rename "Black Forest" — 12 seats and 1 pending request reference it. Remove or reassign them first.`) and refuses to write. Only **active seats** and **non-terminal (pending) requests** count — completed / rejected / cancelled requests are historical and never block. A seat counts when the name appears in EITHER its primary `building_names` OR any `duplicate_grants[].building_names` (counted once per seat) — so a member whose primary seat is in another building but who holds a duplicate-site grant on the renamed one still blocks. The guard fires only when the display name actually changes; address / Kindoo-site-only edits (and saves that leave the name untouched) still go through. The slug FK is immutable, so wards are unaffected — only the display-name grant arrays need guarding. Like the Delete guard, this is client-side (Firestore rules can't iterate sibling collections); the Buildings tab subscribes to seats + requests and gates Edit until those snapshots hydrate. The Ward form's building `<Select>` carries the building's `building_id` as its option value; on submit the handler resolves the building's current display name and stores **both** `building_id` (preferred FK) and `building_name` (legacy snapshot) on the ward. **The Ward form has no "Ward code" field** — the code is derived from `ward_name` via `buildingSlug()` once at create and pinned as the immutable doc ID, never shown and never re-derived (an edit carries the existing doc ID through unchanged, so a renamed ward keeps its original code and orphans no seat / request / grant keyed on it). Because the name is now the only visible ward identifier, **ward display names must be unique** across the stake: a create or edit whose name (case-insensitive, trimmed) matches another ward's name is blocked, even when that other ward sits under a legacy 2-letter doc ID the derived slug would not collide with (`duplicateWardNameBlocker` against the live wards snapshot, mirroring `duplicateBuildingNameBlocker`). The create path additionally backstops in its transaction: if the derived doc ID already exists it rejects rather than merging. Wards are sorted by display name in the admin list (legacy uppercase codes would otherwise sort before slug-derived lowercase ones).
- **App Access** — view over the `access/{canonical}` collection. Server-managed grants (`importer_callings`, written by Sync via `syncApplyFix`) are read-only; the manager cannot edit them because the next Sync run would just recreate them. Manual grants (`manual_grants`) have a themed Delete confirmation, and an "Add manual access" modal lets the manager grant app access to someone whose calling isn't on the app-access list for their scope (§8). The modal carries an **Access level** `<select>` — **Full** (the default) or **Limited** — above the Reason field, with a hint reading "Full gives the same authority you have. Limited lets them request temporary access only — up to 90 days — and change or remove just those temporary seats." Choosing Limited writes `level: 'limited'` onto the grant object; choosing Full writes **no `level` key at all** (`firebase-schema.md` §4.5), because grant deletion is an `arrayRemove` matching by deep equality and a stray `level: 'full'` would make the grant undeletable from the UI. **Every row states its tier explicitly**, both tiers, never silently: an empty cell was indistinguishable from a full grant, a render bug, and a stale service-worker bundle. **Full** renders a subtle `info`-variant badge; **Limited** a loud `limited`-variant one (red fill, red border, uppercase, semibold). In the table the chip sits in the **Scope** column after the scope name — a table row is exactly one grant or one importer calling, so the pairing is accurate. In the card view it stays beside each grant's reason (or importer calling), *not* on the card's scope chip, because one scope heading groups grants that can differ in tier. **Both sources read a stored tier; neither is inferred.** Manual grants read the `level` marker on the grant object. Importer rows read `importer_limited_callings[scope]` (§3.2, `firebase-schema.md` §4.5, `architecture.md` D26) and render LIMITED when the row's calling appears there — matched trimmed + case-insensitively, the same key scheme the shared calling sets use — Full otherwise. The chip is **per calling**, not per scope, in both views: a scope holding both a Bishop and an Elders Quorum President labels each row independently. **The page never classifies a calling by name.** Deriving the tier at read time would let the page contradict enforcement: claims re-mint only when the access doc is written, so a calling joining the limited set would leave existing holders with full access while the page labelled them LIMITED. Reading the stored field is what keeps the page, the minted claim, and the rules on one fact. A missing map, a missing scope key, or a malformed value all render **Full**, the same fail-toward-more-access direction the claim minter takes. That is correct, not drift. **There is no edit-level control:** changing someone's tier means deleting the grant and re-adding it at the other level. On desktop the page renders a table; at narrow viewports it swaps to a card stack. The card view sorts by the doc-level `sort_order` (Phase 10.4); the table view's per-row sort is T-29 (open).
- **Audit Log** — filterable view over the `auditLog` subcollection (Phase 8 / Phase 10.3). Cursor-paginated against Firestore; max 100 rows per page. Filters combine as AND: `actor_canonical` (canonical-email compare; literal match against the automated actors — `"RemoveTrigger"`, `"OutOfBand"`, `"Migration"`, `"SyncActor:<code>"` — and the legacy `"Importer"` value for pre-Sync rows), `action` (exact match from the `firebase-schema.md` §4.10 enum), `entity_type` (enum), `entity_id` (exact, case-sensitive), `member_canonical` (cross-collection per-user view), `date_from` / `date_to` (ISO dates, inclusive on both ends in stake timezone — the day boundaries are computed in the stake's `timezone`, so `date_from` resolves to start-of-day and `date_to` to end-of-day in that zone, matching the stake-tz timestamp display). Default window when neither date is supplied is the last 7 days. Deep-linkable via search params. Per-row rendering: a coloured action badge, a one-line summary (with `complete_request.completion_note` surfaced inline for the R-1 no-op case), and a `<details>` block that expands to a Field / Before / After diff table sourced from `computeFieldDiff(before, after)` (T-21).
- **Notifications** (under Account) — push-subscription panel. Five render branches keyed by device state (`push-unsupported`, `push-requires-install`, `push-vapid-missing`, `push-denied`, `push-enable-button`, `push-subscribed-with-toggle`). Per-device subscription via stable `crypto.randomUUID()` persisted in localStorage; subscribe writes the deviceId-keyed token slot to `userIndex/{canonical}.fcmTokens`. Disable on one device leaves other devices' tokens intact. Manager-only for now; the route gate widens for bishopric/stake users in Phase 10.6 (deferred).

### 5.4 Platform Superadmin

Visible iff `principal.isPlatformSuperadmin === true`. A new "Super Admin" section in the app shell's nav (see `navigation-redesign.md` §8) carries one entry:

- **Stake List** (`/superadmin/stakes`) — lists every stake in the platform: `stake_name`, doc ID slug, `created_at`, `setup_complete` flag, and a deep-link to each stake's normal landing page (e.g. the manager Dashboard scoped to that stake). A **Create Stake** button in the page header opens a modal dialog containing the create form, whose fields in order are `stake_name`, a **Stake ID** (the doc-ID slug, which fills itself from the name — see below), `bootstrap_admin_email`, and an optional IANA timezone (defaults to `'America/Denver'`; the field uses the shared `TimezoneCombobox` in `apps/web/src/components/`, constrained to the curated US-IANA list in `usTimezones.ts`). The modal closes on successful submit (the new row arrives via the live stakes subscription), on Cancel, on Escape, or on backdrop click; re-opening it after a successful create yields an empty form. Submit calls the `createStake` Cloud Function callable (superadmin-gated server-side; the web-side render gate is defense-in-depth), which resolves the doc-ID slug, validates collision, lowercases the bootstrap email while preserving dots and `+suffix` (NOT `canonicalEmail()` — see F19 / `firebase-schema.md` §4.1: `isBootstrapAdmin` compares against `request.auth.token.email`, which Firebase Auth always emits lowercased, while Gmail-dot / `+suffix` aliases must survive to keep that escape hatch usable), writes the `stakes/{slug}` parent doc with `setup_complete=false`, and emits a `platformAuditLog` `create_stake` row. An inline hint under the email field (`"Lowercased on save to match the user's Google sign-in address."`) tells the operator the case-normalization will happen — without it, the resulting list row would silently show different casing than what they typed. On successful submit, `CreateStakeForm` does **not** force an ID-token refresh. A forced `getIdToken(true)` was tried and removed (`architecture.md` D28(d)): it ran immediately after the callable resolved, while `syncBootstrapClaims` — an async Firestore trigger on the same stake-doc write — was still in flight, so it lost that race almost every time, fetched a token that still lacked the new `bootstrap` claim, and re-cached it as fresh for the ~1h idle-session staleness window (`firebase-schema.md` §2) rather than letting the tab's existing token refresh on its own schedule. The new stake now becomes switcher-visible the ordinary way, on the tab's next natural token refresh. The **immediate** path is the Stake List row itself: the new row arrives via the live stakes subscription the moment the doc lands, and its link deep-links to `?stake=<slug>`. That link needs no claim at all — the active-stake resolver's URL tier has a superadmin-permissive branch (§2.1) that admits any `?stake=X` value for a platform superadmin with no validation against their accessible set, and `createStake` is superadmin-gated server-side, so whoever just submitted the form is always a superadmin. The named bootstrap admin must then sign in for the bootstrap wizard (§10) to run — superadmin's only act is creating the parent doc. How that admin's own client discovers the new stake before any role claim exists is covered in §2.1 "Pre-claim bootstrap admin" and §10 below.

  **Stake doc ID.** The doc ID is a slug, and the **Stake ID** field *is* the slug — there is no separate preview line, because the input can only ever hold a canonical value. It fills itself from the Stake name, slugified live: every keystroke in the name re-derives `buildingSlug(stake_name)` into the field, so typing `Cottonwood South Stake` leaves `cottonwood-south-stake` sitting there to be read or overwritten. A hint under the field reads `Lowercase letters, digits, and hyphens — defaults from the stake name.`

  **Detach and re-attach.** Editing the Stake ID takes it over: the name stops driving it, and later name edits leave it alone. Clearing it back to empty hands it back — empty means "give me the default", so the name drives it again and blurring an empty field refills it from the current name. The refill waits for **blur** rather than firing the instant the field empties, so an operator who clears it to type a fresh ID doesn't have their keystrokes appended to the default they just deleted. At rest the field always shows the ID the stake will actually get; the one exception is a stake name with nothing to slugify, which leaves it empty. Detachment is per-open form state — a ref reset by the same open-transition effect that `reset()`s the fields — so a re-opened dialog follows the name again.

  **Two slug rules, and the difference is load-bearing.** Auto-fill runs `buildingSlug`, which re-derives from the whole name each keystroke and so has no mid-word state to preserve. Direct typing runs `sanitizeSlugInput` (`packages/shared/src/slugInput.ts`) on every keystroke: the same lowercase / collapse-non-alnum-runs-to-one-hyphen / trim-leading-hyphens rule, except that a **trailing** hyphen survives. Typing `CS North` therefore yields `cs-north` — under plain `buildingSlug` the space would collapse away to `cs` and the next character would land as `csn`. The trailing hyphen is transient and never stored: `buildingSlug` finalizes the field on **blur**, and again on **submit** for a submit that beat the blur. Sanitizing restores the caret to where the operator left it (shifted by whatever the rewrite added or removed), since writing the value back drops it to the end otherwise. `sanitizeSlugInput` is pinned to `buildingSlug` by test — `buildingSlug(sanitizeSlugInput(x)) === buildingSlug(x)` for every `x` — so rewriting the field under the operator can never change the doc ID they end up with. `buildingSlug` itself is unchanged and remains the authoritative rule the server applies.

  **What the callable does with it.** One slug rule over whichever source won: `buildingSlug(stake_id)` when the payload carries a `stake_id` that is non-empty after trim, `buildingSlug(stake_name)` otherwise. A typed `CS North` therefore writes `stakes/cs-north`, exactly as a stake *named* `CS North` would. Because the field auto-fills, `stake_id` rides on essentially every submit from the SPA and the name-derived branch is reached only when the name yields no slug at all — but the two agree by construction: the form sends an already-canonical value and `buildingSlug` is idempotent, so an untouched autofilled ID resolves to the same doc ID the callable would have derived from the name on its own. The form still omits `stake_id` from the payload entirely when the field is empty rather than sending `''` — an absent key means "derive from the name", a different instruction from an empty string, and the callable reads a whitespace-only value the same way. A supplied value that slugifies to empty soft-fails `invalid_slug` and writes nothing: it deliberately does **not** fall back to the name, because the caller asked for a specific doc ID and silently writing a different one is worse than refusing. Sanitize-on-input means the form cannot produce that case — an unslugifiable value empties the field instead — so it is the callable's answer for non-SDK callers.

  The callable's failure envelope mirrors `syncApplyFix`: auth + shape errors throw `HttpsError`; domain misses return `{success:false, error}` so the form maps each code to an inline field error. A non-string `stake_id` is a shape error (`invalid-argument`), like a non-string `timezone`. Soft-fail codes: `name_required`, `email_required`, `invalid_email` (basic shape regex — missing `@`, missing TLD, embedded whitespace), `slug_collision`, `invalid_slug` (slug derivation collapsed to empty, from whichever source produced it), `invalid_timezone` (the value fails an `Intl.DateTimeFormat` round-trip). `invalid_slug` and `slug_collision` attach to whichever field produced the slug — the Stake ID field when the payload carried one, the Stake name field when it didn't. Since the ID field is populated whenever the name slugifies, the name branch is in practice reached only by `invalid_slug` on a name like `###`, which is the case that leaves the ID empty; a `slug_collision` lands on the Stake ID field and says so ("A stake with that ID already exists. Pick a different ID."), because that is where the fix goes — a collision is not a reason to rename the stake. The web form pre-empts `invalid_email` with zod `.email()` client-side and pre-empts `invalid_timezone` by constraining the user to the curated US-IANA list; the server checks are defense-in-depth for non-SDK callers (extension clients, direct REST POSTs). The Stake ID field adds no error code — the two slug failures are the existing ones, now reachable from a second input.

**Apply Fixes (per-stake platform maintenance).** Each Stake List row carries an **Apply Fixes** dropdown that lets a superadmin run a platform maintenance fix against that row's stake — without holding any per-stake role there. The dropdown is driven by an extensible client-side fix registry (`apps/web/src/features/superadmin/fixes.ts`); adding a fix is a one-object change. The first (and currently only) fix is **Backfill Kindoo site IDs**, which invokes the `backfillKindooSiteId` callable (see §15 "One-shot migration"). Selecting a fix opens an Explain dialog (the fix's label + a plain-language description + "Apply to &lt;stake name&gt;?") with **Cancel** / **Apply Fix**; both buttons disable while the fix runs. On resolve, a Result dialog replaces the Explain dialog and renders the callable's returned object **generically** — every scalar field as a key/value row plus the `warnings[]` list — with a **Copy** button that puts the formatted result on the clipboard. On error, the Result dialog shows the error code + message, also copyable. The result rendering is fix-agnostic, so future fixes need no new UI code. The fixes are **superadmin-only server-side**: `backfillKindooSiteId` is gated on the `isPlatformSuperadmin` custom claim (it previously gated on being an active Kindoo Manager of the stake; that gate was removed). The web render gate is defense-in-depth.

The `platformSuperadmins/{canonical}` allow-list itself is **not** managed from the web. Adding or removing a superadmin is a Firestore console write; the `syncSuperadminClaims` trigger picks up the write and mints / revokes the `isPlatformSuperadmin: true` claim. No in-app UI exists for it.

## 6. Request lifecycle

State machine (pending is the only admissible starting state; each terminal state is a one-way flip):

```
              submit
                |
                v
             pending
              / | \
    complete /  |  \ cancel
            /   |   \
           v    v    v
      complete rejected cancelled
```

1. **Submit.** Requester writes a doc to `stakes/{stakeId}/requests/{rid}` with `status='pending'`, `requester_canonical = authedCanonical()`, `requested_at = serverTimestamp()`, and a `lastActor` matching the auth token. Rules enforce: scope is one the requester can submit for (any scope for a Kindoo Manager; otherwise stake-scope iff stake-member, ward-scope iff Bishopric for that ward — §6.1), member_name is non-empty for add types, `building_names` is non-empty for every `add_*` and `edit_*` type regardless of scope, `urgent` is a boolean, and — for a requester carrying `stakes[stakeId].limited` (§4) — the type is one of `add_temp` / `edit_temp` / `remove`, a temp window spans at most 90 days, a ward-scope temp request names exactly the ward's own building, and a `remove` targets a seat whose `type == 'temp'` (§6.1). The `auditTrigger` Cloud Function fans an `auditLog` row. The `notifyOnRequestWrite` trigger fires the new-request email to active managers. `pushOnRequestSubmit` fans push notifications to active managers' subscribed devices.
2. **Manager action.**
   - **Mark Complete** flips `status='complete'` and writes the matching `seats/{canonical}` doc atomically. Add types: client transaction creates the seat with `granted_by_request = requestId` and the chosen `building_names`. Remove type: the `removeSeatOnRequestComplete` trigger handles the seat deletion via Admin SDK (rules cannot read `request.resource.data` on a delete). Two audit rows fan in (one for the request flip, one for the seat write/delete). The `notifyRequesterCompleted` trigger emails the requester. **Organization carry (stake scope only):** `markRequestComplete` stamps the request's `organization_id` onto the seat — onto the new seat's primary grant for an add, onto the stake-grant slot (primary or appended duplicate) in the auto-merge path, and onto the resolved slot for an edit. **Add vs edit are asymmetric.** On an **add** the request form (`NewRequestForm`) never pre-fills org from any existing seat, so the auto-merge onto an existing stake grant re-stamps `organization_id` **only when the request carries a non-null id** — a `null` add never clears an org the seat already holds (this guards against silent loss when a seat appears between submit and completion). The brand-new-seat add still writes `null` when no org is picked (there is no existing org to clobber). On an **edit** the form pre-fills the current value, so the request is authoritative and `null` legitimately clears. Ward-scope completions write `null`; `edit_auto` is forbidden at stake, so no edit-auto path carries an org.
   - **Reject** flips `status='rejected'` with a non-empty `rejection_reason`. One audit row; `notifyRequesterRejected` emails the requester.
3. **Cancel.** Only the original requester may cancel a `pending` request (`request.auth.token.canonical == resource.data.requester_canonical`). Flips `status='cancelled'`. One audit row; `notifyManagersCancelled` emails active managers.

Attempting to complete / reject / cancel a non-pending request is rejected by rules (the `update` predicate requires `resource.data.status == 'pending'`). The client surfaces the rejection as a clean error toast.

Remove-requests follow the same lifecycle; the `complete` action triggers `removeSeatOnRequestComplete` to delete the matching `seats/{canonical}` doc instead of inserting one. Two extra rules apply only to remove:

- **R-1 race (seat already gone at completion time).** If the seat is missing when the trigger fires (a duplicate remove already ran, or Sync removed the temp seat as `sba-only` after Kindoo expired the temp user between submit and complete — §7, §8), the request still flips to `complete`. A `completion_note = "Seat already removed at completion time (no-op)."` is stamped on the request. Only ONE audit row is fanned (`complete_request` on the request — there is no seat to delete). The completion email body surfaces the note (`Note: ...`) so the requester is not confused that nothing visibly changed.
- **Submit-time guards.** A remove submit is rejected by client transaction (rules cannot do a presence check at create time without a `getAfter` against a non-existent doc) if no active manual/temp seat exists for `(scope, member_canonical)`, or if another `pending` remove request for the same `(scope, member_canonical)` is already open. The UI also gates: the remove control is only rendered on manual/temp rows and is disabled when `removal_pending` is set.

**Inline organization edit — the one direct client seat-write.** Setting a stake-roster member's organization from the chip (§5.2) is the **sole** mutation that writes a seat doc directly from the client, deliberately bypassing the request flow (organizations are a stake-scope display concept, not access). Every other seat field is request-only — an `edit_*` request completed by `markRequestComplete`. The direct write is scoped tightly by the Firestore `seats` `update` rule (`firebase-schema.md` §6, §4.12): the actor must be a stake member, the seat must be `scope == 'stake'`, and the write's `affectedKeys()` must be exactly `['organization_id', 'last_modified_at', 'last_modified_by', 'lastActor']` — the `useSetSeatOrganization` mutation writes exactly those four keys, so a hand-crafted write can't smuggle any other field change through this path. See `architecture.md` D21.

### 6.1 Edit-seat requests

In addition to `add_manual`, `add_temp`, and `remove`, managers can mutate an existing seat in place through three edit request types. All three flow through the same Pending Queue → Mark Complete pipeline as the existing add/remove types: requester submits a `pending` request; manager hits Mark Complete; the `markRequestComplete` callable resolves the seat slot and writes the field replacements in the same transaction. The `auditTrigger` fans audit rows on the request flip and the seat update automatically — no new audit semantics.

| Seat type / scope | Edit allowed? | Editable fields | Limited principal? |
| --- | --- | --- | --- |
| **Auto, stake scope** | **No.** Church-granted access to all stake buildings; nothing to remove or constrain. Three-layer defense (see below). | — | No — already forbidden for everyone. |
| **Auto, ward scope** | Yes (`edit_auto`) | `building_names` only (all currently-granted buildings pre-checked + disabled — additions only, per Policy B). | **No.** Auto seats are calling-derived and outside a limited user's authority. |
| **Manual (any scope)** | Yes (`edit_manual`) | `reason` (= the calling name for manual seats) and `building_names`. `seat.callings` is **not** touched (manual seats carry `callings: []` by convention). | **No.** Manual grants are durable. |
| **Temp (any scope)** | Yes (`edit_temp`) | `reason`, `building_names`, `start_date`, `end_date`. | **Yes** — the only editable seat type for a limited principal, subject to the ≤90-day window cap and (ward scope) the building lock. |

**Who can submit.** Three independent branches in the requests `create` predicate (`firestore/firestore.rules`), mirrored on the SPA by `isScopeAllowed` / `allowedScopesFor` (`apps/web/src/features/requests/scopeOptions.ts`). Any one of them authorises the create:

| Role held in the active stake | Scopes they may submit for |
| --- | --- |
| **Kindoo Manager** (`stakes[stakeId].manager === true`) | Every scope — the stake and every ward — for every request type. No `access` row of their own required. |
| **Stake membership** (`stakes[stakeId].stake === true`) | `scope == 'stake'` |
| **Bishopric** (ward code in `stakes[stakeId].wards`) | That ward's scope |

**Manager authority is blanket, not an intersection.** A manager who *also* holds a Bishopric claim for one ward may submit for every other ward too — the manager branch matches first and the ward list stops being the binding constraint. This widens behaviour for managers who already had an `access` row, not only for those without one.

**Platform superadmin status alone grants nothing here.** Only the per-stake manager claim carries request authority. This is a deliberate discrepancy with the nav model (`apps/web/src/components/layout/navModel.ts`), whose `isManager` helper *does* treat a platform superadmin as a manager for the purpose of showing manager nav sections. Request creation does not follow it; the regression is explicitly test-guarded in `apps/web/src/features/requests/tests/scopeOptions.test.ts`.

**Policy 1 survives for managers.** `edit_auto` at `scope == 'stake'` remains forbidden for everyone, managers included. It is an independent conjunct in the rule (evaluated before the role branches) and the first early-return in `canEditSeat`, so no role branch can satisfy it.

The manager branch widens **who** may create, never **what** the payload must carry: the non-empty `member_name` for add types, the non-empty `building_names` for stake-scope add/edit types, the required `comment` on edit types, and every other create conjunct still apply to a manager submit exactly as they do to anyone else's.

**The rule does not verify that the ward code exists.** A manager could write a `scope` naming a ward that isn't in the `wards` collection; the rule admits it rather than spending an `exists()` read. Accepted data-quality gap for a trusted role — see `architecture.md` D24.

**Limited app access narrows the surface, it does not add a branch** (`architecture.md` D25). A requester carrying `stakes[stakeId].limited` (§4) must still satisfy one of the three branches above — the flag grants nothing on its own. **A Kindoo Manager is never narrowed by it**, and not because the manager branch out-ranks the clause: the claim minter refuses to write `limited` at all for a user with an active `kindooManagers` row (`isLimitedTier({ limited, manager })` in `computeStakeClaims`, §4), so a manager who also holds a limited-tier grant carries no flag for `isLimited` to find. The manager branch keeps its full reach structurally. On top of whichever branch admits them, five extra constraints bind a limited requester at creation time:

| Constraint | Rule predicate | SPA mirror |
| --- | --- | --- |
| Type restricted to `add_temp` / `edit_temp` / `remove` — no `add_manual`, no `edit_manual`, no `edit_auto` | `type in ['add_temp','edit_temp','remove']` | `NewRequestForm` renders Temporary as the only option and defaults to `add_temp`; `makeNewRequestSchema(…, { limited })` re-checks it; `canEditSeat` returns false for any `seat.type !== 'temp'` |
| Temp window ≤ 90 days, inclusive of both endpoints | `tempWindowWithin90Days` — a `timestamp.date()` subtraction compared against `duration.value(90, 'd')` | `exceedsLimitedTempWindow` (`packages/shared/src/tempWindow.ts`), wired into both `makeNewRequestSchema` and `makeEditSeatSchema` as an error on `end_date` |
| Ward-scope temp requests locked to exactly that ward's building | `limitedWardBuildingOk` — `data.building_names == [limitedWardBuildingName(…)]`, an exact one-element equality (no supersets) | `NewRequestForm` and `EditSeatDialog` both drop the buildings checklist for a read-only row naming the ward's building and force `building_names` to that single name, resolved via `defaultBuildingsForScope` |
| `remove` only against a seat whose `type == 'temp'` | `limitedRemoveTargetIsTemp` — a `get()` on `seats/{seat_member_canonical}` compared against `'temp'` | `canRemoveSeat` |
| `edit_temp` only against a seat whose `type == 'temp'` | `limitedEditTargetIsTemp` — a `get()` on `seats/{member_canonical}` compared against `'temp'`. Note the different seat key: edit requests target `member_canonical`, removals `seat_member_canonical` | `canEditSeat` |

Exactly 90 days passes and 91 does not, on both sides. `tempWindow.ts` does its arithmetic on UTC midnights precisely so a window straddling a DST transition can't measure 89.96 days on the client and 90.04 in the rules. The whole limited clause is the **last** conjunct of the create predicate, after the ISO-shape and `start_date <= end_date` checks, so the date split inside `tempWindowWithin90Days` is always operating on well-formed input; and it short-circuits on `!isLimited(stakeId)`, so a full user never pays for the document reads the ward and seat checks need.

**Both sides resolve "the ward's building" id-first.** `resolveWardBuilding` (`packages/shared/src/resolveWardSite.ts`) is the client's resolver — `ward.building_id` → that building's current `building_name`, falling back to the ward's own `building_name` snapshot — and the rules' `limitedWardBuildingName` reproduces it: `ward.get('building_id','')` non-empty *and* `exists(buildings/{bid})` → `buildings/{bid}.building_name`, else the raw `ward.building_name`. Reading the ward's `building_name` directly would have demanded a **stale** name, because `buildingRenameBlocker` blocks a building rename only while a seat or pending request pins the old display name and never consults `wards` — a ward with no seats can therefore have its building renamed out from under its snapshot (T-74). The client would then send the current name and the rules would insist on the old one, locking the limited user out behind an opaque permission error. Rules ternaries short-circuit, so a dangling `building_id` falls through to the name path instead of erroring the predicate; `Map.get(key, default)` is used over bare field reads for the same reason. Degenerate input still fails closed: a missing ward doc denies, and a ward with neither a resolvable id nor a non-empty name resolves to `''` and fails the size guard. The ward-scope create path costs at most four document accesses of the ten a single-document request allows: ward `get`, building `exists`, building `get`, plus the seat `get` on a ward-scope `edit_temp`. A stake-scope `edit_temp` costs one, `add_temp` three, `remove` one.

**The client is always at least as strict as the rules.** The single asymmetry runs the safe direction: a ward whose `building_id` dangles *and* whose `building_name` matches no live building resolves to `undefined` on the client (Submit blocked, blocked-message rendered) while the rules would accept that raw name. The UI never offers a submit the rules would reject.

`canRemoveSeat` is **deliberately stricter than the rule**: it requires both the seat's primary `type` and the specific grant row being removed to be temp, while `limitedRemoveTargetIsTemp` can only see the seat's primary `type` (a rules `get()` can't cheaply prove which `duplicate_grants[]` row a removal targets). The asymmetry is one-directional — everything the client admits the rules also admit — and exists so the UI never renders a Remove button whose submit the server would reject. Callers keep their own `grant.type !== 'auto'` gate on top; auto grants are calling-managed for everyone.

**Enforcement is at creation time only — there is no `markRequestComplete` third layer.** This is the deliberate difference from Policy 1 below, which does defend in three layers (UI, rule, callable). A requester's tier can legitimately change between submit and complete: a manager may add a full grant, or delete the last limited one, in the days a request sits in the queue. Re-checking the tier at completion would reject a request that was valid when submitted, for a reason the completing manager can neither see on the card nor fix. The completing manager is a human review step, and the request document is immutable between submit and complete on every field the limited clause constrains, so nothing can be smuggled past the create gate afterwards. A limited user editing a temp seat whose **existing** window already exceeds 90 days therefore has to shrink it before the form will submit — the cap is on what they may request, not on what already exists.

**Manager-granted stake access for foreign-site-only members ("Give Access To Stake Buildings").** A Kindoo Manager can grant a foreign-site-only ward member access to home-site stake buildings without waiting for that member to submit their own request. The affordance is a per-member button on the manager **All Seats** page (§212), rendered only when the viewer holds a manager claim in the active stake, the member is *foreign-site-only*, and the member has no existing stake-scope grant. A member is **foreign-site-only** when their seat holds ≥1 grant, every grant resolves to a foreign Kindoo site, no grant resolves to the home site, and there is no stake-scope grant (`isForeignSiteOnly` / `hasStakeScopeGrant` in `apps/web/src/lib/foreignSiteOnly.ts`; site resolution mirrors `siteLabelForGrant` — a grant's own `kindoo_site_id` wins, falling back to the grant's ward → building site, and a stake-scope grant always resolves to home, short-circuiting the predicate). The button renders once per seat (on the primary row) so a member's multiple grant rows don't each carry it. Clicking it opens `GrantStakeAccessDialog` (`apps/web/src/features/requests/components/GrantStakeAccessDialog.tsx`): scope is locked read-only to **Stake**, the building checklist is filtered to home-site buildings only (`filterBuildingsBySite(buildings, null)` — stake scope is home per §15), a free-text **reason** is required (not the calling typeahead — a stake-building grant isn't calling-derived), a **comment** is optional, ≥1 building is required, and a red `.kd-danger-banner` warns exactly: "Giving this user access to these buildings will consume an additional Kindoo license." (the `BANNER_TEXT` constant; `grantStakeAccessSchema` in `apps/web/src/features/requests/schemas.ts`). Submit creates an ordinary `add_manual` / `scope: 'stake'` request through the existing `useSubmitRequest` path — there is no special request type and no client-side seat write. The dialog is unchanged by the blanket manager authority above and remains the entry point for this flow: the license warning and home-site building filter are what make it distinct, not the authority it carries. (The rule no longer needs a dedicated `add_manual` branch to admit the submit — the manager branch subsumes it.) The end-to-end result — a parallel-site stake grant appended to the member's existing seat, and the additional Kindoo license the banner warns about — is described in §15 "Manager-granted stake access — parallel-site grant on completion."

**Policy 1 — stake auto seats are non-editable.** Three layers of defense:

1. **Web UI** hides the Edit button on stake auto rows on the Roster pages. (All Seats has no Edit button on any row — see §212 — so this rule applies to the Roster pages only.)
2. **Firestore rule** rejects creation of an `edit_auto` request when `scope == 'stake'` — see `firestore/firestore.rules` §requests.create.
3. **`markRequestComplete` callable** rejects `edit_auto` completion when `scope === 'stake'` with `permission-denied` — see `functions/src/callable/markRequestComplete.ts`.

**Policy B — `edit_auto` building selection.** The auto-primary's current `building_names` (the importer's seed plus any prior `edit_auto`-added extras) are pre-checked AND disabled in the edit modal. Operator can ADD other ward-site buildings beyond them; cannot REMOVE any currently-granted building (the constraint exists because the `edit_auto` callable path REPLACES the auto-primary's `building_names` with the request body — silently dropping a previously-added building would be a destructive edit). The dialog distinguishes two related sets:

- **Visual lock** (`lockedBuildings` in `EditSeatDialog`): the union of the auto-primary's `building_names` and any same-scope non-auto DuplicateGrant's `building_names` (manual or temp). This mirrors what the collapsed AllSeats / roster row displays (PR #166's same-scope collapse) so the user sees the same building set on both surfaces; every locked checkbox carries a tooltip explaining why it cannot be unchecked. Locking the full union is the honest UX — the `edit_auto` request type cannot touch DuplicateGrants, so allowing the operator to uncheck a dup building would no-op silently.
- **Submit-included set** (`autoOwnedBuildings` in `EditSeatDialog`): ONLY the auto-primary's current `building_names`. The wire body is `autoOwnedBuildings ∪ operator-additions`; same-scope DuplicateGrant buildings are deliberately excluded from the submit. The `markRequestComplete` callable's `planEditSeat` for `edit_auto` replaces the auto-primary's `building_names` and does not visit the duplicate-grants array, so absorbing dup buildings into the wire body would double-credit the user on display (still in the dup) and double-provision on Kindoo (now also on the auto-primary's set).

Future work could decompose the submit into multi-request coordination (`edit_auto` plus `edit_manual` / `edit_temp` / `remove` for the dup) so the operator can prune dup buildings from the same modal; until that lands, the conservative lock keeps the data clean. The constraint on the auto-primary's own buildings is resolved from `seat.building_names` — there is no other per-calling building source. Stake-scope auto seats never reach this modal (Policy 1).

**`edit_manual` reason semantics.** Manual seats store the operator-typed calling name in `seat.reason` (not `seat.callings`, which stays `[]`). The `edit_manual` request's `reason` field replaces `seat.reason` verbatim. `seat.callings` is left untouched.

**Organization on edit.** For stake-scope `edit_manual` / `edit_temp`, the `EditSeatDialog` shows the Organization selector pre-filled from the seat, and `planEditSeat` replaces the resolved slot's `organization_id` (top-level for a primary match, on the entry for a duplicate match) from the request — `null` clears. The selector never renders for `edit_auto` (forbidden at stake) or for ward-scope edits, and `markRequestComplete` only carries `organization_id` for stake-scope `edit_manual` / `edit_temp`. The inline chip (§5.2) is the faster path for re-orging a primary stake grant without a request; the edit-form path additionally reaches a parallel-site stake *duplicate* grant, which the chip leaves read-only.

**Comment required on edit requests.** All `edit_*` requests require a non-empty `comment` field at creation time. Enforced by (a) the shared `accessRequestSchema` zod refinement (trimmed non-empty) for any parse-side consumer, (b) the Firestore rule predicate on creation (non-empty string), (c) the web form (`EditSeatDialog`) blocks submit with an inline error when the comment is empty or whitespace-only. The rule predicate is intentionally looser than the schema (Firestore rule expressions have no string-trim primitive), so a hand-crafted REST POST with whitespace-only `comment` would pass the rule even though the SDK / form layer rejects it; the SPA's submit path trims before write, so this gap is reachable only by non-SDK clients. Add and remove requests are unaffected — their existing comment behavior is preserved (optional at the wire boundary; the cross-ward-add comment-required rule lives in the web form schema, not the wire schema).

**Slot resolution** (in `planEditSeat`, `functions/src/callable/markRequestComplete.ts`): primary `(scope, type)` match wins; otherwise walk `seat.duplicate_grants[]` for the first `(scope, type)` match. If neither matches, the callable throws `failed-precondition` (no editable slot found). Edits never change scope/type, so per-pool counts are unchanged — the callable skips the over-cap recompute (responsibility split with `removeSeatOnRequestComplete`).

**Edit badge in the Pending Queue.** Edit requests render with a distinct "Edit (auto)" / "Edit (manual)" / "Edit (temp)" type badge so managers can disambiguate them at a glance against add/remove.

**Audit trail.** `markRequestComplete` stamps the manager's email on both the request flip (`lastActor`, `completer_*`) and the seat update (`lastActor`, `last_modified_by`). The `auditTrigger` fans one row per write, same as add/remove. No new audit `action` values needed (existing `update_seat` and `complete_request` cover edits).

**Extension Provision flow — direct-grant awareness.** Before writing AccessSchedules to Kindoo, the extension orchestrator (`provisionAddOrChange` and `provisionEdit` in `extension/src/content/kindoo/provision.ts`) consults the user's actual door grants (via `KindooGetUserAccessRulesLightWithTotalNumberOfRecordsWithEntryPoints`) and the per-rule door sets (via `KindooGetEnvRuleWithEntryPointsFormatted`). Any AccessRule whose door set is fully covered by the user's existing direct door grants (typically Church Access Automation's auto-grants) is skipped — the extension does not write a redundant AccessSchedule for a building the user already has access to via direct door grants. This avoids the duplicate-rule pollution scenario where MERGE semantics on `saveAccessRule` would otherwise create a parallel AccessSchedule for the same building. The strict-subset chain lives in `extension/src/content/kindoo/sync/buildingsFromDoors.ts` (also used by the Sync drift report). On derivation failure (transient Kindoo error during the rule-door / user-door reads) the orchestrator logs a `[sba-ext]` warning and falls back to the legacy `targetRids - currentSchedules` diff — the provision still completes; in the worst case a redundant rule is written rather than blocking the operator.

## 7. Temporary-seat expiry

Temp seats are time-bound in Kindoo, which is authoritative for seats; SBA runs no expiry scheduler of its own (the Phase 8 `runExpiry` Cloud Function was retired 2026-06-05 — `architecture.md` D19). The SBA seat is held through its end date; when Kindoo expires the temp user's access, the extension's Sync detects the now-orphaned SBA seat as `sba-only` and removes it via the existing "Remove From SBA" path (§8).

## 8. Auto-seat ingestion

Auto seats, calling-change detection, and calling-end removal flow through the companion Chrome extension's Sync feature (see §15 Phase 4 for the active-site resolution and per-site scoping rules; parser, detector, and fix-path live in `extension/src/content/kindoo/sync/`). Sync reads the operator's live Kindoo session — which Kindoo already populates from LCR via Church Access Automation — parses each Kindoo user's Description for scope + callings, derives the seat **type** from the Kindoo role (`DepartmentType`) and, for Guests, from observed door grants (see "Seat type from Kindoo role, then door grants" below), and applies the resulting fixes through the `syncApplyFix` callable. There is no separate weekly LCR Sheet importer.

**Kindoo is authoritative; Sync never writes SBA → Kindoo.** Every Sync fix is an SBA-side mutation that reconciles the SBA seat to Kindoo's observed state; Sync does not push anything into Kindoo. Provisioning *into* Kindoo (inviting a user, writing AccessSchedules) happens exclusively through the request flow's provision orchestrator (§6.1, §15), never through Sync. The per-discrepancy fixes:

- `kindoo-only` (a Kindoo user with no SBA seat from which a seat **can** be derived) → **Create SBA seat**. The grant-derived type for the seat-to-create follows the role/grant ruleset below (temp → `temp`; Administrator/Manager → `auto`; Guest with ≥1 church-direct grant → `auto`; else `manual`). **Exception:** a Guest with a **blank** Description (empty or whitespace), no church-direct grant, and no seat has nothing to derive a seat from — the would-be type is `manual` but there is no scope/calling to mint — so it is emitted as a `kindoo-no-description` **review** row, not an actionable `kindoo-only` drift. A blank Description still yields an actionable `kindoo-only` drift when the type is otherwise derivable: temp (`temp`), Administrator/Manager (`auto`), or a Guest with ≥1 church-direct grant (`auto`). A **non-blank** Description (parseable, or present-but-unparseable) with no grant still produces the `kindoo-only` drift — the parsed intended scope/calling is meaningful.
- `callings-mismatch` (auto seat whose `callings[]` differ from Kindoo's parsed primary calling(s)) → **Update SBA** — **replaces** the seat's `callings[]` wholesale with Kindoo's full parsed set (Kindoo is authoritative, so a renamed calling replaces the old name rather than sitting beside it). A true sibling of `scope-mismatch` / `buildings-mismatch`: the detector (auto seats only) emits it whenever the two differ as normalized sets in **either direction** — rename, add, or drop — comparing trimmed + case-insensitively, and only when Kindoo's target set is non-empty. Severity **drift**. Beyond the seat's `callings[]` and `sort_order`, the callable **reconciles the scope's `importer_callings`**: a replace can *remove* app access (the prior callings may have been on the app-access list the new ones aren't), so it rewrites `importer_callings[scope]` to `filterAppAccessCallings(scope, newCallings)` — evaluated against the stake's Elders Quorum President opt-in (§8) — when that yields a grant and clears the scope's entry otherwise (deleting the doc when both maps go empty, `manual_grants` preserved). It rejects an empty target set.
- `scope-mismatch` → **Update SBA** only — flip the seat's `scope` to Kindoo's parsed primary scope. When the new scope is a **ward** (off stake), `applyScopeMismatch` also clears `organization_id` (`FieldValue.delete()`) — organizations are stake-scope-only, so a seat leaving stake scope sheds its org. The other `syncApplyFix` paths (`kindoo-only` create, `callings-mismatch` / `buildings-mismatch` update, and the auto-merge) **preserve** a client-set `organization_id` — only this stake-departure clears it.
- `type-mismatch` → **Update SBA** only — flip the seat's `type` to the role/grant-derived target (`grantTargetType`; PROMOTE → auto, DEMOTE → manual). PROMOTE fires for an Administrator/Manager seat that isn't already `auto`, or for a Guest holding ≥1 church-direct grant; DEMOTE fires only for a Guest with zero church-direct grants (see "Seat type from Kindoo role, then door grants").
- `buildings-mismatch` → **Update SBA** only — replace the seat's `building_names` with the door-grant-derived set.
- `kindoo-unparseable` (Kindoo Description is **present** but doesn't match the `Scope (Calling)` convention) is treated as a **church-wide calling**, for **every seat role** (managers can hold seats too — there is no Guest gate). The detector gates the actionable row two ways: it produces the **"Update SBA"** drift row only when (a) the active Kindoo site is the **home** site — on a foreign site the row is suppressed entirely, since "apply to stake scope" is a home/stake concept; and (b) the SBA seat is **not already aligned** to the stake target (`scope==='stake'` plus the calling recorded per type — `callings===[description]` for auto, `reason===description` for manual/temp, case/whitespace-normalized). Once the operator applies the fix, or the seat already matches, the row resolves and disappears on the next Sync run like every other drift code. On apply, the `syncApplyFix` callable moves the seat to `scope='stake'`, **clears `kindoo_site_id`** (stake-scope primaries resolve to the home site — see §15), preserves its existing `type`, and sets the calling from the raw Description text per the §6.1 seat-shape convention (auto → `callings[]`; manual/temp → free-text `reason`, callings cleared, temp dates preserved). For an **auto** seat the callable reaps the OLD scope's calling-derived access (`importer_callings[oldScope]`) and then, **iff** the calling is in the **stake** app-access calling list (see "App access" below — the Elders Quorum President opt-in gates the ward set only, so it never changes this branch), writes a fresh `importer_callings['stake']` so the member keeps stake-scope app access. "Unparseable" only means the Description didn't match `Scope (Calling)`; a bare app-access calling name (e.g. `Stake Clerk`, no parens) reaches this path and *is* in the stake list, so its app access is preserved rather than silently dropped. A calling outside the list earns no new grant (old scope still reaped; the access doc is deleted when its `importer_callings` and `manual_grants` both end up empty).
- `kindoo-no-description` (Kindoo Description is **blank** — empty or whitespace) → **review-only, no action**. Nothing can be derived from an empty Description, so the row surfaces for the operator's manual judgment with no fix button. Two cases reach this code: a member with **both** sides present (SBA seat + blank-Description Kindoo user), and a member with **no SBA seat** whose blank-Description Kindoo add would otherwise be a `manual` `kindoo-only` row (Guest, no church-direct grant — nothing to mint a seat from; see `kindoo-only` above). In the no-seat case the row's `sba` block is `null`, matching the `kindoo-only` rendering.

A `severity: 'review'` Sync row **never renders an action** — `fixActionsFor` returns no buttons for any review row, regardless of code. The display-only Sync rows are therefore: `kindoo-no-description` (blank Description — both the both-sides case and the no-seat, no-grant Guest case) and the defensive "Description parsed but resolved no primary segment" fallback (emitted as `kindoo-unparseable`, review — routing a parseable string to Update SBA would corrupt the seat). Every other discrepancy code offers an SBA-side action.
- `sba-only` (an SBA seat with no Kindoo presence) → **Remove From SBA** — the seat is an orphan because the authority (Kindoo) doesn't have it, so the `syncApplyFix` callable deletes it (or, when the seat carries `duplicate_grants[]` for other sites, promotes the first duplicate to primary rather than nuking parallel access). The delete mirrors `removeSeatOnRequestComplete`'s seat-removal semantics. **The removal also reaps the removed scope's calling-derived access:** it clears `importer_callings[scope]` from the member's `access/{canonical}` doc (so `syncAccessClaims` stops granting SBA app access on the strength of a calling whose seat is gone), **preserves `manual_grants`** (deliberate manager grants are independent of seats) and every other scope's `importer_callings`, and deletes the access doc only when both maps end up empty. For an auto orphan this drops real access; for a manual/temp orphan (no `importer_callings`) it is a no-op. In the duplicate-grant promote case only the removed primary's scope is reaped — the promoted scope's `importer_callings` survives. The reap uses `clearImporterCallingsForScope`, the same helper the `type-mismatch` demote path uses.

There is no "Provision in Kindoo" or "Update Kindoo" Sync action — `scope-mismatch` and `buildings-mismatch` no longer offer a Kindoo-side button, and the CS-side Kindoo-write orchestrator that backed those actions has been removed. The display-only (no-action) Sync rows are the three review cases enumerated above.

**Seat type from Kindoo role, then door grants.** Seat type (`auto` / `manual` / `temp`) is **observed**, not predicted from calling templates. The detector branches first on the Kindoo **role** — the `DepartmentType` enum carried on every bulk environment-user record — and only falls through to door-grant provenance for Guests.

`DepartmentType` (Kindoo's role enum, present on every bulk environment-user record):

| Value | Role |
|---|---|
| `0` | Administrator |
| `1` | Manager |
| `2` | Guest |
| `3` | Installer |

The type-determination ruleset, evaluated **in order** (in `kindooRole` + the `detect()` branches in `detector.ts`):

0. **Installer (`DepartmentType 3`)** → **not classified.** A 3rd-party access vendor; Sync skips the user entirely — no seat, no discrepancy row of any kind (kindoo-only, type/buildings/callings-mismatch, unparseable, scope-mismatch). The skip lands after the `sba-only` branch (which has no Kindoo user) and before every branch that needs a live Kindoo user, so one `continue` suppresses all installer rows at once.
1. **Temp (`IsTempUser`)** → `temp`. Time-bound (`IsTempUser` + expiry); never promoted or demoted. Orthogonal to role and to grant provenance.
2. **Administrator (`0`) / Manager (`1`)** → `auto`, **forced.** A non-Guest role is admin-managed church-owned access, so the seat is `auto` regardless of grant backing; the Guest grant check below is **bypassed**. (Any concrete `DepartmentType` other than `2`/`3` is treated the same way — force-auto.)
3. **Guest (`2`, or role unreadable)** → type is **observed from door grants**:
   - grant data unreadable (`directGrantBuildings === null`, the per-user door fetch failed) → **leave the type unchanged** (no reclassify — never demote on unknown provenance).
   - **any** church-direct grant (`directGrantBuildings` non-empty — the member holds ≥1 door whose **grantor** is the Church Access Automation: `GrantedBy.Username === sentry@groups.churchofjesuschrist.org` or `GrantedBy.IsSuperApi === true`) → `auto`.
   - **zero** church-direct grants (`directGrantBuildings === []` — every door the member holds is SBA-provisioned via an AccessRule) → `manual`.

A door is a church direct grant by its **grantor**, **not** by `AccessScheduleID`: real church grants carry `AccessScheduleID: -1`, not `0`. The Guest decision is **any church-direct grant**, not the seat's building-set coverage — a single church-direct door is enough; the seat's own `building_names` no longer enter the type decision (they still drive `buildings-mismatch`). This supersedes the prior "all of the seat's building doors are church-backed" (subset) rule. The predicate lives in `isChurchBacked` / `grantsBackAuto` (`detector.ts`), reading the per-user door-grant rows from `getUserAccessRulesWithEntryPoints`.

**Promote / demote (existing Guest seat).** For a Guest seat that isn't `temp`: **promote `manual → auto`** when the member holds **any** church-direct grant; **demote `auto → manual`** only when there are **zero** church-direct grants (`[]`, not `null` — a failed fetch is `null` and is skipped, never demoted). Administrator / Manager seats are handled by the force-auto branch above (promote a non-`auto` admin seat to `auto`; an already-`auto` admin seat emits no type row) and never reach the Guest grant decision. Practical effect: a Guest with a calling (the church grants ≥1 door) is `auto` even when they also carry some SBA-provisioned access; only a Guest whose access is **entirely** SBA-provisioned is `manual`. Installers and Admins/Managers are role-decided, not grant-decided.

SBA still *provisions* every new Kindoo seat as a **Guest** (`UserRole: 2` on the invite wire shape, `KindooInviteUserPayload`); `DepartmentType` is the role read back off the live roster. The full design (incl. the self-healing lifecycle and the prefer-church door dedup) is in `extension/docs/sync-design.md` §"Grant-derived seat type".

**App access.** Whether a member gets in-app (web/SPA) access is decided by a churchwide calling list with exactly one per-stake degree of freedom (the Elders Quorum President opt-in, below). There are no `wardCallingTemplates` / `stakeCallingTemplates` collections, no Configuration tabs to edit them, and no `give_app_access` / `auto_kindoo_access` / `sheet_order` template fields. App access is granted **iff** the member's calling is in the list for their scope (`packages/shared/src/appAccessCallings.ts`, matched trimmed + case-insensitively):

- **Stake scope:** Stake President; Stake Presidency First Counselor; Stake Presidency Second Counselor; Stake Clerk; Stake Executive Secretary; Stake High Councilor.
- **Ward scope:** Bishop; Bishopric First Counselor; Bishopric Second Counselor; Ward Clerk; Ward Executive Secretary — plus **Elders Quorum President** when the stake has opted in.

Every calling on those lists confers **full** app access except **Elders Quorum President**, which confers **limited** access (§4, `architecture.md` D26). The tier is written onto the access record as `importer_limited_callings[scope]` by whichever writer inserts the calling; no read path derives it from the calling's name. `LIMITED_TIER_CALLINGS` / `filterLimitedTierCallings` (`packages/shared/src/appAccessCallings.ts`) hold that one name and are consulted on write paths only.

Apart from that one gated ward calling the list is **exclusive**: no wildcard mechanism, and no other per-stake customization. Sync's `syncApplyFix` populates `access.importer_callings[scope]` from `filterAppAccessCallings(scope, callings)` (the subset of a seat's callings that hit the scope's list) and, in the same write, `access.importer_limited_callings[scope]` from `filterLimitedTierCallings` over that subset; a scope whose callings yield no match gets both entries cleared. Because the list is the only criterion, any app access a member previously held through an off-list calling (or via a wildcard template) is **revoked on the next Sync run** that touches their seat. Seat **type** is unaffected — it stays role-derived (`DepartmentType`) + door-grant-derived (see "Seat type from Kindoo role, then door grants" above), never template-derived. Seat / access `sort_order` and roster ordering use the canonical churchwide `callingSortOrder` table (`seatCallingOrder()`), which already ranks Elders Quorum President — the opt-in changes who gets access, never how anyone sorts. See "Roster sort order" below.

**The Elders Quorum President opt-in.** `stake.eq_president_app_access` (boolean) is the only per-stake app-access control. It is **opt-in — absent means off** — and is read as `=== true` everywhere, deliberately the opposite defaulting from `notifications_enabled` (`?? true`). `true` adds **Elders Quorum President** to the **ward** calling set for that stake only; the stake set is never affected, and the match is on the exact title — the quorum's counselors and its secretary never grant access. The plumbing is an optional `AppAccessOptions { eqPresidentAccess?: boolean }` trailing parameter on `appAccessCallingsForScope` / `filterAppAccessCallings`; the two exported arrays are unchanged. `syncApplyFix` reads the stake doc **once** per invocation (after the manager gate, before the drift-type switch) and threads the options into `applyKindooOnly`, `applyCallingsMismatch`, `applyTypeMismatch`, and `applyKindooUnparseable` — the last is inert, since it probes the stake set. A missing stake doc reads as off. A config flip landing mid-Sync-run is a benign race: the next run re-detects the row and heals it. The extension's `pickPrimarySegment` / `pickSegmentForSite` tiebreak takes the same flag off the stake doc the content script already holds, so drift rows agree with the server on which segment grants access.

**The toggle is not retroactive in either direction.** Flipping it changes only what future Sync runs derive — **turning it off revokes nothing by itself.** No drift code detects "access disagrees with the toggle", so an existing Elders Quorum President keeps app access until Sync next rewrites that seat's callings. Symmetrically, turning it on grants nothing until Sync touches each seat. Reconciling existing access is a separate, explicitly confirmed action.

**Backfill / un-backfill dialog.** The switch (labelled "Elders Quorum Presidents Get App Access") lives on Configuration → Config (§5.3) and on the bootstrap wizard's Step 1 (§10). Saving the Config tab with a **changed** value opens a confirm dialog offering the reconcile pass — OFF→ON "Grant access now", ON→OFF "Revoke access now"; declining ("Not now" / "Leave access in place") leaves existing access docs exactly as they were. **The config save always lands regardless of the dialog answer** — the dialog is a second, optional action, and a failed backfill is a delay rather than a broken state. The dialog is suppressed unless `stake.setup_complete === true`; the wizard never raises it, because a stake still in setup has no seats to reconcile.

**`backfillEqPresidentAccess` callable.** `{ stakeId, direction: 'grant' | 'revoke' } → { ok, seats_matched, docs_written, docs_deleted }`. Auth is **active Kindoo Manager of the stake**, read from `kindooManagers/{canonical}` directly rather than from the custom claim (which can be ~1h stale on an idle session) — the same check `syncApplyFix` uses. `direction` is validated against the stake's **current** config: `grant` requires the flag ON, `revoke` requires it OFF, `failed-precondition` otherwise, so a stale dialog confirmation fails loudly instead of writing the wrong side. The sweep runs one `where('type','==','auto')` query (single-field; no composite index) and filters in memory to ward-scope seats whose `callings[]` carry the exact title, ordered by `member_canonical` for a readable audit fan-out. Per seat, one transaction **merges only the Elders Quorum President entry** into or out of `importer_callings[scope]` — never a wholesale replace of that scope's list, so unrelated stale entries are left alone — and `manual_grants` is neither read-modified nor deleted. Grant stamps `importer_limited_callings[scope]` for the entry it inserts; revoke removes the calling from both maps. Revoke deletes the access doc only when `importer_callings` empties **and** no manual grants remain. Both directions are idempotent: a grant whose scope entry already carries the calling, or a revoke whose entry doesn't, writes nothing. `sort_order` is handled asymmetrically, deliberately: **grant** keeps the lower of the doc's prior value and the Elders Quorum President order (`pickMin`), following `writeAccessForAutoScope`'s precedent, while **revoke** re-derives from `seatCallingOrder()` over everything left in `importer_callings` — a removal can strand the stored value on a calling the member no longer holds. That is stricter than `clearImporterCallingsForScope`, which leaves the prior value in place. Audit rows fan through `auditTrigger` and claims through `syncAccessClaims`; the callable writes neither. The actor is the calling manager — a human-confirmed action, not a synthetic system actor.

**Roster sort order.** The bishopric Roster, stake Roster, Ward Rosters, and manager All Seats surfaces sort seats at **render time** from a compiled churchwide `calling → order` table (`packages/shared/src/callingSortOrder.ts` — stake callings, then ward callings; exact trimmed case-insensitive match, no wildcards) keyed on the seat's `callings` (auto) / `reason` (manual). The denormalized `seat.sort_order` (now stamped from the same `seatCallingOrder()` table, not from any template) is **no longer read by the web** (it stays stamped, vestigial). Ordering:

- **Type bands first**: auto, then manual, then temp.
- **Auto band**: by calling order — a multi-calling seat uses the **MIN** order across its `callings[]`.
- **Manual band**: by calling order of the free-text `seat.reason` (manual seats carry `callings: []` and store the calling in `reason`, per §6.1). The single reason string is matched against the table.
- **Temp band**: by `end_date` descending (soonest-expiring at the band bottom) — temps carry a free-text reason, not a roster calling, so calling order does not apply.
- **Unknown** within the auto / manual bands (no calling / reason matches the table) → bottom of the band, then `created_at` ascending (oldest first), then `member_name`.
- **All Seats (cross-scope)**: scope-primary (stake first, then wards alphabetical by `ward_code`) is preserved; the banding above applies within each scope. The grant-overlay shim feeds the same comparator, so All Seats and the per-ward rosters order identically.

The compiled table is global (the calling hierarchy is churchwide), so there is no per-stake roster-ordering customization.

**Cap interaction.** The over-cap calc lives in `functions/src/lib/overCaps.ts`; today's call sites are `markRequestComplete` and `removeSeatOnRequestComplete`. After the importer's removal, **`syncApplyFix` does NOT recompute over-caps** — Sync-driven auto-seat additions / removals (including temp-seat releases that come through the `sba-only` path, §7) leave `stake.last_over_caps_json` unchanged until the next request completion picks up the new seat count. For each ward with `seat_cap > 0` an over-cap is flagged when the count exceeds the cap. For the stake an over-cap fires when the **home stake portion-cap** (`stake_seat_cap - sum(home-site ward seats)`) is exceeded by the **home stake count** (`stakeN`). `stakeN` is stake-primary seats (primary `scope === 'stake'`) **plus** one unit for each foreign-ward-primary seat that also carries a `scope: 'stake'` entry in `duplicate_grants[]` — a manager-granted parallel-site stake grant (§6.1). That parallel-site grant consumes a home Kindoo license the primary-scope count can't see: the primary is foreign (drawn from a foreign site's pool, not `'stake'`), so without the fold the home license is invisible to the cap. Double-counting is avoided — a stake duplicate on a seat already in the home pool is skipped (stake-primary is already in `stakeN`; home-ward-primary is already in `homeWardSeatsN`). The invariant is that **each member contributes at most one unit to `stakeN + homeWardSeatsN`**. Foreign-site ward seats (§15) are otherwise excluded from both sides of the home-stake calculation — they come out of a different Kindoo site's pool, not the home stake's — but each foreign-site ward's own over-cap fires normally against its own `seat_cap`. The result array is persisted to `stake.last_over_caps_json`; when it transitions empty → non-empty, `notifyOnOverCap` emails active managers (Phase 9). No audit row is written by the recompute — the importer-era `over_cap_warning` row is preserved on pre-T-45 audit history for filtering, but no new writes produce it. Accepted regression at v1 scale (12 wards, ~250 seats, 1–2 requests/week — the next request completion catches up within days). Wiring `computeOverCaps` into `syncApplyFix` is a follow-up if the lag becomes visible in practice.

**Cadence.** Sync runs on-demand, when the operator opens the extension's Sync panel on Kindoo and triggers a run. No scheduled cadence. The system-clock interval between LCR-side changes and SBA-side auto-seat existence is therefore bounded only by how often the operator runs Sync, not by a server-side schedule. Accepted at v1 scale (csnorth, ~250 seats, 1–2 requests/week). If the lag becomes operationally visible the next-step fix is either a scheduled Sync trigger or a Cloud Function that polls Kindoo on the same cadence the old importer ran.

**Bishopric lag.** New Bishopric members can't sign into the app until Sync runs against the latest Kindoo data (which itself reflects Church Access Automation's LCR pull). Lag is unbounded by clock; bounded only by Sync-run cadence (see "Cadence" above).

## 9. Email notifications

Six notification types ship via Resend (five in Phase 9, plus the app-access welcome email), fired by Firestore triggers on the relevant entity changes.

| Trigger | Recipients | Subject | Link back |
| --- | --- | --- | --- |
| Request submitted | active Kindoo Managers | `[Stake Building Access] New request from <requester name + calling> — <scope label>` | `<base>/manager/queue` |
| Request completed | original requester | `[Stake Building Access] Your request for <member name> has been completed` | `<base>/my-requests` |
| Request rejected | original requester | `[Stake Building Access] Your request for <member name> was rejected` | `<base>/my-requests` |
| Request cancelled | active Kindoo Managers | `[Stake Building Access] Request cancelled by <requester name + calling> — <scope label>` | `<base>/manager/queue` |
| Over-cap detected | active Kindoo Managers | `[Stake Building Access] One seat pool is over its cap` (one pool) / `[Stake Building Access] <Two … Twelve> seat pools are over their cap` (more; numerals past twelve) | `<base>/manager/seats` |
| App access granted | the granted member | `[Stake Building Access] You can now request building access for <scope list>` (limited tier: `… request temporary building access for …`) | `<base>/` and `<base>/help/requesting-access.html` |

`<base>` is `WEB_BASE_URL` (set per project via `functions/.env.<project>`) unless the stake carries a `web_base_url_override` — see "Per-stake base URL" below. **All six emails ship an HTML part and a plain-text fallback**: `EmailPayload.html` alongside the always-required `text`, which Resend delivers as the multipart alternative. The two parts always say the same thing; the only permitted difference is markup. Every email includes a link back to the relevant page. The R-1 completion email surfaces a `Note from the manager` row carrying `request.completion_note` so the requester knows nothing visibly changed. The over-cap email lists every flagged pool with its current count / cap / overage and a deep-link to the filtered All Seats page.

**Body shape (the five notification emails).** New-request, completed, rejected, cancelled, and over-cap share one layout: a lead sentence, a table of detail rows, and one centred call-to-action button (`Review the queue` / `View your requests` / `Open the queue` / `View seats`). The HTML part is inline styles only — mail clients drop `<style>` blocks — built from module-level primitives in `functions/src/services/EmailService.ts` (`WRAPPER`, `PARA`, `BUTTON`, `LINK`, `TABLE`, `TH`, `TD`, `FLAG`, plus `htmlDocument` / `htmlRow`) that the welcome email shares. The text part renders the same rows through `textRow` as aligned `Label:    value` lines carrying the same labels and the same content, so a text-only client loses styling and nothing else. The four request-lifecycle emails carry `Request` (the type), the scope, and `Member` (name on one line, address beneath it — a `mailto:` link in the HTML part). `Reason` — the request's own `reason` field, the calling the seat was asked for — sits directly after `Member` on **new-request, completed, and cancelled**, in both parts, and drops out of both when the request's `reason` is empty. New-request then adds `Dates`, `Comment`, and `Emergency` on the same present-only condition; completed adds `Note from the manager` beneath the `Reason` row. Rejected always carries `Reason given` — the manager's `rejection_reason` — **and deliberately carries no `Reason` row**: the two are different fields, and a table printing both side by side reads as a contradiction rather than as two facts. All user data is HTML-escaped.

**Ward names, not codes.** All six emails resolve a `scope` to its ward display name through the shared `scopeLabel(scope, wards)` (§3.3) against a single `stakes/{stakeId}/wards` collection read per send — `loadScopeLabeller` in `EmailService.ts` returns a resolver so one read labels any number of scopes, which is what the over-cap email needs. An unresolved code falls back to the raw code. The row is labelled `Ward` for a ward-scoped request and `Scope` for the stake pool, whose value reads `Stake`. This replaces the uppercased raw ward code the five notification emails printed before; the welcome email already resolved names.

**Human request types.** `TYPE_LABEL` renders `request.type` as `Manual access`, `Temporary access`, `Removal`, `Auto-seat edit`, `Manual-seat edit`, `Temporary-seat edit`. The raw enum (`add_temp`, `edit_temp`, …) appears in no email. The completed / rejected / cancelled leads lower-case the same label mid-sentence ("Your temporary-seat edit request for …"), so the lead and the detail row cannot drift.

**Leads name people, not addresses.** Every lead sentence names the subject person by `member_name`, falling back to the address only when the record carries no name; the address itself appears once, in the `Member` row. The over-cap lead spells the pool count ("One seat pool is over its cap", "Two seat pools are over their cap"), matching its subject.

**Emphasis.** One value per email is chipped rather than spelled out: `Emergency` renders as a red `Yes` chip, and each over-cap pool's overage as a red `+N` chip. The word "rejected" in the rejected email's HTML lead carries the same red. The over-cap HTML part is a `Pool` / `Seats` / `Cap` / `Over by` table with right-aligned tabular figures. A rejection with no reason still renders `Reason given: (not provided)` rather than dropping the row — a silent omission reads as a bug.

**Subject formats changed with this work — operator note.** Every one of the five notification subjects has a new format, and three of them (completed, rejected, over-cap) no longer contain the string a mail filter would have matched on. `Over-cap warning` and `Your request was rejected` no longer exist as substrings anywhere. A manager or requester filtering, labelling, or forwarding on those exact strings will silently stop matching. The `[Stake Building Access]` prefix is unchanged on all six and remains the only stable anchor for a filter.

**Requester naming (manager emails).** The two manager-facing emails — new-request and cancelled — name the requester as `{Name} ({Calling})` in both subject and body, not the raw email (the new-request subject reads `New request from {Name} ({Calling}) — {ward name}`; its body opens `{Name} ({Calling}) submitted a new manual-add request for {member name}`; the cancelled subject reads `Request cancelled by {Name} ({Calling}) — {ward name}`, body `{Name} ({Calling}) cancelled their {type} request for {member name}`). `resolveRequesterLabel` in `EmailService.ts` derives the label live per send, through the same shared `deriveRequesterDisplay` / `formatRequesterLabel` pair the manager Queue and extension card use (§5.3 / §15) — name from `member_name`, calling from `importer_callings[scope]` (falling back to `manual_grants[scope][].reason`). It reads the requester's `access/{requester_canonical}` and `kindooManagers/{requester_canonical}` docs concurrently, batched with the wards read (all of it sits on the send path), and passes both, so a manager-submitted request from someone with no access row names them `{Name} (Kindoo Manager)`. It falls back to the raw `requester_email` when neither doc yields a name. The completion / rejection / over-cap emails name the member, not the requester.

**App-access welcome email.** The `notifyOnAccessGranted` trigger watches `stakes/{stakeId}/access/{memberCanonical}` and welcomes a member the first time their access doc carries any scope. It sits on the document — the third trigger on that path, alongside `syncAccessClaims` and `auditAccessWrites` — because the document is the only hook that sees every grant path, including the manager Access page's raw client write to `manual_grants`, which goes through no callable. It fires **iff the before-doc has zero scopes and the after-doc has at least one**, computed by `scopesFromAccessDoc` (`functions/src/lib/seedClaims.ts`) over `importer_callings` and `manual_grants` together:

- First grant → fires.
- A scope added to someone who already holds one → silent (already welcomed).
- A revoke down to zero scopes → silent.
- A re-grant after a full revoke → fires again. Intended.
- A doc delete → never fires.

The scope list names the Stake first, then ward display names resolved from `stakes/{stakeId}/wards` via the shared `scopeLabel` (an unresolved ward code falls back to the raw code), joined as `A` / `A and B` / `A, B, and C`; `Stake` reads as `the Stake` in the sentence. Body links the app root and the requester guide (`/help/requesting-access.html`, the same path constant `apps/web` links, exported from `@kindoo/shared` so the two can't drift). The welcome email is the one notification built from **prose paragraphs rather than detail rows** — it goes to someone who may never have seen the app — so it composes its own body from the shared style primitives instead of going through `htmlDocument`. The HTML part carries **no heading element** — the greeting paragraph is the first thing inside the wrapper `<div>`, and the wrapper's padding is the whole top gap. The sign-in paragraph branches on the recipient's address through the shared `isGmailAddress`: a Gmail address is told to click **Continue with Google**; every other address is told to enter it and click **Send me a sign-in link**. Google Workspace addresses deliberately get the magic-link copy — they can sign in with Google too, but the address alone doesn't say so. Recipient is the doc's `member_email`, falling back to the doc ID (itself a canonical email); the greeting uses `member_name` when present, otherwise `Hello,`. `kindooManagers` grants are not app-access grants and never send this email. A send failure lands as an `email_send_failed` audit row with `entity_id: 'email:accessGranted'` and a suffix keyed on the member's canonical email.

**Welcome-email access tier.** The copy branches on the limited tier (§4) as well, independently of the Gmail branch above. Since D26 that includes a newly-granted **Elders Quorum President**, whose only grant is limited-tier: they receive the limited wording. The mechanism is unchanged — the tier now comes off the stored `importer_limited_callings` field rather than a name match, and nothing else about the branch moved. The trigger resolves the tier itself rather than reading a claim: it folds `scopesFromAccessDoc(after).limited` together with a direct read of `stakes/{stakeId}/kindooManagers/{memberCanonical}` (the doc, plus `active === true`) through the shared `isLimitedTier` (`functions/src/lib/seedClaims.ts`), the same helper `computeStakeClaims` calls to mint the claim. One definition, so what the email tells a member matches what their token will carry. The manager read is batched into the stake-doc read the trigger already makes. The folding rules are §4's: one full grant anywhere in the access doc makes the whole stake full, an active Kindoo Manager is never limited, and an inactive `kindooManagers` row does not rescue a limited grant.

What the tier buys is **one word, in two places**: the subject reads `You can now request temporary building access for <scope list>` and the opening sentence reads "…sign in and request temporary building access for …". Both parts carry it. Everything else is character-for-character identical between tiers — greeting, the rest of the opening paragraph, button, sign-in paragraph, guide link, styling. The email states no constraint the tier imposes: not the 90-day cap, not the temp-only edit/remove rule, not the ward-scope building lock. Both tiers link the same guide URL, with no anchor variant, and a test pins the two to one string so they cannot quietly diverge.

**Welcome-email send burst (operator note).** The welcome email is **not** gated on `setup_complete`. A new stake's first extension Sync creates access docs in bulk, so it sends one email per newly-granted member — roughly one per member at the ~250-seat target scale. That is intended: the burst doubles as the launch announcement. It can, however, exceed a low Resend daily quota, in which case the overflow lands as `email_send_failed` audit rows and those members are never welcomed. An operator who wants a quiet onboarding sets `notifications_enabled: false` on the stake for the duration of the initial Sync and flips it back afterwards.

**Per-stake base URL.** `stake.web_base_url_override` (optional string) replaces `WEB_BASE_URL` as the base for **all** of that stake's email links — all six templates, not just the welcome email. It is a hidden operator-only escape hatch: there is no UI anywhere, and the operator sets it by hand in the Firestore console. It exists because the app is dual-hosted (§12), so a stake whose members live on the legacy host can get email links on that host. The value must start with `http://` or `https://`; absent, empty after trim, or missing the scheme means it is ignored (a rejected value emits a `logger.warn`) and the `WEB_BASE_URL` param applies. It affects email links only — never routing, hosting, or auth domains.

**From address.** Fixed envelope `noreply@mail.stakebuildingaccess.org` (verified Resend subdomain per F17 / T-04). Display name interpolates the stake name: `<stake.stake_name> — Stake Building Access <noreply@mail.stakebuildingaccess.org>`. Optional `Reply-To` from `stake.notifications_reply_to` when set; otherwise the header is omitted (replies bounce off `noreply@`).

**Best-effort discipline.** Every notification trigger catches Resend errors, writes one `email_send_failed` audit row via Admin SDK with a deterministic `auditId(writeTime, suffix)`, logs, and returns. The underlying entity-write trigger never re-throws on a mail failure — the Sheet write is atomic, the email is best-effort. See [`architecture.md`](architecture.md) §9.5 (preserved verbatim from the legacy doc) for the full rationale on why the email lives outside the lock.

**Email kill-switch.** `stake.notifications_enabled` (boolean; default `true`) gates every Resend send. Flipping it to `false` short-circuits before the API call; one log line emitted. Editable from the manager Configuration page.

**Push notifications** (Phase 10.5) ship the new-request notification only. Independent kill-switch per user per device per category at `userIndex/{canonical}.notificationPrefs.push`. The remaining four notification categories (completion / rejection / cancel / over-cap) on push are Phase 10.6, deferred. The app-access welcome email has no push counterpart by construction — its recipient has never opened the app, so no device is subscribed.

## 10. Bootstrap flow

`stake.bootstrap_admin_email` (lowercased on save by the `createStake` callable; dots and `+suffix` preserved — see `firebase-schema.md` §4.1) is seeded by the operator at stake creation, alongside `setup_complete=false`. Until `setup_complete` flips to `true`, every page load first routes through the **setup-complete gate** in `apps/web` (runs **before** role resolution):

**Reaching the wizard.** Before the gate below can run, the SPA first has to resolve which stake to even look at — the bootstrap admin has no role claim yet, so nothing about their account says "stake X" except the stake doc itself. The active-stake selector (§2.1) closes that gap via `StakeClaims.bootstrap`, a custom-claim marker synced onto the admin's auth token by the `syncBootstrapClaims` trigger on `stakes/{stakeId}` writes (or seeded at the admin's first sign-in by `seedClaimsFromRoleData`, if the stake was created before they had a Firebase Auth account). The marker costs zero extra network calls — it rides the ID token the app already fetches on every page load — and it grants no access on its own; it only makes the stake *discoverable* so the active-stake resolver's tier 4 can land the admin directly on it instead of on a dead end. The StakeSwitcher additionally lists any such stake with a **"Setup needed"** badge, so an admin who is also a manager elsewhere can navigate into it manually. See §2.1 "Pre-claim bootstrap admin" for the full resolution mechanics, and `docs/BUGS.md` B-19 / `docs/architecture.md` D28 for why this replaced an earlier callable-based design.

- If the signed-in email matches `bootstrap_admin_email` (plain string compare against `auth.token.email`, which Firebase Auth always emits lowercased) and `setup_complete === false` → render the bootstrap wizard, ignoring deep-link route params.
- If `setup_complete === false` and the email does NOT match → render a "Setup in progress" page (distinct from "Not authorized" — the user isn't unauthorised, the app isn't ready).
- If `setup_complete === true` → normal role resolution.

The wizard is multi-step and writes directly into the live collections (`stakes/{stakeId}` parent doc, `buildings/`, `wards/`, `kindooManagers/`). Each step persists immediately, so closing and reopening mid-setup resumes where the data says it should. Rules carve out a bootstrap-admin escape hatch (`firebase-schema.md` §6.1) — the predicate `isBootstrapAdmin(stakeId)` is OR'd into the read+write rules of the four wizard-managed collections, gated on `stake.setup_complete === false`. Once the wizard's final write flips `setup_complete=true`, the predicate goes silent and the manager claim (already minted by `syncManagersClaims` after the auto-add) takes over.

**Leaving the wizard.** `BootstrapWizardPage` renders outside `<Shell>` — no nav, no StakeSwitcher, no sign-out control — which was a dead end once the StakeSwitcher started listing bootstrap-only stakes (§2.1, the "Setup needed" badge): a Kindoo Manager of stake A who clicked into stake B's badge out of curiosity had no way back to A short of finishing B's setup or clearing site data, and a pure bootstrap admin with no other accessible stake had no sign-out control anywhere on the page at all. A `WizardEscapeBar` in the wizard header — present in both the loading and loaded states, so it's there even before the stake doc resolves — closes both gaps with two controls, evaluated off the live principal and independent of wizard step or progress:

- **"Back to my stake" / "Back to my other stakes"** (only when `accessibleStakes(principal)` **minus the active (in-setup) stake** is non-empty) — switches the active-stake selection to a stake from that filtered set, through the same persist-to-both-storage-tiers path the StakeSwitcher's click handler uses (`useActiveStakeSwitcher`), then navigates to `/`. Routing the switch through that persistence, rather than a bare navigate, is what stops the resolver bouncing the user straight back into this same wizard on the next render. Singular vs. plural label tracks the filtered count, not the raw `accessibleStakes` count.

  The active stake has to be excluded explicitly, not just happen to be absent: `useEnsureBootstrapAdmin` auto-adds the bootstrap admin to the in-setup stake's `kindooManagers` on first wizard load, and `syncManagersClaims` mints a manager claim from that write in-session — so by the time this control renders, `accessibleStakes(principal)` already includes the very stake the button exists to leave. Unfiltered, a pure bootstrap admin got a "Back to my stake" button that returned them to the wizard they were trying to escape, and a dual-role admin whose bootstrap stake happened to sort first got routed back to it instead of their real stake.
- **"Sign out"** (always present) — reuses `features/auth/signOut.ts`. The only way out for a bootstrap admin with no other accessible stake who signed in with the wrong account.

Neither control touches the wizard's step state — a bootstrap admin who leaves and later returns resumes where the persisted data left them, per the step-persistence described above.

**Step navigation.** A step bar of four clickable tabs sits above the panel, plus **Back** / **Next** buttons below it. The tabs are unrestricted in both directions — they are the escape hatch out of any step, and stay clickable no matter what the data looks like. **Back** is likewise never gated. **Next** is gated on the two steps whose data the rest of the wizard depends on: it is disabled on Step 2 while the stake has zero buildings ("Add at least one building to continue.") and on Step 3 while it has zero wards. Step 3's hint defers to the upstream gap when there are none: with at least one building it reads "Add at least one ward to continue.", and with none — reachable, since the tabs are free — "Add a building (Step 2) before adding wards.", because Step 3's own Add-ward button is disabled in that state and naming the ward would instruct an impossible action. Step 1's Next is ungated — Step 1's own **Save** already validates its fields, and Complete Setup blocks on them separately. The gate is advisory rather than load-bearing: it stops the admin walking Next into Step 3's building selector with nothing to select, or into Step 4 with a stake that cannot finish setup, while the tabs keep every step reachable. Both hints render below the button row, and they are the only helper text *in that slot* on Steps 1–3: the Complete Setup blocker checklist is scoped to Step 4 (see below), so the slot never restates the same gap twice. Step-local helper text inside a step's own form panel is separate and unaffected — Step 3's ward form carries its own "Add a building first (Step 2) before adding wards." next to its disabled Add-ward button.

Steps:

1. Stake name, stake seat cap, and the **Elders Quorum Presidents Get App Access** switch (writes to `stakes/{stakeId}` parent doc). The switch is the one app-access control the wizard exposes, so a stake can opt in before its first Sync run. It raises **no backfill dialog** (unlike the Configuration → Config tab, §8) — a stake still in setup has no seats to reconcile. `createStake` seeds `eq_president_app_access: false`, so the switch renders off on a fresh stake.
2. At least one Building (writes to `buildings/`). Buildings come **before** Wards because every ward references an existing building — the same dependency the manager Configuration page enforces (§5.3).
3. At least one Ward with `ward_name`, a chosen building, and `seat_cap` (writes to `wards/`). There is no "Ward code" field — `ward_code` is derived from `ward_name` via `buildingSlug()` and pinned as the doc ID (§3.2); the wizard rejects a name that collides (case-insensitive, trimmed) with a ward already in the pending list, and the commit transaction backstops a same-slug collision. The Building selector's value is the building's `building_id` slug; the write stores both `building_id` (preferred FK) and `building_name` (legacy snapshot) — §3.2. A ward stores no `kindoo_site_id`; its Kindoo site is inherited from the chosen building (§3.2).
4. Additional Kindoo Managers (optional; writes to `kindooManagers/`). The bootstrap admin is **auto-added** as an active manager on first wizard load (one-shot idempotent write keyed on canonical email) — they cannot delete themselves and won't be locked out after setup.

**Complete Setup** renders on every step but is enabled only when steps 1-3 are complete. Its **blocker checklist** — the helper text naming every outstanding prerequisite ("Fill in stake name and seat cap (Step 1).", "Add at least one building (Step 2).", "Add at least one ward (Step 3).") — renders on **Step 4 only**. On Steps 1–3 the button can therefore sit disabled with nothing explaining it; that is intended. The operator's next action on those steps is **Next**, whose own step-scoped hint says what is missing there, and Step 4 — the step Complete Setup is the point of — carries the full checklist. The list itself is computed unconditionally from all three steps; only its rendering is step-scoped.

Complete Setup flips `stake.setup_complete=true` via a single `updateDoc` (the same write carries the `lastActor` integrity field), then redirects the admin to the manager default page. That Firestore flip is the entire action — no callable is invoked. The write is rules-gated and the `auditTrigger` fans the `setup_complete` audit row; the routing gate redirects once the flip lands. There is nothing to install at setup time: the only scheduled job (`reconcileAuditGaps`) is single-loop and platform-managed (installed at first deploy), so it needs no per-stake provisioning.

**One-shot wizard.** The bootstrap-admin gate's `setup_complete === false` clause is what makes this strictly time-bounded. Post-setup edits go through the normal manager Configuration page.

**Operator pre-step.** The stake doc must exist with `setup_complete=false` and `bootstrap_admin_email=<lowercased email>` BEFORE the bootstrap admin signs in. The `createStake` callable handles the lowercase transform; any out-of-band seed path (direct-console write, future CLI) must do the same — see `firebase-schema.md` §4.1 for the rationale. The gate's `get()` short-circuits if the stake doc is missing — operator seed is mandatory. See `infra/runbooks/provision-firebase-projects.md`.

## 11. Concurrency

All multi-doc writes wrap in `db.runTransaction(...)` (Cloud Functions side, Admin SDK) or `runTransaction` from the Firestore JS SDK (client side). Firestore's optimistic-concurrency model handles contention — a transaction that observes a write race retries up to its internal limit before throwing. The client surfaces the throw as a clean error toast.

Reads do not need any lock. Live `onSnapshot` subscriptions on shared-attention pages (Queue, Roster, MyRequests, Dashboard, Audit Log) refresh automatically as state changes; request-response queries (filtered All Seats, etc.) re-run on filter changes.

Audit log writes are server-only and fan in via the `auditTrigger` Cloud Function (F8). The trigger uses a deterministic `auditId(writeTime, suffix)` so retries collapse onto one row. Eventually consistent (~<1s); the nightly `reconcileAuditGaps` job (deferred wiring; mocked in v1) is the safety net.

## 15. Kindoo Sites (multi-site Kindoo management)

The operator manages a single SBA stake (`csnorth`) but is a Kindoo Manager on multiple Kindoo sites — two wards in csnorth live in buildings whose access doors are physically governed by a different stake's Kindoo environment than the SBA stake's own home site. "Kindoo Sites" tracks those N Kindoo environments the operator's managers can write to (home + 0..N foreign), so the SPA, the companion Chrome extension, and the weekly sync can route Kindoo-side operations to the correct environment without misprovisioning.

This is **not** multi-stake on the SBA side. Kindoo Sites is local per stake — the existing `kindooManagers` allow-list governs all Kindoo writes regardless of which Kindoo site they target, and Kindoo Sites does NOT introduce a new role or principal shape. **Phase 12 (multi-stake) interaction.** The data layer is unaffected: each stake's `kindooSites/{kindooSiteId}` sub-collection is local to that stake, and a foreign Kindoo site configured under stake A is not visible from stake B. The extension's multi-stake behaviour is described in the next paragraph; the rest of the Kindoo-Sites spec assumes a single stake context resolved by it.

**Extension EID-to-stake resolution (Phase 12.5).** When the slide-over panel mounts on a Kindoo session, the extension's service worker reads the operator's `managerStakes` off their auth-token claims and queries each managed stake's parent doc + `kindooSites/*` to find every stake that has the active session's EID configured (`stake.kindoo_config.site_id === eid` for home, or some `kindooSites/<id>.kindoo_eid === eid` for foreign). The candidate set drives the panel's behaviour:

- **Zero candidates.** Recovery copy: "This Kindoo site (EID N) is not configured under any SBA stake you manage." No picker; no panel content beyond the error + retry.
- **Single candidate.** Auto-resolved — the panel proceeds straight into the tabbed shell against that stake. No storage write (the resolution is structural, not a remembered choice).
- **Multiple candidates (rare; reachable when a foreign-site grant from stake A and a home grant from stake B both target the same Kindoo environment).** The slide-over surfaces a full-takeover stake picker listing each candidate by `stake_name` with a home / foreign hint. The operator's click persists the choice to `chrome.storage.local` under a single canonical key `sba.eidStakeChoice` shaped as `Record<eidString, stakeId>`. Subsequent panel mounts against the same EID short-circuit straight to the resolved stake.

**Partial-failure banner.** When the EID resolver succeeds on a subset of managed stakes but at least one per-stake read caught (rules denial, Firestore hiccup), the panel renders a non-modal warning banner ("Couldn't read N of your stakes — partial results shown") above the picker or auto-picked view with a Retry button. The auto-pick behaviour for a single surviving candidate is preserved (the picker is NOT forced open on partial failure); the banner is the operator's signal that they may be working in the wrong queue.

**Stale-choice invalidation.** Every panel mount re-runs the EID resolver and validates any stored choice against the live candidate set. If the stored stake is no longer a candidate (manager role revoked between sessions, or the EID was un-configured from that stake's `kindooSites/`), the stored entry is dropped and the picker re-asserts. The whole `sba.eidStakeChoice` map is wiped on sign-out alongside the principal snapshot and the cached Google access token.

**Storage scope.** `chrome.storage.local` only (not `sync`), so the choice does not propagate across the operator's Chrome profiles. The single-key-per-map shape keeps sign-out cleanup atomic. Shared-laptop scenarios (two operators on the same Chrome profile) inherit each other's choices between sign-ins; sign-out's wipe covers the practical case.

All extension callables (`getMyPendingRequests`, `markRequestComplete`, `syncApplyFix`) and Firestore reads / writes propagate the resolved `stakeId`. There is no single-stake constant in the extension. See `firebase-migration.md` Phase 12 sub-deliverable 12.5 + `docs/changelog/phase-12.5-extension-stake-mapping.md`.

### Data model

- **Home site is implicit.** It lives on the parent stake doc (`stake.kindoo_config.site_id` / `kindoo_config.site_name`, plus the optional `kindoo_expected_site_name` override). There is no `KindooSite` document representing the home site.
- **Foreign sites live as documents** under `stakes/{stakeId}/kindooSites/{kindooSiteId}`. The doc ID is a manager-chosen slug. See [`firebase-schema.md`](firebase-schema.md) §4.11. The Kindoo environment ID (`kindoo_eid`) is NOT a manager-supplied field — the extension discovers it via the active-site DOM-scrape resolver (`readActiveEidFromDom` in the extension's `content/kindoo/auth.ts`) and writes it on first use (Phase 3). The Configuration UI captures only the display name and the Kindoo site-name string.
- **Each `Ward` and `Building`** carries an optional `kindoo_site_id: string | null`. `null` (or field absent) means the home site; a string value points at a doc ID under `stakes/{stakeId}/kindooSites/`. Wards and buildings carry the field independently — a foreign-site building hosts foreign-site wards, and the building's value is the load-bearing one for door access, while the ward's value flags Kindoo-side roster placement.

### Home-stake utilization

Foreign-site wards (those whose building resolves to a non-home `kindoo_site_id`) do not contribute to home-stake utilization on either side of the calculation. Their `seat_cap` is excluded from the home stake portion-cap, and their (foreign-primary) seats are excluded from home-stake used counts. The **one exception** is the over-cap count: a foreign-ward-primary seat that carries a manager-granted parallel-site stake grant (a `scope: 'stake'` entry in `duplicate_grants[]`, §6.1) adds one unit to the home stake count, because that grant consumes a home Kindoo license — see §244. (The UI utilization bars read primary scope only, so they don't reflect this; the over-cap warning does.) Per-ward over-cap and per-ward utilization are unaffected — each ward's bar reflects what its own Kindoo site allotted it. See §244 for the cap-interaction rule and §135 / §137 for the manager surfaces that render the home-stake bars.

### Phase plan

Kindoo Sites lands in five phases. **Phase 1 ships the data model + the Configuration UI only — no behavioural changes elsewhere.** Defaults treat everything as home site (`kindoo_site_id: null` on every existing ward and building). No backfill is required.

- **Phase 1 (data model + Configuration UI).** Shipped. Adds the `kindooSites` collection, the `kindoo_site_id` field on `wards` / `buildings`, security rules, and a Configure-tab UI for managers to add / edit foreign sites and assign them to wards / buildings.
- **Phase 2 (form filtering + roster labels).** Shipped. Both the New Request form and the Edit Seat dialog filter their building checklists to the current scope's Kindoo site — stake-scope shows home-site buildings only (per operator decision 2 below), ward-scope shows the buildings whose `kindoo_site_id` matches the ward's site (derived from the ward's building — §3.2). Pre-checked buildings outside the visible set (seat building_names left over from a prior site assignment) are dropped silently from the form's defaults so the user can only check / uncheck what they can see; the form's submit is gated on at least one visible building remaining checked. Buildings without the field are treated as home. When the site filter narrows the catalogue to zero (e.g. a foreign-site ward whose foreign building has not yet been configured) both surfaces render an explicit empty-state directing the manager to Configuration rather than presenting an empty checklist. Roster pages (bishopric roster, stake ward rosters, manager All Seats) render a small foreign-site badge alongside each ward seat whose ward sits on a non-home Kindoo site; home and stake-scope seats carry no badge.
- **Phase 3 (extension orchestrator enforcement).** Shipped. The companion Chrome extension's Provision & Complete flow validates that the active Kindoo session's EID matches the request's target site (`stake.kindoo_config.site_id` for stake-scope and home-ward requests; `kindooSites/<id>.kindoo_eid` for foreign-ward requests) before writing to Kindoo. On mismatch the extension refuses with the explicit error `"This request needs to be provisioned on '<expected site name>'. Switch Kindoo sites and try again."` — no silent fallback. Foreign-site docs whose `kindoo_eid` hasn't been recorded yet get auto-populated on the first provision against a session whose site name matches the doc's `kindoo_expected_site_name`; the EID write completes before any Kindoo write fires. Auto-populate additionally refuses when the active session's EID equals the home `kindoo_config.site_id` — even on a name match — so a foreign doc whose `kindoo_expected_site_name` collides with the home name (typo, blank-then-copy, Kindoo-side rename) can never trap HOME_EID on the foreign doc and silently bypass the guard. The operator must be inside a specific Kindoo site (not the "My Sites" listing page) for the extension to identify the active site.
- **Phase 4 (sync filtering).** Shipped. The Sync feature scopes its diff to the Kindoo site the operator's active session is pointed at, so a home-site session does not flag foreign-site grants as drift (and vice versa). The active site's EID is recovered by DOM-scrape: `readActiveEidFromDom` (in the extension's `content/kindoo/auth.ts`) matches the visible Kindoo header text (rendered as `[dir="auto"]`) against the `EnvironmentName` values in `localStorage.state.sites.entities`, and returns the matched EID iff exactly one entity name is visible. `localStorage` itself does NOT carry the active-site signal — `state.sites.ids[0]` is the access-list head (not the active site), `user.object.EnvironmentID` is always `null`, and there is no URL or DOM-data-attribute discriminator. Kindoo tracks the active site only in React in-memory state; the rendered header is the only observable surface. The resolved EID is then classified against `stake.kindoo_config.site_id` (home) and each `KindooSite.kindoo_eid` (foreign). On `home`, only seats whose ward resolves to the home site (its building's `kindoo_site_id` is null / absent — §3.2; plus stake-scope seats) and Kindoo users whose Description resolves to those wards or the stake are compared; on `foreign(siteId)`, only seats / users whose ward resolves to `siteId` (via its building) are compared (stake-scope seats are excluded — home-only per the Phase 1 policy). The rule-fetch + door-grant enrichment also restrict to buildings owned by the active site, so foreign rule_ids are never issued against the home EID (or vice-versa) — that mis-targeting was the original `HTTP 303 ObjectNotFound` regression for multi-site managers. When the active site can't be identified (the listing page is open, the operator hasn't picked a site yet, or a Kindoo redesign broke the scrape selector), the panel surfaces the `no-eid` recovery state directing the operator to open a specific Kindoo site and retry. When the live EID matches neither home nor any configured `KindooSite`, the panel suppresses the report and surfaces an empty-state recovery message directing the operator to Configuration → Kindoo Sites (or to switch to a known site). The operator must be inside a specific Kindoo site (not the "My Sites" listing page) for the extension to identify the active site.
- **Phase 5 (re-runnable configure wizard, per active Kindoo site).** Shipped. The extension's configure wizard detects the active Kindoo session's site (via the same resolution `siteCheck.ts` uses for the Phase 3 orchestrator entry guard) and scopes rule-mapping to that site's buildings only. Home active → home buildings + `stake.kindoo_config` write; foreign active → only that foreign site's buildings + `kindooSites/<id>.kindoo_eid` auto-populate (on first encounter) + per-building `kindoo_rule` writes. The wizard never overwrites `stake.kindoo_config` on a foreign run. The wizard's home-by-name resolution refuses when the active session's EID matches a known foreign `kindoo_eid`, or when the active name is ambiguous between home and a foreign site — preventing the symmetric FOREIGN_EID → home-doc leak. Active Kindoo session whose site is not configured in SBA → wizard refuses with `"This Kindoo site (<active site name>) isn't configured in SBA. Add it in Configuration → Kindoo Sites first."` — operator switches sites in Kindoo's own UI and reopens the panel; there is no "switch sites" button in SBA. First-run gate also relaxes: only home buildings must carry `kindoo_rule` for the panel to leave the wizard takeover and show the tabs; foreign buildings get mapped on a subsequent wizard run while the operator's Kindoo session is on that foreign site. The operator must be inside a specific Kindoo site (not the "My Sites" listing page) for the extension to identify the active site.

### Extension queue panel — request-queue parity

The slide-over's Queue tab (`extension/src/panel/QueuePanel.tsx`, `RequestCard.tsx`) mirrors the web manager Requests Queue's pending view (§211):

- **Priority sections.** Pending requests render in three ordered sections — **Emergency → Outstanding → Future** — computed from the same `comparison_date` rule as the web (`start_date` at local midnight for `add_temp` with a valid ISO start date; `requested_at` otherwise) and a today+7 local-midnight cutoff. (The "Emergency" section heads the `urgent`-flagged requests — field name `urgent`, displayed label "Emergency".) Each section heading shows the open count in parentheses (e.g. `Emergency Requests (2)`); a section with zero requests is hidden; cards within a section sort by comparison-date ascending (oldest first). The section logic lives in `@kindoo/shared`'s `partitionPendingRequests` (whose `requestedAtMs` reader handles both the callable's serialised `{ seconds }` / `{ _seconds }` wire shape and a live Firestore `Timestamp`), consumed by both the web queue and the extension queue.
- **Per-card Reject.** Every card carries a **Reject** button alongside its provision button. It opens a small modal (`RejectDialog.tsx`) with a required "Rejection reason" input; Confirm is disabled until the reason is non-empty. Reject is a service-worker-side Firestore `getDoc` + `updateDoc` (`rejectRequest` in `background/data.ts`, message `data.rejectRequest`) that flips `status` pending → rejected and writes exactly `['status', 'completer_email', 'completer_canonical', 'completed_at', 'rejection_reason', 'lastActor']` — the reject rule's `hasOnly` allowlist — stamping the actor from the SW's Firebase Auth user (`completer_email` / `lastActor.email` the raw token email, `completer_canonical` / `lastActor.canonical` the token's `canonical` claim, mirroring the web's `readActor()`). No `runTransaction`: transactions ride the WebChannel transport that needs `XMLHttpRequest`, undefined in an MV3 service worker, so they throw at runtime — discrete `getDoc` / `updateDoc` use the fetch-based RestConnection and work in the SW. The pending precondition is enforced by the reject rule (`resource.data.status == 'pending'`) at write time, so dropping the transaction loses no safety — a concurrent terminal transition makes the rule reject the stale write; the SW pre-read only yields a friendlier "no longer pending" message. On failure the modal stays open with the inline error (`role="alert"`) and does not refetch the queue. No Cloud Function; the manager custom claim on the SW token satisfies the rule's `isManager`.
- **Add for an existing user → Reject-only (with one carve-out).** When an `add_manual` / `add_temp` request's member already has an SBA seat (any scope — `getSeatByEmail` returns non-null), the card hides the provision button and shows a blocking notice ("Member already has a seat — reject this request."), leaving only Reject. The panel fetches the seat for each add request after the queue loads; a lookup failure resolves to "not blocked" so the provision button stays visible rather than blocking the queue. Edit / remove types are unaffected (an existing seat is expected for those). **Carve-out — stake-scope `add_manual` for a member with no stake grant.** This single add-onto-existing-seat case stays applyable: `markRequestComplete` → `planAddMerge` appends a cross-scope `duplicate_grant` and succeeds (the "Give Access To Stake Buildings" flow — §6.1 / "Manager-granted stake access — parallel-site grant on completion" above). **The rule has one definition:** `addBlockedByExistingSeat` in `@kindoo/shared` (`packages/shared/src/existingSeatGate.ts`). It takes the request plus two facts about the member's existing seat — that it exists, and that it already holds a stake-scope grant (primary `scope === 'stake'`, or any `duplicate_grants[]` entry at `stake`) — and returns `isAdd && hasSeat && !applyableStakeAdd`, where `applyableStakeAdd = type === 'add_manual' && scope === 'stake' && !hasStakeGrant`. The web queue card (§5.3) calls it directly; the panel still expresses the same predicate inline over the `memberHasSeat` / `memberHasStakeGrant` props it already threads onto the card, and adopts the shared helper under T-82. It was lifted into `shared` because the two copies had drifted and the drift did not fail safe: the web's gate was `isAdd && !!seat`, which withheld **Apply via extension** and printed "this request can't be completed — reject it" on precisely the carve-out the desktop provisions cleanly. The gate is broader than the **"Give Access To Stake Buildings"** button that produces most of its traffic: it permits the merge for **any** member with a seat but no stake grant — not only a foreign-site-only member, but also a home-ward member (whose existing home Kindoo user simply gains the stake buildings). The web "Give Access To Stake Buildings" button (§6.1) is the foreign-site-only entry point, but other request-creation paths can produce the same `add_manual` / stake shape and `planAddMerge` handles them all. The `!memberHasStakeGrant` backstop keeps blocking if the member already holds a stake grant — the add would be a true stake duplicate and couldn't apply cleanly. Every other add-on-existing case is Reject-only exactly as before.
- **Requester line — name + calling (parity).** The card's `Requester:` line reads `{Name} ({Calling})` exactly as the web queue (§5.3), through the same shared `deriveRequesterDisplay` / `formatRequesterLabel` helpers and the same scope-keyed derivation (`importer_callings[scope]`, falling back to `manual_grants[scope][].reason`, falling back to the literal "Kindoo Manager" for a manager-submitted request). The extension holds no live subscriptions, so `RequestCard` fetches `stakes/{stakeId}/access/{requester_canonical}` and `stakes/{stakeId}/kindooManagers/{requester_canonical}` once on mount via one-shot service-worker reads (`getAccessByEmail` / `getKindooManagerByEmail` → `background/data.ts`, mirroring the existing `getSeatByEmail` path); the SW token's manager claim satisfies both read rules, so no rule change was needed. The two reads resolve **together** and commit in a single `setState` so the label doesn't paint once with the access-only value and again once the manager doc lands; each carries its own `catch` so a miss on one never discards the other's contribution. While the reads are in flight, resolve absent, or fail, the label degrades to the raw email — the same graceful fallback as the web.
- **Edit for a nonexistent seat → Reject-only.** The edit-side analog. When an `edit_auto` / `edit_manual` / `edit_temp` request's member has **no** SBA seat (`getSeatByEmail` positively returns `null`), the card hides the provision button and shows a blocking error notice ("This request edits a seat that no longer exists — reject it."), leaving only Reject — completing the edit would throw `failed-precondition` from `markRequestComplete` ("no seat found for member … — cannot {type}"), raised against the missing seat doc before any slot planning runs. (The distinct seat-exists-but-no-matching-`(scope,type)`-slot case — where `planEditSeat` throws "no editable slot" — is an out-of-scope follow-up; this gate triggers only on a wholly absent seat.) The panel's post-load seat-existence fetch covers every non-`remove` request and distinguishes three states per card: seat present, seat positively absent (lookup resolved to `null`), and unknown (lookup failed / not yet resolved). The edit gate blocks **only on positively-absent**; an unknown / failed lookup falls back to showing the provision button (the opposite fail-safe direction from the add gate — we don't false-block an editable request on a transient miss, and the server-side `markRequestComplete` precondition is the backstop). `remove` and edits whose seat is present keep their provision button; Reject is always available.

### Multi-site grants — data model

A Kindoo user whose callings straddle home + foreign sites (e.g. `'Maple Ward (Bishop) | Pine Ward (Stake Clerk)'` with Maple on the home site and Pine foreign; or the stake-clerk-plus-foreign-ward shape `'<StakeName> (Stake Clerk) | Pine Ward (Elders Quorum President)'`) surfaces on every site that owns one of those callings. The seat doc carries one primary grant at top level and zero-or-more `duplicate_grants[]` entries that capture every additional grant — both within-site priority losers and parallel grants on other Kindoo sites.

**`duplicate_grants[]` semantics.** The array records "additional grants" of two kinds, distinguished by a per-entry `kindoo_site_id`:

- **Within-site priority loser.** Same `kindoo_site_id` as the seat's primary grant. Informational; the primary's write already covers the access.
- **Parallel-site grant.** Different `kindoo_site_id` from the primary. A legitimate independent grant on another Kindoo site that needs its own write to that site's Kindoo environment.

The distinguishing test is field equality on `kindoo_site_id`; no separate flag.

**`Seat.kindoo_site_id` field.** Mirrors the building convention: `null` (or field absent) means the home site; a string value points at a doc ID under `stakes/{stakeId}/kindooSites/`. The top-level value reflects the primary grant only; each `duplicate_grants[]` entry carries its own `kindoo_site_id`. Stake-scope primary grants resolve to home (per Phase 1 policy, decision 2). Ward-scope primary grants take the site derived from the ward's building (`resolveWardSite(ward, buildings)` / the `wardSiteMap` helper in `functions/src/lib/wardSites.ts` — a ward stores no `kindoo_site_id`; §3.2). **Every server seat-writer that sets or moves a seat's scope stamps `kindoo_site_id` per this convention** — the auto-seat creators (`syncApplyFix`'s `kindoo-only` and `scope-mismatch` paths) and `markRequestComplete`'s new-seat path all resolve the ward's building-derived site and stamp it for foreign sites, leaving the field absent for home / stake / unknown-ward (where the read-time ward-fallback classifies). A **write-time invariant** (`assertSeatSiteStamped` in `functions/src/lib/wardSites.ts`) backstops the convention: a seat whose primary `scope` is a known ward resolving to a foreign site is never persisted with `kindoo_site_id` absent/null — the writer throws rather than silently mis-classifying it as home. The guard does not fire for stake-scope, home-ward, or unknown/missing-ward seats. Two `syncApplyFix` paths clear `kindoo_site_id` when they move a seat to `scope='stake'` — stake-scope ⇒ home, so a foreign-site value left over from a prior site assignment doesn't linger on the now-stake-scope seat: the `kindoo-unparseable` fix (§8) and `applyScopeMismatch` when `newScope==='stake'` (the fix for B-15). Both resolve a foreign-site seat to stake scope and delete the stale `kindoo_site_id` in the same write.

**`Seat.duplicate_scopes: string[]` field.** Denormalised mirror of `duplicate_grants[].scope` — Firestore CEL has no `[*].field` projection over an array of objects, so rules that need to ask "does this seat carry a duplicate grant under this scope" use `scope in duplicate_scopes` against the primitive-string array. Server-maintained on every seat writer (`syncApplyFix`, `markRequestComplete`, `removeSeatOnRequestComplete`, migration); rules reject client writes. T-42 / T-43.

**Sync auto-seat fan-out.** When Sync creates an auto-seat for a person whose callings span multiple Kindoo sites:

- Primary selected by `stake > ward (alphabetical)` per `firebase-schema.md` §4.6 Invariants. Multi-calling within a scope continues to collapse into `callings[]` (with `sort_order` still stamped as the MIN canonical `seatCallingOrder` across the array — vestigial; the web no longer reads it). The `syncApplyFix` writer stamps `scope`, `building_names`, and the derived `kindoo_site_id` at top level.
- For every **(scope, kindoo_site_id)** combo that isn't the primary, `syncApplyFix` emits one entry in `duplicate_grants[]` carrying that site's `kindoo_site_id`, the scope, the calling list for that scope, and the buildings derived from that scope. Two foreign wards on the same foreign site produce two `duplicate_grants[]` entries, both with that site's `kindoo_site_id` but distinct `scope` values; the sync detector unions their `building_names` per-site when computing expected buildings.
- Sync-written parallel-site duplicates always set `building_names` (derived from the duplicate's `scope` → ward → assigned building's display name, resolved id-first via `resolveWardBuilding`, or the stake-scope home-buildings list for stake duplicates). Within-site Sync duplicates leave the field unset and inherit from the primary's ward.
- Within-site priority losers land in `duplicate_grants[]` with `kindoo_site_id === primary.kindoo_site_id`.

**Sync detector.** `pickPrimarySegment`'s collapse-to-one-segment is gone for the per-site path. For each Kindoo site under inspection the detector takes the union of the seat's primary (when its `kindoo_site_id` matches) and each `duplicate_grants[]` entry whose `kindoo_site_id` matches; expected buildings are the union of those grants' `building_names`. The home/foreign mismatch detector still routes off `kindoo_site_id`.

**Provision orchestrator — per-site writes.** When a request or auto-seat needs provisioning, the orchestrator emits one Kindoo write per distinct `kindoo_site_id` across (primary + parallel duplicates), each using the matching Kindoo session. Within-site priority losers (same `kindoo_site_id` as primary) do not get a separate write — the primary's write already covers them. The EID check keys off each grant's `kindoo_site_id`.

**Within-site union.** The per-site write includes the union of `building_names` across the primary (when it sits on that site) and every same-site `duplicate_grants[]` entry. The request-driven provision orchestrator in `extension/src/content/kindoo/provision.ts` implements this; the per-site fan-out applies the same union within each site bucket so that no within-site duplicate's buildings are silently dropped.

**Multi-site provision — sequential per-site walk.** Multi-site provisioning walks the plan sequentially. The orchestrator iterates over the distinct `kindoo_site_id` values required by the write, in a stable order. For each step, the Phase 3 EID check (see §15 Phase 3) validates that the active Kindoo session's EID matches the step's `kindoo_site_id`; if it doesn't, the orchestrator refuses with the existing "switch to site X" error and the operator switches sites in the Kindoo UI before retrying. Each per-site Kindoo write is atomic at the Kindoo level, so a half-progressed plan (operator completes step 1 then walks away) is recoverable — re-running the request from scratch produces the same end state. There is no session-registry or upfront-reachability machinery; the per-step EID check is the gate.

**Utilization.** Foreign-site ward seats stay excluded from home-stake utilization. The calculation reads `Seat.kindoo_site_id` directly when populated (`syncApplyFix`, `markRequestComplete`, and the migration stamp it) and falls back to the seat's `scope` → ward → building `kindoo_site_id` (via `wardSiteMap`) for legacy seats still in the migration window. Externally observable behaviour is unchanged — the field is a denormalisation.

**Request completion auto-merge.** `markRequestComplete`'s server-side `planAddMerge` (in `functions/src/callable/markRequestComplete.ts`) stamps `kindoo_site_id` on a newly-appended `duplicate_grants[]` entry, derived from the request's scope and ward lookup. `building_names` is already recorded on the duplicate; this adds the site. The extension's deprecated v2.2 auto-merge path (referenced in the `DuplicateGrant.building_names` comment in `packages/shared/src/types/seat.ts`) is not affected — that code path is separate.

**Manager-granted stake access — parallel-site grant on completion.** The "Give Access To Stake Buildings" flow (§6.1) submits an `add_manual` / `scope: 'stake'` request for a foreign-site-only member who already holds a ward seat on a foreign Kindoo site. Because the member already has a seat, completing the request is an add-onto-existing-seat merge, not a fresh-seat create: `markRequestComplete` → `planAddMerge` appends the stake grant as a **parallel-site `duplicate_grant`** with `kindoo_site_id = null` (home — stake scope resolves to home per the data-model rules above) alongside the member's existing foreign-site grant. The grant becomes a home-site write in the per-site provision walk. When the manager applies it from the extension while in the **home** Kindoo environment, the member — who exists only in a foreign Kindoo environment — is not found there, so Kindoo invites them, **consuming an additional home-environment Kindoo license** (exactly the cost the dialog's red banner warns about). This is an instance of the add-onto-existing-seat case the extension's queue panel permits — a stake-scope `add_manual` for a member with no stake grant (see §15 Extension queue panel below); every other add for a member who already has a seat is Reject-only.

**One-shot migration.** A separate migration step backfills `kindoo_site_id` on every existing primary seat and every existing `duplicate_grants[]` entry by looking up the entry's `scope` → ward → building `kindoo_site_id` (stake-scope ⇒ home). Decisions locked in:

- **Skip-if-equal.** The migration reads the existing `kindoo_site_id` on each seat and each `duplicate_grants[]` entry; it writes only when the derived value differs from what's already stored. First run produces ~500-750 audit rows (one per write); re-runs over an already-migrated stake produce 0.
- **Missing-ward fallback.** When a `duplicate_grants[]` entry's `scope` points at a ward that no longer exists, the migration skips the entry with a logged warning. It does not error out the whole migration and does not fall back to "home" (which could silently miscategorize a foreign-site grant).
- **Audit-row churn.** Migration writes stamp `lastActor.canonical = 'Migration'`; the `auditTrigger` recognises that sentinel and emits each row under `action='migration_backfill_kindoo_site_id'` rather than generic `update_seat`. First run: ~250 seats × ~1-2 duplicates each → ~500-750 rows, one-time. Re-runs: 0 audit rows (skip-if-equal).
- **Scope.** Per-stake. The migration callable (`backfillKindooSiteId`) takes a `stakeId` parameter, matching the rest of the architecture's stake-parameterization (F15).
- **Auth.** Platform superadmin only — gated on the `isPlatformSuperadmin` custom claim (it previously gated on being an active Kindoo Manager of the stake; that gate was removed so a superadmin can run it against any stake without holding a manager role there). Superadmins invoke it from the Stake List page's per-row Apply Fixes menu (§5.4).

### Phase B — roster surfaces for parallel grants

Phase A (above) makes the data model and the Kindoo-side writes correct per-site. Phase B closes the visibility gap on the Manager-facing roster surfaces: AllSeats renders one row per grant; Bishopric / Stake / Ward Rosters and the Manager Dashboard's per-scope rollups broaden inclusion so a seat appears under any scope its primary or any `duplicate_grants[]` entry matches; the per-row foreign-site badge keys off the rendered grant's `kindoo_site_id`; and the Remove path on duplicate rows splices only the matching `(scope, kindoo_site_id)` entry. Implementation landed in T-43.

**Prerequisite.** Phase B assumes the T-42 Phase A migration callable (`migration_backfill_kindoo_site_id`) has run on every target stake so that `Seat.kindoo_site_id` and each `duplicate_grants[]` entry's `kindoo_site_id` are populated. The Phase B `isParallelSite = grant.kindoo_site_id !== primary.kindoo_site_id` predicate is meaningless on un-migrated seats where both sides are `undefined`. Deploying Phase B against an un-migrated stake renders every duplicate as `isParallelSite === false` (same-site) and the broadened-inclusion / per-grant badge work degrades to a no-op rather than misclassifying — but the operator-visible behaviour is undefined and Phase B does not roll out until the migration has run.

**AllSeats — one row per (member, scope) per seat.** `apps/web/src/features/manager/allSeats/AllSeatsPage.tsx` renders one row per **scope** on each seat: the primary plus one row per `duplicate_grants[]` entry whose scope differs from every earlier grant on that seat. Same-scope duplicates (a primary plus one or more DuplicateGrants sharing the primary's `scope`) collapse into the row that owns that scope (primary if it matches, else the first duplicate at that scope) — the collapsed row's `building_names` is the union of every same-scope grant's buildings in stable primary-first order. Cross-scope duplicates render unchanged (their own row). Each row's columns — scope, callings, type, building_names, foreign-site badge, reason / dates for manual / temp — reflect the grant being rendered. The pending-removal badge query (`partitionPendingForRoster` in `apps/web/src/features/requests/rosterPending.ts`) discriminates by `(member_canonical, scope, kindoo_site_id)` via the exported `pendingRemoveKey` helper, so a pending remove on one row doesn't light up another row with the same scope but a different `kindoo_site_id`. Two same-scope rows on the same `kindoo_site_id` no longer exist post-collapse on a single seat.

**Reconcile button removed.** The Reconcile button + `ReconcileDialog` + `useReconcileSeatMutation` are gone. Phase B's multi-row rendering surfaces every grant visually, making Reconcile redundant.

**Per-row data shape.** The helper `grantsForDisplay(seat: Seat): GrantView[]` in `apps/web/src/lib/grants.ts` returns one `GrantView` per grant: `{scope, callings, type, building_names, kindoo_site_id, reason?, start_date?, end_date?, isPrimary, isParallelSite, duplicateIndex, hasSameScopeDuplicates}`. The first entry corresponds to the primary; each subsequent entry to a `duplicate_grants[]` entry in array order. `isParallelSite` is `kindoo_site_id !== primary.kindoo_site_id` per the Phase A distinguishing test. `hasSameScopeDuplicates` is always `false` on a raw `grantsForDisplay` view; it is set to `true` by the same-scope collapse helpers (`collapseSameScopeGrants` for AllSeats; `pickGrantForScope` for per-scope roster pages) when the chosen view absorbed building_names from one or more other same-scope grants. AllSeats pipes every seat's views through `collapseSameScopeGrants(views)`, which folds same-scope DuplicateGrants into the row that owns each scope and unions their `building_names`. Per-scope roster pages use `pickGrantForScope(seat, scope)` to pull just the grant that matched the page's scope; if other grants share that scope on the same seat, their `building_names` are unioned into the returned view and `hasSameScopeDuplicates` is set.

**Bishopric Roster / Stake Roster / Ward Rosters — broadened inclusion, single row.** `apps/web/src/features/bishopric/RosterPage.tsx`, `apps/web/src/features/stake/RosterPage.tsx`, and `apps/web/src/features/stake/WardRostersPage.tsx` include a seat on a scope's roster page when **any grant** (primary OR any `duplicate_grants[]` entry) matches the page's scope. One row per person; the row renders the fields of the grant that matched the scope (calling list, type, building_names, foreign-site badge), not the primary's fields. When a seat carries more than one grant at the page's scope (primary + one or more same-scope DuplicateGrants), `pickGrantForScope` returns a single view whose `building_names` is the union of every same-scope grant's buildings (primary-first stable order) and whose `hasSameScopeDuplicates` flag drives the same-scope-duplicate badge on the row (label by primary type — see "Same-scope-duplicate badge — label by grant type, unified tooltip" below). The hooks (`useBishopricRoster`, `useStakeRoster`, `useWardSeats`) implement the wider read as a two-query union per KS-10 Option (b): `where('scope', '==', X)` plus `where('duplicate_scopes', 'array-contains', X)`, merged client-side by `member_canonical`. The presentation extracts to a shared `apps/web/src/components/roster/PerGrantRosterCard.tsx` primitive. Each `PerGrantRosterCard` lays its header out over **two lines**: the **first line** carries the grant-type and status badges (auto / manual / temp, plus any "Pending Removal", "edited"/"duplicate", and Kindoo-site badges) on the left and the right-justified Edit / Remove action buttons; the **second line** shows the member name and email. The calling/reason, buildings, and (for temp grants) date lines follow below as before. The AllSeats `GrantRowCard` uses the same two-line header, but with only the right-justified **Remove** action button on the first line (grant-type / status badges + scope on the left, Remove on the right; member name and email on the second line) — All Seats has no Edit affordance (see §212). On a foreign-site-only member's primary row, the manager-only **"Give Access To Stake Buildings"** button (§6.1) sits in the same right-justified action span, before Remove. It shares the `roster-card--two-line` modifier and `roster-card-member-line` wrapper so the two surfaces stay visually consistent. (The `PerGrantRosterCard` roster surfaces keep both Edit + Remove on the first line.) Auto / manual band rows matched on a duplicate grant sort by the **seat's** `callings` (auto) / `reason` (manual) — the grant-overlay shim doesn't override those fields — so a duplicate-matched row sorts at the primary's calling rank. In the rare case where a duplicate's calling rank differs from the primary's, the row sorts at the primary's slot. Acceptable at target scale — fix only if it becomes visible in production rosters.

**Manager Dashboard — broadened inclusion on per-scope rollups.** `DashboardPage.tsx`'s `countSeatsForScope` helper counts a seat on a scope's bar when its primary OR any duplicate's scope matches. Same-scope within-site duplicates collapse — one count per `(member_canonical, scope)` — so a seat with two `scope='CO'` grants doesn't double-count on the Maple bar.

**Same-scope DuplicateGrants — collapsed everywhere.** A DuplicateGrant whose `scope` matches the primary's (whether a within-site Sync-written priority loser, a `planAddMerge` same-scope manual addition like a manager-added grant naming extra buildings, or anything else with `dup.scope === primary.scope`) does NOT render as its own row on any manager surface. AllSeats and per-scope roster pages collapse it into the (member, scope) row owned by the primary (or the first same-scope grant when no primary matches); the collapsed row's `building_names` is the union of every same-scope grant's buildings. A same-scope-duplicate badge (labelled "Edited" for auto primaries, "Duplicate" for manual/temp — see below) marks any collapsed row whose union absorbed buildings from at least one same-scope DuplicateGrant. No separate Kindoo write happens for same-`kindoo_site_id` same-scope grants — the primary's write covers them per §454.

**Same-scope-duplicate badge — label by grant type, unified tooltip.** Both AllSeats (`GrantRowCard` in `AllSeatsPage.tsx`) and per-scope roster pages (`PerGrantRosterCard.tsx`) render this badge on any collapsed row whose `grant.hasSameScopeDuplicates` is `true`. The **label follows the collapsed row's primary grant type**, identically on every surface (AllSeats, Bishopric Roster, Stake Roster, Ward Rosters): primary `type: 'auto'` → **"Edited"**; primary `manual` or `temp` → **"Duplicate"**. (An auto primary is calling-derived from the LCR import, so absorbing additional buildings reads as an edit to that baseline; a manual/temp primary has no such baseline, so the additive grant reads as a duplicate.) In all cases — both labels, every surface — the tooltip is the single unified copy **"This user was manually granted access to additional buildings."**, which explains that the row's `building_names` was widened beyond the primary grant's explicit set. The label is computed inline as `grant.type === 'auto' ? 'edited' : 'duplicate'`; there is no per-view prop. AllSeats also continues to render a "Duplicate" badge on cross-scope DuplicateGrant rows (`!isPrimary && !hasSameScopeDuplicates`) with the older parallel-site / within-site tooltips on the badge itself for those still-standalone rows.

**Foreign-site badge — per-row / per-grant.** The new `siteLabelForGrant(grant, wards, sites)` helper in `apps/web/src/lib/kindooSites.ts` resolves the badge from the grant's own `kindoo_site_id`, falling back to the ward catalogue when the grant's site is null (legacy / pre-migration). A Maple bishopric row showing a stake-primary person whose Maple duplicate is being rendered shows the badge based on Maple's site (home → no badge; foreign → that site's display name), not on the seat's primary site. The legacy `siteLabelForSeat` sibling remains for non-grant-aware callers.

**Edit Seat dialog — unchanged.** Phase B does not modify the Edit Seat dialog. Edits continue to operate on the primary grant only. Parallel-site changes require a new request.

**No Edit affordance on AllSeats.** All Seats has no Edit button on any row (primary or duplicate). Editing a seat is roster-only — it flows through the roster pages' `EditSeatDialog` request flow (§212, §6.1), which creates an audited edit request; no edit dialog writes the seat doc directly. (Per-scope roster pages similarly don't render an Edit button on grant-matched duplicate rows — the `canEditSeat` gate keys off `seat.scope`, which is the primary's, and a bishopric viewing a stake-primary duplicate row has no authority over the primary scope.)

**Remove button on duplicate rows in AllSeats — functional when the duplicate's (scope, kindoo_site_id) differs from the primary's.** Clicking Remove on a duplicate row generates a `remove` request whose `scope` and `kindoo_site_id` field reflect the duplicate's grant, not the seat's primary. `kindoo_site_id` is always present on `remove` requests, mirroring the (scope, kindoo_site_id) discriminator pair. For a primary-row remove, the value equals the seat's top-level `kindoo_site_id`; for a duplicate-row remove, it equals that duplicate's `kindoo_site_id`. The `planRemove` trigger discriminates on the (scope, kindoo_site_id) pair against the seat's grants. The `<RemovalAffordance>` component requires a `grant` prop carrying both fields; every caller passes it.

Same-`(scope, kindoo_site_id)` collisions on a single seat no longer produce a standalone duplicate row at all — they collapse into the primary's row per §485, so the Remove discriminator never has to disambiguate a same-`(scope, kindoo_site_id)` pair from a duplicate row. The `planRemove` trigger's KS-9 auto-primary disambiguation in `functions/src/triggers/removeSeatOnRequestComplete.ts` remains in place as defense-in-depth for the path where a Remove on the (collapsed) primary row of an `auto` primary that absorbed a manual same-scope DuplicateGrant resolves to the non-auto duplicate (per `planAddMerge` semantics). Cross-scope (`scope`-different) duplicates and parallel-site (`kindoo_site_id`-different) duplicates always render their own row and always render Remove; the (scope, kindoo_site_id) discriminator targets that row's grant unambiguously.

**Mark Complete dialog — unchanged.** Phase A's `markRequestComplete` merge logic already stamps the new duplicate's `kindoo_site_id` correctly.

**Audit Log — unchanged.** Phase A's roughly 2× audit-row volume on multi-site provisions is accepted as-is.

**Sort and filter on AllSeats.** Each row sorts independently by its own grant's fields. There is no grouping by seat — a person's two rows can interleave with other people's rows when sorted by calling, type, or any other column.

**Server-side surface.** Phase B requires three server-side changes:

- **`Seat.duplicate_scopes: string[]` denormalized field (OWNED BY PHASE A).** Firestore-rules CEL cannot project a field across an array of objects (no `array[*].field` projection; only primitive-array operations like `in` / `hasAny` / `hasAll`), so the bishopric `seats.read` widening reads against this primitive mirror. Phase A maintains it on every seat-write path: `syncApplyFix.ts`, `markRequestComplete.ts` (fresh-seat create + `planAddMerge` merge branches), `removeSeatOnRequestComplete.ts` (both promote and drop_duplicate paths), and the T-42 migration backfill. (The former web-side queue-completion seat write was dropped when the app queue became read-only — completion now runs through the Chrome extension's `markRequestComplete` callable path.)
- **`firestore/firestore.rules` — bishopric `seats.read` widened.** The bishopric clause now reads `resource.data.scope in bishopricWardOf(stakeId) || ('duplicate_scopes' in resource.data && resource.data.duplicate_scopes.hasAny(bishopricWardOf(stakeId)))`. The presence guard is defense-in-depth: if any seat-write path lands a doc without `duplicate_scopes`, `hasAny(...)` on the missing field would throw and the bishopric read would explode; the presence check degrades that case to "no duplicate matches" rather than a hard rule error. The stake-presidency clause needs no widening — `isStakeMember(stakeId)` already grants unrestricted seat reads in the stake.

## 16. Remote apply — running a request from your phone

A Kindoo Manager standing in a building with a phone could read the Requests Queue (§5.3) but not act on it: every Kindoo write runs in the Chrome extension, which is desktop-only. Remote apply closes that gap without moving any Kindoo work onto the phone. The manager opts in on their desktop; the phone then offers **Apply via extension** on each pending card, and tapping it makes the manager's own desktop do exactly what its own button would have done. Design rationale and the alternatives that were rejected are in `architecture.md` D27; the mailbox's shape and rules are `firebase-schema.md` §3.4.

**The whole feature is live-only.** Nothing is queued for a sleeping desktop. The button exists only while the desktop has checked in recently, and a job the desktop never picks up is cancelled rather than left waiting.

**Coverage is per Kindoo site, not per manager.** A stake can run more than one Kindoo site (§15), and a Chrome tab can only provision for the site it is currently inside. So the desktop publishes one liveness record per site it has a live tab on, every request resolves to the one site it must be provisioned on, and the button appears on a card only when a live tab is sitting in that site. A manager with two tabs on two sites covers both at once; a manager with one tab covers one, and the cards for the other site say which site to open.

### Opting in (desktop)

The extension's Queue tab carries a checkbox above the request list, **"Allow requests from my phone"**, with the hint "Lets you tap **Apply via extension** in the SBA queue on your phone and have this Chrome tab do the Kindoo work. Only while this Kindoo tab is open and signed in." It is **off by default and off for every profile that predates the feature** — it hands a second device the authority to provision building access, so it has to be an explicit act, and a failure to read the setting resolves to off.

The setting lives in `chrome.storage.local`, so it is per Chrome profile, not per person: a manager with Chrome on two computers opts in on each one separately. A second Kindoo tab in the same profile converges on the change without a reload. **The opt-in is the one profile-wide fact in the feature** — ticking the box in one tab enables every tab in that profile, so it knows nothing about sites.

While opted in, and only while a Kindoo tab is open **and its Kindoo session actually works**, that tab publishes a heartbeat every 60 seconds for the one Kindoo site it is sitting in, naming the stake it resolved, the site, and its own version. Two tabs on two sites of one stake publish two independent records and neither disturbs the other. A tab whose Kindoo site is one this stake hasn't configured publishes nothing at all: it can't name the site to the phone and couldn't provision for it either.

The session test is a real Kindoo API call (the same one that resolves the site name the phone displays), not merely the presence of a token — an expired token looks identical to a live one until something uses it. A desktop that fails that call publishes nothing, and **the absence of a fresh heartbeat is exactly how the phone learns that desktop can't help**. Signing out of Kindoo, closing the last Kindoo tab, or putting the computer to sleep all produce the same silence.

**A tab that can't resolve its site retries on the heartbeat's clock, not the poll's.** An expired Kindoo session and a Kindoo site this stake hasn't configured both leave a tab unable to name where it is, and neither clears on its own — so a retry driven by "still unresolved" would put a call on Kindoo's servers every 10 seconds for as long as the tab stayed open. The budget is one Kindoo call per 60 seconds per open tab whether the tab is healthy or not. Navigating to a different Kindoo site re-resolves at once, because that is new information rather than a retry, and it is what lets a tab recover the moment the manager signs back in or configures the site they are sitting in.

Switching the toggle off publishes the opted-out state immediately rather than just going quiet, and the tab also **deletes its own liveness record** rather than letting it age out — a stale-but-present record still names its site as covered on the phone for the rest of the staleness window, which is precisely the wrong advice. Both writes are sent even when the Kindoo session is already dead, because clearing consent must never be blocked. Stopping the heartbeat loop cannot abort a beat already in flight, so the extension re-reads the opt-in synchronously in the instant before every presence write: a beat that was waiting on Kindoo when the toggle flipped is dropped rather than landing after the opted-out write and leaving the phone showing the desktop as online for the rest of the staleness window.

A tab that *moves* to another Kindoo site does not delete the record it is leaving. The delete is safe only because the opt-in is profile-wide and now off, so no sibling tab is serving that site either; a move says nothing about the sibling.

### What the phone shows

One line sits under the queue's extension note and answers a single question: which Kindoo sites can this phone apply for right now. It renders nothing until presence resolves, so the page never flashes advice at someone whose desktop is fine.

| State | Line | Means |
| --- | --- | --- |
| Live | "You can apply requests for {sites} from here." — every covered site named, alphabetically, `A`, `A and B`, `A, B and C` | Opted in, at least one heartbeat fresh, and in this stake. Naming one site when two are covered would read as a promise about the other, so the line names them all. Falls back to "Kindoo is open on your computer — you can apply requests from here." when no covered site can be named at all. |
| Not online | "Open Kindoo in Chrome on your computer to apply requests from here." | Opted in, but every heartbeat has aged out — Kindoo tabs closed, computer asleep, or signed out of Kindoo. |
| Wrong stake | "Your computer has a different stake open in Kindoo. Switch it to this stake to apply requests from here." | A heartbeat is fresh but every live tab is in another stake's Kindoo site. Distinguished deliberately: telling a manager whose desktop is heartbeating fine to go open Kindoo sends them chasing the wrong problem. |
| Off | "Turn on 'Allow requests from my phone' in the extension on your computer." | No presence doc, or the toggle is off. Also the fallback when the read errors — the advice is the same either way. |

A site's name is the one its own tab reported from Kindoo, so it matches what the manager will see on the desktop. Where the stake's own configuration names that site, that name wins.

A heartbeat counts as fresh for 150 seconds, comfortably more than two heartbeat periods so a single missed tick doesn't flap the button. Freshness is re-evaluated on a 30-second timer, not on a write, because a desktop that goes away produces no snapshot to react to.

### Which Kindoo site a request needs

Every pending card resolves to exactly one Kindoo site, and that site decides whether the card gets a button.

**The site is derived, never stored.** A `stake`-scope request goes to the home site unconditionally — its buildings may span sites, and it is still provisioned on home, so buildings never enter the derivation. A ward-scope request goes to its ward's building's site, and a ward the catalogue doesn't know resolves to home, which is what the desktop's own site check does with the same input. Home has no `kindooSites` document (it lives on the stake's `kindoo_config`), so it is spelled with the reserved site key `home` and matched exactly the way a foreign site is.

**`AccessRequest.kindoo_site_id` is not this site.** That field records the site of the grant a `remove` targets (§15) and is absent on every add and edit; reading it as the target would resolve to "no site" on almost every request. The derivation lives in `@kindoo/shared` (`remoteApplyTargetSiteKey`) for one reason: it must give the same answer as the extension's own `checkRequestSite`, which is what actually refuses a provision on the wrong site. A phone that derived differently would offer a button the desktop then rejects.

**No site derived, no button.** Until the ward and building catalogues have loaded, no target is derived and no card offers anything — an empty ward catalogue derives every request to home, which is the right answer for a genuinely unknown ward and the wrong one for a subscription that hasn't arrived yet.

When a card's site is covered by a live tab, it gets **Apply via extension**. When it isn't — but something else is live — it gets one line instead: "Open {site} in Kindoo on your computer to apply this one.", or "Open this request's Kindoo site in Chrome on your computer to apply it." when the site has no name to give. With nothing live at all the line is suppressed, because the header already says to open Kindoo and repeating it on every card is noise.

### Applying

Tapping **Apply via extension** writes one job for that request, stamped with the site it must be provisioned on. **Only a tab inside that site may claim it.** The desktop polls every 10 seconds while its Kindoo tab is in the foreground and every 60 seconds when it is hidden; each poll reads a page of queued jobs, skips any whose site this tab can't serve, and claims the first one it can. Reading a page rather than the oldest job is what makes two tabs work: with two sites open the oldest queued job routinely belongs to the other tab, and both taking it and stalling behind it are wrong. The card then shows, live:

| Status | What the manager sees |
| --- | --- |
| Sending | "Sending to your desktop…" — the tap is being written. |
| `queued` | "Sent to your desktop — waiting for it to start…" |
| `running` | "Your desktop is applying this…" |
| `applied` | "Applied ✓" |
| `partial` | "Applied in Kindoo, but this request is still open here." plus the desktop's explanation, defaulting to "Finish it on your desktop to close it out." |
| `failed` | "Your desktop didn't finish this." plus the desktop's message. The headline deliberately stops short of saying the apply didn't happen: a job whose tab died mid-run is finalised `failed` too, and for that one nobody knows whether Kindoo took the write. |
| `cancelled` | "Your desktop didn't pick this up." plus "Open Kindoo in Chrome on your computer, then try again." |

**Retry is offered on `failed` and `cancelled` and withheld on `applied` and `partial`.** `partial` means Kindoo took the write and only the Stake Building Access side didn't get marked complete — the access exists, and re-running it would consume a second Kindoo licence. The manager finishes that one on the desktop.

**One job per request at a time.** A second tap is blocked while any non-terminal job for the same request is in flight, and the guard is armed before the write is issued rather than derived from the render that follows it — a phone synthesises a click from a touch, and both taps arrive in the same task, before any state derived from the first one exists. The button is withheld for a second reason: until the job subscription has resolved, "no job for this request" is not yet a fact, and offering **Apply via extension** against a mailbox nobody has read yet is the other way one request ends up with two jobs. Reloading the page mid-apply does not lose the job — the phone subscribes to the manager's whole mailbox, so a request being applied from their other device shows its status here too.

**When one request does hold several jobs, the card shows the most conclusive one, not the newest.** Precedence runs `applied`, `partial`, `running`, `queued`, then `failed` / `cancelled`, with the newest winning inside a rank. Ranking by recency would be wrong in exactly the case that matters: when two jobs exist for one request, the desktop claims the second one *after* it has already applied the first, finds the request no longer pending, and reports `failed` — so the newest job for a request that was successfully applied is a failure notice. Reporting that is the worst thing this surface can say, because the manager's correct response to it is to go redo a provision that has already consumed a Kindoo licence.

**Two phones tapping at the same moment can still produce a duplicate, and that is accepted.** Each device writes its own job and neither can see the other's tap in time; the create rule permits it and nothing on the client can close it. It is harmless: the precedence above keeps the successful job on screen, and the desktop refuses the loser with `request_not_pending` before touching Kindoo.

**A job nobody picks up is cancelled after 90 seconds.** That is longer than one hidden-tab poll, so a backgrounded desktop still wins. If the desktop happens to claim it in the same moment, the cancel is rejected server-side and silently dropped — the card is already showing `running`.

**The desktop enforces the same 90 seconds, because the phone cannot be trusted to.** The phone's timeout is a timer inside the open page: locking the screen suspends it and closing the tab kills it, which is how a phone session normally ends. So the poller checks a queued job's age before claiming it, and cancels anything already past the pickup window. Without that, a manager who taps **Apply via extension** and pockets their phone has the request provisioned unattended whenever Kindoo next opens on their computer — the next morning, if that is when they open it.

Cancelling rather than merely skipping is the load-bearing part. A `queued` job is not inert on the phone: its row reads "Sent to your desktop — waiting for it to start…" and counts as in flight, so the manager cannot tap Apply for that request again. Skipping would trade an unattended provision for a request the manager is silently locked out of. The cancelled card says the desktop didn't pick it up and offers retry, exactly as it does for the phone's own timeout — the two paths are indistinguishable on screen, and differ only in the job trail, where the desktop's write records that nothing was changed in Kindoo and the phone's records no outcome at all. Any of the manager's Kindoo tabs will do this, including one sitting in a different Kindoo site: the tab that could have run the job is the one most likely to have been closed, which is how the job went stale in the first place.

### Acknowledging the result

**A terminal outcome raises a dialog, not just a changed row.** The desktop ends every **Provision & Complete** in a modal the manager has to dismiss; the phone showed only the inline row, so a manager who tapped Apply and pocketed the phone came back to a card that had quietly changed colour. The row stays — it is the at-a-glance state, and it is what history looks like — and the dialog is the acknowledgement. Escape and a tap outside do nothing; **Dismiss** is the only exit, because the point of it is that it gets read.

**The dialog belongs to the page, not to the card.** It is mounted once by the queue and selects across the manager's whole mailbox, so its lifetime is independent of whether the request is still pending, still rendered, or in the queue at all — it raises with an empty queue behind it, which is the state applying the last pending request actually produces. Mounted inside the request's card it sat in the one component whose lifetime ends exactly when the event it exists to announce occurs: a successful apply completes the request, the request drops out of the pending subscription, the card unmounts and takes the dialog with it. What that produced on screen was a flash — two snapshots landing in order, the terminal job first and the request's status change a beat later. The inline row is per-card and stays that way, because it is the at-a-glance state of a request that is on screen.

**It raises on sight of a terminal job this device queued and has not acknowledged.** Waiting to witness the transition fails for exactly the device the feature exists for: the manager taps Apply, turns to the desktop to watch it work, and the phone locks. On wake the page has re-mounted and the job is already terminal on first sight, so the dialog was suppressed in the commonest real flow. The two properties a transition rule was carrying are carried by narrower facts instead. *Not someone else's* — the job records the device that queued it, and only that device raises; a job queued from the manager's other phone belongs to that phone's screen, and a device id that can't be read matches nothing, so an unattributable job raises nothing rather than raising everywhere. *Not history* — dismissing is what makes an outcome history, and the acknowledgement is persisted per device rather than held in component state, because a locked phone guarantees the reload.

**Acknowledgements are capped per device, and the cap is a storage backstop rather than a working limit.** Evicting an id is not free once the dialog selects across the whole mailbox: the outcome that id acknowledged raises again, and dismissing that re-raise evicts the next-oldest, which raises in turn — a modal walk backwards through the manager's own history. The bound is therefore sized never to be reached (500 ids; decades at 1–2 requests a week, a few kilobytes against a multi-megabyte quota). A device that clears its storage loses its device id in the same act, so its old jobs stop matching and nothing raises at all.

**Several outcomes finishing close together are shown one at a time, oldest completion first**, each needing its own **Dismiss**. Every outcome is a separate acknowledgement — a `failed` must not be buried under an `applied` that finished after it. Completion order rather than newest-first because it is monotone: an open dialog can only change by being dismissed, so a job terminating a beat later cannot swap the title and body out from under a tap already travelling toward Dismiss. Ordering reads `finished_at`, falls back to `created_at` for the phone's own `queued → cancelled` write (whose `serverTimestamp()` is still unresolved in the snapshot that follows it), then breaks ties on the job id, since the mailbox query is unordered.

**All four terminal statuses raise it, where the desktop's dialog has two modes.** The desktop is a computer someone is sitting at; a phone gets pocketed, and a silent failure there is worse than a silent success. So `failed` and `cancelled` raise the dialog too, worded exactly as the row is.

**`applied` carries what the row has no room for.** The dialog shows the desktop's provisioning note — what it actually did in Kindoo — and, when the completion pushed a seat pool past its cap, a **"Now over cap:"** list with one line per pool, each naming the pool with the same scope label the rest of the card uses and reading `{count} / {cap} (over by {n})`. The desktop's own result dialog has always shown that warning; before this the remote path dropped it entirely, so a manager applying from their phone never learned a cap had been breached. The warning appears only on `applied`: `partial` means the completion never landed, so there is no over-cap answer to carry, and an empty list there would read as "all clear" rather than "never asked".

**Dismiss is the only button, on every status — the dialog offers no retry.** For `partial` the desktop's dialog does have one, and it is an action this surface cannot reproduce: it replays the completion input the desktop captured in memory (an SBA-only write, no second Kindoo call), and the job doc records the outcome rather than that input, so the phone would be guessing the completion note it writes into the permanent record. It would also be the first `markRequestComplete` this page has ever issued, against a queue whose only action is remote apply (§5.3). For `failed` the question is sharper, because the request may have left the queue and taken its **Try again** with it — but every shape that produces one says no anyway. `request_not_pending` means the request is gone precisely because someone else resolved it, so there is nothing left to apply. A stranded tab that reached `markRequestComplete` before dying is finalised `failed` with a message that refuses to say whether Kindoo took the write, and retrying that is how a licence gets consumed twice. The failures genuinely worth another go — `site_mismatch`, `kindoo_session_lost`, `building_rule_missing` — leave the request `pending`, so its card is still on the page with the **Try again** that belongs there. A retry on the dialog would be available exactly when it is unsafe and redundant exactly when it is safe. The card's **Try again** is unchanged: a fresh job, meaning a full re-provision, offered on `failed` and `cancelled` only.

### When the desktop stops partway

A job the desktop has claimed but never reports on would otherwise sit at `running` forever. Nothing else in the system moves it: the desktop polls only for `queued` work, and the phone's timeout only cancels a job that was never claimed. The manager would watch "Your desktop is applying this…" with no exit.

Two mechanisms close that. The desktop retries its final write three times, one second then four seconds apart, so a single Firestore blip is not what strands a job. A permission denial is not retried — it means the job has already left `running`, so the write can never succeed. Then, when the loop starts and once a minute after, every one of the manager's Kindoo tabs looks for long-`running` jobs and finalises them as `failed` with a message that refuses to say whether the work landed: "Your desktop stopped partway through this request, so it never reported back. It may or may not have gone through in Kindoo — check this request on your desktop before applying again."

**How long is "long" depends on whether the sweeping tab could have run the job.** A job on the tab's own site is swept after five minutes; anything else — another site, another stake, or a tab that hasn't resolved its own site yet — waits ten. Two thresholds rather than a site filter, because a filter trades one bug for a worse one. Filter absolutely and a job stranded on site B is only ever cleaned up by a tab on site B, when the overwhelmingly likely reason it stranded is that the manager closed that very tab — the cleanup would wait on the thing that just failed to happen. Don't filter at all and the foreground tab finalises the other site's genuinely in-flight work out from under it. Splitting by threshold keeps both properties: the tab that could have done the work sweeps promptly, and every other tab still guarantees eventual cleanup, just late enough that "a sibling is still running it" is not a credible reading.

**Age is what stands in for attribution, deliberately.** The mailbox is keyed to one manager and the rules admit no other writer, so every `running` job in it was claimed by one of that manager's own Kindoo tabs. That is as far as identification goes: the `claimed_by` stamp carries an extension version and a Kindoo site, neither of which is unique to a tab, so filtering on it could not distinguish a live sibling tab from a dead one — it would only guarantee that a job stranded by another Kindoo site or an older extension build never got cleaned up. What remains is the clock, plus the set of jobs the sweeping tab is running itself, which it never touches. A real run is a handful of API calls; five minutes is far outside it. A job whose claim time can't be read is left alone entirely, since its age is the only thing that would justify sweeping it.

The sweep runs ahead of everything else on each tick, including the Kindoo session check — a tab whose session just died is a prime candidate for having stranded a job, and finalising one needs no Kindoo session at all. The cost is that the first sweep after a page load has no resolved site yet and holds everything to the longer threshold.

The residual: a manager with two Kindoo tabs, one of them stuck on a run that genuinely takes longer than its threshold, can have the other tab mark that job `failed` while it goes on to succeed. That is precisely why the wording refuses to claim the Kindoo write didn't happen, and why the desktop's own button is the place the manager is sent to check.

### What each failure means

The desktop authors every failure message, so the phone and the desktop word the same problem identically. The distinct causes:

| Cause | What happened |
| --- | --- |
| Desktop stopped partway | The tab that claimed the job went away before reporting — browser quit, tab closed, final write exhausted its retries. Swept to `failed` by any of the manager's Kindoo tabs, at whichever of the two thresholds above applies. The message says the Kindoo write may or may not have landed, because nothing knows. |
| Wrong Kindoo site | The tab moved to a different Kindoo site between claiming the job and running it. Rare now — the site key on the job means only a tab already inside the right site can claim it — but the desktop's check still runs, and it is the authority. The message names **both** sites, where you are and where you need to be, because switching sites is something only the person at the desktop can do. |
| Kindoo session lost | The Kindoo tab no longer has a usable token, or the extension can't tell which site it is in (the "My Sites" listing page is open rather than a specific site). |
| Building rule missing | One of the request's buildings has no Kindoo rule mapped yet. Fixed by re-running the extension's configure wizard. |
| Request no longer pending | It was completed, rejected, or cancelled before the desktop got to it. The desktop re-reads the request before doing anything, so this is caught before any Kindoo write. |
| Applied in Kindoo, not closed here | The `partial` case above. |
| Anything else | The underlying Kindoo API error, surfaced verbatim. |

**The phone routes; the desktop refuses.** The phone derives which site a request needs and uses it to decide whether to offer a button and, when it can't, which site to name. It never asserts a mismatch — the check that actually blocks a provision runs on the desktop, which is the only place that knows which Kindoo site is open right now, and its sentence is what the phone displays. The two stay in step because both read the same derivation out of `@kindoo/shared`; a divergence would show up as a button that always fails.

### On the desktop

While a phone-initiated job runs on this tab, the extension's Queue tab shows a banner — "Applying a request you sent from your phone…". A job in any other hand — still waiting in the mailbox, or claimed by another of the manager's Kindoo tabs — shows "Your desktop is handling a request you sent from your phone…" instead. The two never stack: only the tab actually running the job can say so, and that is the stronger statement. The queue refetches when the job finishes, so the desktop never sits displaying a request the phone just completed. The heartbeat and poll loop, the queue fetch, and that refetch are all owned by the panel shell rather than the queue view: switching to the Sync tab or closing the slide-over entirely must not make the manager unreachable from their phone, and phone-initiated work is normally done with the panel shut, which is precisely when a refetch owned by the queue view would not run.

**That request's own Provision & Complete button is disabled while any phone-initiated job holds it**, with a line on the card saying which hand it is in: "You sent this one from your phone — this tab is applying it now. Wait for it to finish rather than applying it twice." when this tab is the one running it, and "…your desktop is handling it. Wait for it to finish rather than applying it twice." when it is not. Tapping on the phone and then clicking on the desktop otherwise runs the same provisioning code twice against one request, and for a member who isn't in Kindoo yet the second run is a second invite — a consumed licence that no amount of later bookkeeping undoes. **Reject stays enabled**: it makes no Kindoo write, so a concurrent reject can't duplicate anything.

**What the gate covers, and the one window it doesn't.** A job this tab could never claim — another Kindoo site, another stake — is gated from the tap until whichever tab does claim it finishes; so is a job queued behind the one this tab is already running; and so is a job **another of the manager's Kindoo tabs is running**, which is why each tab reads the mailbox's `running` jobs on every poll rather than only when it sweeps. Reading only the `queued` ones would drop the gate the instant a sibling claimed the job — the start of the risky window, not the end of it. A run that ended **without managing to report its outcome** is gated too, and for longer: the desktop retries the write that records the result, and if all those attempts fail it has done work in Kindoo it cannot describe, so the button stays shut until the job is finalised as stopped-partway (which the manager sees as "check this request on your desktop before applying again"). Handing the button back at that moment instead — the moment the run ends, rather than the moment it reports — would offer a second provision for exactly the request whose first one nobody can account for. What is *not* covered is the tap → claim window for a job this very tab can serve: the poll that first sees such a job claims it in the same breath, so the gate is held there for one Firestore write rather than a poll period. The phone closes that window from its own side, by withholding **Apply via extension** for a request that already has a live job. And two Kindoo tabs whose manager clicks **Provision & Complete** in both, with no phone involved, remains uncovered — no job doc exists, so neither tab has anything to see. That one is still the manager's own two hands.

**A desktop that momentarily can't check keeps the button shut on what it last saw.** A Kindoo call that timed out, a site reading that came back ambiguous, a Firestore read that failed — none of them are evidence that a sibling tab stopped working, and each can be over by the time the manager's click lands, which is exactly when a second run does the damage. So the gate holds its last reading for **150 seconds** and then lifts. It lifts because the opposite failure is real too: a manager whose desktop can't see the mailbox at all, and whose other tabs aren't serving them either, would otherwise be locked out of their own button with nothing to lift it. Turning the opt-in off is the one thing that clears the gate immediately rather than waiting it out — with it off no tab in the profile is picking anything up.

The work itself is the same code the desktop's own **Provision & Complete** button runs — one shared orchestration, so the two surfaces cannot report different results for the same request. Self-approval, audit rows, over-cap warnings, and completion emails are all unchanged: the request is completed by `markRequestComplete` exactly as it would have been from the desktop, and the job doc is a transport record, not an audited entity.

### Not in scope

- **Waking a closed Chrome.** No push, no background execution. If no Kindoo tab is open, the phone says so and stops.
- **Rejecting from the phone.** Rejection needs no Kindoo session at all and the rules already permit a manager's reject write, so it could be a plain button with no extension involvement — a cheaper feature than this one, and a separate one. Not built.
- **Acting for anyone else.** The mailbox is keyed on the manager's own canonical email and the rules gate on it; there is no path by which one manager's phone reaches another's desktop.
