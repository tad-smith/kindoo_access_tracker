# Remote apply — tap on the phone, execute on the desktop extension

**Shipped:** 2026-08-03
**Commits:** PR #250 (`feat/remote-apply`), folding three parallel streams: `feat(shared)` + `feat(firestore)` (mailbox types + rules), `feat(web)` (queue UI), `feat(extension)` (opt-in, heartbeat, poller, `applyRequest` extraction).

## What shipped

A Kindoo Manager can now act on a pending request from their phone. They opt in once on their desktop Chrome extension ("Allow requests from my phone", top of the Queue tab); the opt-in lands at `remoteApply/{canonicalEmail}` and is profile-wide. While it is on and a usable Kindoo tab is open, that tab heartbeats liveness into `remoteApply/{canonicalEmail}/desktops/{siteKey}` for the one Kindoo site it is inside. The web queue on the manager's phone reads that presence and offers **Apply via extension** on each pending card whose own target Kindoo site a fresh tab covers. Tapping writes a job doc stamped with that site; the tab inside it claims it, runs the identical provisioning flow its own button runs, and writes the outcome back; the phone renders queued → running → applied ✓ / partial / failed live.

No new Cloud Functions, no new Chrome permissions, no new composite index, and no new role. The Requests Queue page is no longer read-only.

## Why polling, and why it was the only real option

Worth stating plainly because it looks like a lazy choice and isn't: **Kindoo writes can only happen in the content script.** They need the page's `localStorage.kindoo_token` and the active-site EID recovered by scraping the Kindoo header. Remote execution therefore already requires an open, signed-in Kindoo tab — and whenever that tab exists, the content script is mounted (on every page load, panel open or closed) and can simply poll.

That reduces push to a latency argument, and the latency is about five seconds. Buying those five seconds costs a VAPID keypair, a Secret Manager entry, a `web-push` sender, and a receiver in an MV3 service worker that structurally cannot hold state — and the receiver would still have to hand the work to the content script, which is where the poll already lives. At 1–2 requests a week that trade is not close.

Two other transports were considered and are dead on arrival rather than merely worse: a Firestore `onSnapshot` listener in the service worker (`onSnapshot` rides WebChannel, which needs `XMLHttpRequest`, undefined in MV3 — the same wall the reject path hit), and `externally_connectable` (same-device only; the phone is by definition a different device).

Recorded as `architecture.md` **D27**.

## Decisions made during the build

- **The heartbeat is gated on a *usable* Kindoo session, not on a token string.** `readKindooSession()` only proves a token exists; an expired one is indistinguishable from a live one until something calls the API. The loop resolves the active site name via Kindoo's `getEnvironments` on each heartbeat — a call it needs anyway, since the phone displays that name — and treats a rejection as "this desktop cannot act": no presence write, and the poll is skipped too. That costs one Kindoo API call per 60s per open Kindoo tab. It is worth it because **absence of a fresh heartbeat is the entire mechanism by which the phone learns the desktop can't help.** A heartbeat that outlived its session would leave the manager tapping a button that fails every time, with nothing on screen explaining why.

- **`partial` is a distinct terminal status, not a failure.** Kindoo took the write and `markRequestComplete` didn't. The phone says "Applied in Kindoo, but this request is still open here", tells the manager to finish it on the desktop, and deliberately offers **no Retry** — retrying would consume a second Kindoo licence. Calling this "failed" is the one wording mistake in the whole feature that costs real money.

- **The rules type-check the terminal fields but do not require them.** `finished_at`, `outcome`, `claimed_at`, and `claimed_by` are all optional in their transition branches. A denial on the extension's report-back would strand the job in `running` with the phone spinning forever, which is a worse failure than a terminal row missing a timestamp. Related: `outcome.code` is checked as `is string` rather than against the `RemoteApplyOutcomeCode` union, so the desktop's vocabulary can grow without a rules deploy — the extension ships through Chrome Web Store review on its own cadence, and making a rules deploy a prerequisite for an extension release would be a standing trap. Both are written down in `firebase-schema.md` §6.1 so a future reader doesn't "tighten" them by accident.

- **The job *create* rule is an exact key set, not a minimum.** `hasOnly` AND `hasAll` over the six fields the phone knows at tap time. Adding a field to the job doc later requires widening the rule first — deliberate friction, since the create rule is the only thing standing between "a manager's phone" and "arbitrary documents in a collection keyed on their own email".

- **Ownership alone was not enough; `isManager` is the second gate.** Because the doc key *is* the writer's canonical email, an ownership-only rule would let any signed-in user write whatever they liked to their own mailbox. Every write predicate also requires the manager claim for the doc's `stake_id`. It reads the claim only — no document read — so it costs nothing on the heartbeat path.

- **The status transitions are the lock, because no transaction is available.** The consuming side is an MV3 service worker, where `runTransaction` throws. So the compare-and-set lives in the rules: each branch pins the before-status. Two Kindoo tabs racing the same job both fire the claim; the first commits, the second is denied and skips silently. The service worker maps that one `permission-denied` to `claimed: false` rather than an error — losing a race is the correct outcome for the second tab, not a fault worth logging loudly — while every other failure still throws, so a rules regression can't masquerade as a lost race. The 90-second no-pickup timeout races the claim in the other direction and is settled by the same mechanism: the phone's `cancelled` write comes back denied, which means the desktop picked it up after all, so it is swallowed.

- **One provisioning orchestration, extracted to `content/kindoo/applyRequest.ts`.** This was the bulk of the work and the main risk. Previously the whole session → seat → envs → site-check → provision → `markRequestComplete` sequence lived inline in `panel/RequestCard.tsx`. Both the desktop button and the remote runner now call the extracted function, which returns a discriminated outcome: the card renders it into `ResultDialog`, the runner serialises it onto the job doc. A second copy would eventually have let the phone and the desktop report different results for the same request, with no way to tell which one lied. `extension/CLAUDE.md` now carries a "don't fork the provisioning flow" rule.

- **`ProvisionSiteMismatchError` now names the active site as well as the target** — "This request needs to be provisioned on 'X'. You are currently in 'Y'. Switch Kindoo sites and try again." This is the **one place the refactor changed existing desktop behaviour**, and it changed the desktop's rendered text too. The reason is on the phone: site mismatch is deliberately *not* duplicated there (the desktop is the only place that knows which Kindoo site is open), so the phone displays the desktop's sentence — and "switch sites" is unactionable on a phone unless the sentence says which site the desktop is currently sitting in.

- **The loop is hosted by `panel/TabbedShell`, not `panel/QueuePanel`.** `QueuePanel` unmounts when the operator switches to the Sync tab. A manager who left the panel on Sync would have silently stopped being reachable from their phone.

- **The phone distinguishes "wrong stake" from "not there".** A desktop can be heartbeating perfectly while sitting in another stake's Kindoo site. Telling that manager to go open Kindoo would send them chasing the wrong problem, so `other-stake` is its own presence state with its own sentence. Freshness for that state is computed by re-running the shared freshness predicate against each *other* stake a desktop doc names, so the staleness window stays defined in exactly one place.

- **The opt-in defaults off and fails closed**, matching the defaulting discipline D25 established for anything that grants authority. Absent means off; a `chrome.storage` read error resolves to off. Turning it off publishes the opted-out state immediately instead of just going quiet, so the button disappears at once rather than after the 150-second staleness window — and that disable write fires even when the Kindoo session is already dead, because clearing consent must never be blocked by a broken tab.

- **The runner trusts the job doc for nothing but a `request_id`.** The phone is a second device with a snapshot that may be minutes stale, so the desktop re-resolves the request through `getMyPendingRequests` and refuses if it is no longer pending. That single check also covers the double-tap case and the "someone already handled it" case.

## What the review changed before merge

The automated reviewer on PR #250 found four real defects. All four are consequences of the mailbox design rather than slips, so they are recorded as `architecture.md` D27 (k)–(o) — refinements of the same decision, not a new one.

- **A job could sit `running` forever.** If the tab that claimed a job went away before the terminal write — browser quit, tab closed, or the write itself failing — nothing in the system would ever move that job again: the poller queries only `queued`, and the phone's timeout only cancels `queued`. The phone would show "Your desktop is applying this…" indefinitely, with the retry button withheld because the job isn't terminal. Two fixes: the terminal write now retries three times (1s, 4s), and every Kindoo tab sweeps `running` jobs on loop start and once a minute, finalising anything older than five minutes as `failed` (the multi-site reshape below split that into two thresholds). `permission-denied` is deliberately excluded from the retry — it means the job has already left `running`, so no number of attempts will land it.

  **The subtle part is attribution, and the answer is that there isn't any.** The mailbox is keyed to one manager and the rules admit no other writer, so every `running` job in it came from one of that manager's own tabs — but that is where identification stops. `claimed_by` carries an extension version and a Kindoo site EID; neither is unique to a tab, so filtering on it cannot tell a live sibling tab from a dead one. It would only guarantee that a job stranded by another Kindoo site, or by an older extension build, never gets cleaned up. What is left is the clock plus the sweeping tab's own in-flight set, and a job whose claim time can't be read is skipped entirely, because its age is the whole safety argument. Five minutes against a run that is a handful of API calls is a wide margin, and the margin is the argument.

  The residual is real and accepted: two tabs, one of them genuinely stuck on a run longer than five minutes, means the sweep can mark `failed` a job that then succeeds. That is why the swept job's message refuses to say whether Kindoo took the write, and why the `failed` headline was reworded (below).

- **The desktop's own button could double-provision.** Tapping **Apply via extension** on the phone and then clicking **Provision & Complete** on the desktop ran the shared `applyRequest` twice against one request — two seat reads, two `provisionAddOrChange` calls, and for a member not yet in Kindoo two `inviteUser` writes, the second of which consumes a licence. `markRequestComplete` picking one winner is no help; the Kindoo writes have already happened. The button is now disabled on that card while the tab is running the job, with a line saying why. **Reject was deliberately left ungated** — it makes no Kindoo write, so a concurrent reject can't duplicate anything, and taking away the reject affordance for five seconds buys nothing.

- **The heartbeat could outlive the opt-out.** Turning the toggle off stops the loop and publishes `enabled: false`, but stopping cannot abort a tick already awaiting Kindoo's `getEnvironments`. That tick's `enabled: true` is a `merge: true` write and could land after the disable write, leaving the phone offering a button the manager had just revoked for a full 150-second staleness window. The opt-in is now re-read synchronously in the instant before the presence write — no `await` between the check and the write, which is the only reason the pref reader is synchronous.

- **A duplicate read out as a failure.** Two defects in one: the tap guard was derived state, which lands a microtask after the phone's synthesised second click, and the display picked the newest job for a request. Those compound badly, because the loser of a duplicate is claimed *after* the job that succeeded and comes back `failed` with `request_not_pending` — so a request that had in fact applied displayed "couldn't apply". That is the single worst thing this surface can say: the manager's correct response is to go redo a provision that already consumed a licence. The guard is now a ref flipped before `mutate`, the Apply button is withheld until the jobs subscription resolves, and the card resolves to the most *conclusive* job rather than the newest — `applied` > `partial` > `running` > `queued` > `failed` / `cancelled`, newest within a rank. Making that possible meant dropping two query constraints (the `status in [...]` filter, which would have hidden the successful job's terminal sibling, and any `orderBy` / `limit`, which would have dropped a just-written job whose `serverTimestamp()` still reads as null and sorts last). Both reasons are written at the hook so they don't get "optimised" back in.

- **Copy change: the `failed` headline is now "Your desktop didn't finish this."** It read "Your desktop couldn't apply this.", which is false for a swept job — that one genuinely does not know whether Kindoo took the write, and its message says so. A headline asserting otherwise would contradict the line beneath it, and a manager reading only the headline would redo the provision. The new wording is true of every `failed` job and claims nothing about Kindoo; the detail carries the specifics. Same reasoning that shaped `partial`'s wording.

## The multi-site reshape, and the question that caused it

After the review fixes landed, the operator asked what happens with two browser tabs. The answer was a defect, not an edge case.

Presence was one document per manager. A manager with two Kindoo tabs open on two Kindoo sites of one stake — an ordinary thing to do, and exactly what §15's multi-site support exists for — had those two tabs overwriting each other's `kindoo_eid` and `kindoo_site_name` every 60 seconds. Worse, the claim filter was stake-only. The foreground tab polls every 10 seconds and a backgrounded one every 60, so the foreground tab reliably claimed jobs belonging to the *other* site and failed them with `site_mismatch` — "switch Kindoo sites and try again", advice that is actively wrong when the site in question is open in the next tab. The failure mode was produced by the situation the message told the manager to create.

**Presence is now split by lifetime.** `remoteApply/{canonical}` carries the profile-wide opt-in and nothing else — profile-wide because it comes from `chrome.storage.local`, so ticking the box in one tab enables every tab in that Chrome profile. Liveness moved to `remoteApply/{canonical}/desktops/{siteKey}`, one doc per Kindoo site with a live tab. Two tabs now write two docs and neither disturbs the other.

**Site keys exist because the home site has no document.** Home lives on `stake.kindoo_config`, not in `kindooSites`, and a Firestore doc id cannot be null — so `remoteApplySiteKey()` maps null to the reserved key `'home'`, and every surface derives keys through that one function rather than hand-rolling `?? 'home'`. If a manager-chosen foreign slug of `'home'` ever needs handling, it is one function to change.

**Jobs carry a required, immutable `target_site_key`, and only a tab inside that site may claim one.** Immutability matters more here than for the other core fields: a mutable one would let a tab retarget work to itself and run a provision on the wrong Kindoo site.

**The target site is derived, never read off the request — and the field that looks like it is a trap.** `remoteApplyTargetSiteKey(request, wards, buildings)` in `@kindoo/shared` mirrors the extension's `checkRequestSite`: stake scope goes to home unconditionally (`building_names` never enters the derivation, because a stake-scope request's buildings may span sites and it is still provisioned on home), ward scope resolves through the ward's building, and an unknown ward goes to home. **`AccessRequest.kindoo_site_id` is not this site** — it is the site of the grant a `remove` targets, absent on add and edit, so reading it as the target resolves to "no site" on almost every request. That misreading cost this PR a full cycle; the field now carries a warning comment, and `firebase-schema.md` §3.4 states it outright so it doesn't catch a fourth reader.

**Gating moved from per manager to per card, and the copy followed.** The queue header names *every* covered site, because naming one when two are covered reads as a promise about the other. A card whose site isn't covered names the site to open instead of letting the manager discover it from a failed job. The top-of-queue extension note lost its "When your desktop is online" clause — online-ness is no longer a single fact — and now reads "Requests are completed and rejected in the Chrome extension on your computer. With Kindoo open there, you can apply them from here."

**Rules changed in three places.** A new `desktops` block, owner-deletable so a closing tab retracts presence immediately rather than leaving the phone naming a site as covered for 150 seconds. `target_site_key` required, non-empty, and immutable on jobs. And the parent presence doc **lost its `isManager` gate**: the gate read `stake_id`, that field moved down to `desktops`, and rules cannot ask "is this user a manager of *any* stake" — the `stakes` claim is a map with no way to test a predicate across its values. Re-adding a `stake_id` purely as a gate anchor would have reintroduced the field that flapped. What replaces it is an exact three-key shape plus `ext_version.size() <= 32`. **That cap is load-bearing, not cosmetic** — it is the entire storage bound on a document any signed-in user may write under their own email, and deleting it as a pointless-looking length check reopens the hole.

**Two thresholds for the stranded sweep, not a site filter.** Five minutes for a job this tab could itself have run, ten for anything else. A hard filter is worse than none in both directions: gate absolutely and a job stranded on site B is only ever cleaned up by a tab on site B, when the likeliest reason it stranded is that the manager closed that very tab; gate not at all and the foreground tab finalises the other site's genuinely in-flight work.

### Before deploying: clear leftover job docs

**A job doc with no `target_site_key` is permanently frozen.** The update rule's `jobCoreUnchanged` reads the field bare; a missing-key read errors, an erroring condition denies, and that helper gates `allow update` ahead of all three transition branches. So the job cannot be claimed, cannot be cancelled by the phone's 90-second timeout, and cannot be reported terminal — and `allow delete: if false` means no client can clear it. Console or Admin SDK only.

Earlier builds of `feat/remote-apply` queued jobs without the field, so **staging may hold such docs and they must be cleared before this build runs there.** The extension drops them from both queries with a repeating warning rather than guessing a site: guessing buys a doomed claim every poll that `claimRemoteApplyJob` misreports as "already claimed elsewhere", and would provision real Kindoo access against the guessed site if the freeze were ever lifted. The warning repeats deliberately — the state needs an operator, and it stops the moment they act. Production has never run a build that could create one.

## The second review round, and the smoke test that produced a dialog

The automated reviewer had been silently skipping runs on this PR; when it finally ran it found four things, and the operator's own smoke test on a phone produced a fifth. Recorded as D27 **(v)–(z)**.

- **The phone had no acknowledgement, only a row that changed colour.** Operator feedback, not a review finding, and the most user-visible change in this round. The desktop ends every Provision & Complete in a modal you have to dismiss; the phone showed the outcome inline and nothing else, which is fine while you are looking at it and useless once the phone is in a pocket. `RemoteApplyResultDialog` mirrors the desktop's, with three deliberate differences. It raises on the **transition** into a terminal status this device watched — the phone subscribes to the manager's whole mailbox, so raising on first sight of a terminal job would pop a modal per historical job on every page load. It is not dismissable by Escape or an outside tap, because the point of it is that it gets read. And it fires for `failed` and `cancelled` as well as the desktop's two modes: a phone gets pocketed, and a silent failure is worse than a silent success. The inline row stays exactly as it was.

- **Over-cap warnings were being dropped on the remote path entirely.** `applyRequest` has always surfaced `overCaps` and the desktop's `ResultDialog` has always rendered them; the job doc simply had nowhere to put them, so a manager who applied from their phone never learned a completion had pushed a pool past its cap. Now `RemoteApplyOutcome.over_caps`, rendered in the dialog as a "Now over cap:" list with pools named through the page's own scope labeller so a ward reads as its name rather than its code. The rules admit it as `is list` with a size cap and nothing deeper — **CEL cannot iterate a list**, so the per-entry shape is not expressible at any depth, and a partial check (typing `over_caps[0]`) would error on the empty list while proving nothing about the rest. The cap is a **render** bound, not a storage one: `message` sits beside it as an unbounded string, so bytes were never what that block defended; `over_caps` is just the one field the phone draws a row per element from.

- **A queued job could be provisioned unattended hours later.** The 90-second pickup timeout existed only as a `setTimeout` in the phone's browser tab. Locking the screen suspends it and closing the tab kills it — which is how a phone session normally ends — so a job nobody claimed stayed claimable indefinitely, and the poller would happily provision a 12-hour-old tap the next time the manager opened Kindoo. The poller now checks age before the claim and writes `queued → cancelled` itself. Two properties are the whole design: it **cancels rather than skipping**, because a `queued` job withholds the phone's Apply button for that request, so skipping would swap an unattended provision for a request the manager is silently locked out of; and it is **site-independent**, unlike every other job decision in the feature, because the tab that could have served the job is the one most likely to be closed — that is *how* the job went stale.

- **The Kindoo resolve had no rate limit when it failed.** `heartbeatIfDue` re-resolved whenever the tab's site was unresolved, and unresolved is the resting state of two ordinary situations that never clear on their own: a Kindoo session that expired while the tab stayed open, and a Kindoo site this stake hasn't configured. In both, `lastHeartbeatAt` never advanced, so every 10-second poll tick fired a `getEnvironments` POST at a third party's server, indefinitely, from every affected tab. Gating on the attempt's own timestamp instead holds a sick tab to the same one-call-per-60s budget D27 (b) claims for a healthy one, while a changed EID still re-resolves at once — that is new information, not a retry.

- **The web queue's existing-seat gate disagreed with the desktop's, and not in the safe direction.** The queue blocked any add for a member who already has a seat; the extension card carves out one case — a stake-scope `add_manual` for a member with a seat but no stake grant, which `planAddMerge` merges cleanly and which the app's own "Give Access To Stake Buildings" button produces. Because the chip and the button suppression are one boolean, that class of request got a red "This request can't be completed — reject it" *and* no **Apply via extension**, for a request the desktop provisions without complaint. The predicate now lives once, in `packages/shared/src/existingSeatGate.ts`. What made this worth lifting rather than patching: two surfaces were answering the same question and neither could see the other's copy, which is a drift that regenerates itself. The extension's adoption is mechanical and deferred to T-82 — `extension/` isn't `web-engineer`'s to change and several extension branches were in flight.

**The one thing deliberately not built: a retry on the phone's `partial` dialog.** The desktop's has one, so its absence looks like an oversight and will read like a bug to whoever finds it next. The desktop's retry replays a `markRequestComplete` input it captured in memory — an SBA-only write, no second Kindoo call. The job doc records `provisioning_note` and `kindoo_uid`, not that input, so the phone would be guessing the completion note it writes into the permanent record. It would also be the web queue's first-ever `markRequestComplete` call, against a page whose only action is remote apply. The request is still `pending`, so the desktop's own card finishes it through the tested path, which is what the outcome message already tells the manager to do.

## Three fixes from the phone, and why the tests were green throughout

The dialog above shipped and did not work. The operator found that by using it — applying real requests from a real phone against production — twice, and each time the cause was somewhere the tests structurally could not reach. Both are amendments to `architecture.md` D27 **(v)** rather than new letters: the decision is unchanged, the rule around it was wrong twice.

- **It raised on a transition the phone was never awake to see** (T-83). The first cut fired only on a status change that device watched happen, so a page load never popped modals for historical jobs. That rule holds for the desktop, which is a machine someone is sitting at with its panel open, and fails for the phone, which is the entire point of the feature: the manager taps Apply, turns to their computer to watch it work, and the phone locks. On wake the page has re-mounted and the job is already terminal on first sight — the commonest real flow, and the one where the dialog stayed away. Raising on sight instead needs the two things "witnessed transition" was quietly standing in for: *not someone else's* (the job's `created_by_device` against `getDeviceId()`, so a job queued from the manager's other phone belongs to that phone's screen, and an unreadable device id matches nothing rather than everything) and *not history* (a dismissal recorded in `localStorage`, not component state, because a locked phone guarantees the reload).

- **Then it raised and vanished, because it lived in the card** (T-84). *"I applied a request that did work, I think I saw the dialog for a few milliseconds, but it went away."* A successful apply ends in `markRequestComplete`; the request stops being pending; `usePendingRequests` drops it; the card unmounts and takes its children with it. The dialog was mounted inside the one component whose lifetime ends exactly when the event it exists to announce occurs, and the few milliseconds were the two snapshots landing in order — terminal job first (dialog paints), request-status change second (card gone). It is now `RemoteApplyResults`, mounted once by the page in **both** return branches, the loading one included, selecting across the whole mailbox. It has to raise with an empty queue behind it, because that is exactly what applying the last pending request produces.

  **Why the tests were no help, which is the part worth remembering.** They transitioned the job and left the request in the pending list — the one sequence in which the bug does not occur. A component test that mounts a card, flips a job to `applied`, and asserts a dialog is testing the dialog against a fixture that contradicts what the feature does to the world. The regression that now holds the line is mounting at page level with an empty request list.

- **Two consequences of the hoist, one of them an inversion.** Outcomes now **queue rather than collapse** — one dialog at a time, oldest completion first, each needing its own Dismiss, because a `failed` must not be buried under an `applied` that finished after it. Completion order beats recency for a reason that is not aesthetic: it is monotone, so an open dialog can only change by being dismissed, where newest-first would let a job terminating a beat later swap the title and body out from under a tap already travelling toward Dismiss. And **the acknowledgement cap went 50 → 500 with its justification reversed.** The original 50 was justified by the dialog being a card's child: an id old enough to be evicted belonged to a request that had long since left the queue, so nothing was rendered that could re-raise it. At page level that argument dies — eviction re-raises the outcome it acknowledged, and dismissing the re-raise evicts the next-oldest, which raises in turn, walking the manager backwards through a year of their own history one modal at a time. The cap is now a storage-quota backstop sized never to be reached, not a working limit. **A bound whose justification depends on what is mounted has to be re-derived whenever that changes.**

- **An extension update left every open Kindoo tab talking to a dead runtime.** Not the dialog, but found in the same smoke tests. Reloading or updating the extension orphans the previous build's content script in every open Kindoo tab with `chrome.runtime` severed, and the loop read the resulting exceptions as ordinary transient tick failures — so it kept heartbeating, polling, and sweeping in a dead page, logging roughly 37 warnings per tab per five minutes, after every update, for as long as those tabs stayed open. The loop now detects the orphaning (`chrome.runtime.id` first, since it costs a property read and Chrome cannot reword it; the "Extension context invalidated" string as fallback) and ends itself with one `console.info` naming the page reload as the remedy. The catch blocks that swallow ordinary errors rethrow this one, because swallowing it is what hid the shutdown signal. The user-visible consequence is a line in the Kindoo Manager guide: **after the extension updates, refresh open Kindoo tabs** — until they are refreshed, those tabs no longer answer the phone.

## The follow-up round (PR #253): three fixes, and the one that had to be fixed twice

Three findings from the automated review of PR #250, landed on a follow-up branch after the squash-merge. All three are amendments to `architecture.md` D27 **(b)**, **(l)** and **(y)** in place rather than new letters.

- **The double-provision gate missed the expensive window, and the first fix for it expired in one poll period.** `onJobStart` fires *after* the claim, so between the phone's tap and a desktop tab claiming the job it sat `queued` with the desktop's own **Provision & Complete** fully enabled — up to 60s on a hidden tab, which is what the tab is while the manager is looking at their phone. That is the happy path the feature is named for. The first fix published the `queued` page the poller already reads and gated the button on that too.

  **The reviewer then found that the gate it bought lasted exactly one poll.** The query is `where('status','==','queued')`, so the moment a sibling tab's claim landed the job left that page, the next poll published a set without it, and this tab's button went live *while the sibling was inside `applyRequest`* — the double `inviteUser` and the consumed licence, in exactly the two-tab configuration (p)–(u) exists for. The set now carries a second half: the `request_id`s of jobs `running` in the mailbox that this tab is not itself running, read on every poll. Three properties are load-bearing. The read is taken **after** the queued page, because a job only ever moves `queued → running` and the other order leaves a hole exactly as wide as the two reads. It is **its own read, not the sweep's**, because the sweep is rate-limited to 60 seconds against a 10-second poll and runs ahead of the session gate — stale on both counts, and a whole run fits inside the gap. And a **failed read holds the previous answer** rather than dropping the gate, since not being able to look is no evidence that a sibling stopped working.

  The test that was supposed to hold this line ticked once against a mock that returned the job as `queued` forever, so it never exercised the transition it protects. It now ticks across the claim landing, and fails without the fix. **A test whose fixture can't reach the state under test proves nothing about it** — the same lesson the dialog's card-level regression taught two rounds earlier.

  **Then the reviewer found that only one side of the gate held.** The failed `running` read held the previous answer; all three of the tick's early returns published `[]`. Those are opposite answers to the same question — "I couldn't look; is a sibling still working?" — and the clearing side covered the *more* reachable failures. Two of them are transient by construction: `heartbeatOk === false` on a `getEnvironments` blip, which this very PR's 30-second timeout made reachable in thirty seconds rather than never, and `!sessionResult.ok` on a `no-eid` from a DOM scrape that returns null on zero *or several* `[dir="auto"]` matches. In both the loop publishes `[]`, the button goes live, and the click's own `readKindooSession()` / `getEnvironments()` may succeed precisely *because* the condition was transient — the tick's failure and the click are independent samples, which is the reasoning error the earlier brief made when it wrote off these paths as ones where the button couldn't provision either. With a sibling mid-`applyRequest`, that is the double `inviteUser` this whole item exists to prevent. (The non-transient cases were checked and are fine: an unconfigured EID resolves to `null` through the same `resolveActiveKindooSite` that `checkRequestSite` uses, so the button refuses on its own.)

  Both sides now hold, on **one clock and one bound**. `lastBusyReadAt` is written in exactly one place — the success branch of the `running` read, whose success implies the queued page's, since it runs second — and every path that can't establish a fresh answer measures against it: the failed read, the two transient early returns, and a tick that throws, which the queued read reaches first and which had been leaving the last set standing for as long as the outage lasted. Past `REMOTE_APPLY_BUSY_HOLD_MS` they all lapse to `[]`. **Choosing that bound is the substance of the fix, and it is sandwiched from both ends.** A hidden tab polls at 60s, so under two of those the hold is useless to the tab likeliest to have blipped; and a single failed Kindoo call blinds a tab for ~90s by itself — 30s to abort, then the resolve gate withholds the retry until 60s past the attempt that failed. That is the floor. The ceiling is `REMOTE_APPLY_STRANDED_MS` (5 min), where this same loop gives up on a `running` job and writes it `failed`: a gate held past there refuses on evidence the sweep has already disowned. **150s** takes a poll period of margin over the floor and half the ceiling — one Kindoo failure doesn't lift it, two consecutive ones do. It lands on the same number as `REMOTE_APPLY_STALE_MS`, the phone's answer to the same "how long does an unrefreshed observation of this desktop stay true?", and stays a separate constant because that one is keyed to the heartbeat period and this one to the poll. Unbounded was not available in either direction: no hold double-provisions, and a hold nothing can refresh strands a manager whose own button is dead while no sibling is serving them.

  **The opt-in check is the one early return that still clears outright**, and the asymmetry is the point rather than an oversight: a bounded hold only lifts if ticks keep coming, and opting out stops the loop, so a held set published there would be the last word. The flag is profile-wide, so no sibling tab is polling either — and `useRemoteApply` clears the set on the same transition for the same reason.

  What the gate still does not buy is the tap → claim window for a job this tab *can* serve: the poll that first sees such a job claims it in the same tick, so the gate is held across one Firestore write rather than a poll period. The phone covers that window from its own side. Two Kindoo tabs whose manager clicks the desktop button in both, with no phone involved, remains uncovered — there is no job doc for either to see.

- **The one-Kindoo-call-per-60s budget was bypassed whenever the presence write failed.** It was keyed on the last *successful* write, so a tab whose site resolves but whose `desktops` doc is denied re-ran `getEnvironments` every tick, forever, per open tab — reachable by deactivating a manager who has a Kindoo tab open, since `App` only flips to NotAuthorized off a queue-fetch denial and nothing there is on a timer. The same shape as the bug (y) fixed one round earlier, in the branch (y) didn't touch. The budget is on calls to a third party, so the gate moved ahead of the resolved / unresolved split and is keyed on the **attempt**: a failing tick consumes its slot.

  **That deliberately loosens a written invariant**, and it is recorded in (b) rather than left implicit. A tab whose `desktops` write is denied now goes on polling, claiming and running jobs while publishing no presence. Presence answers "can the phone see me"; the poll answers "can I do work". A tab that reached Kindoo and knows its site can still finish a job already in the mailbox, and failing it with a real message beats letting it expire as though nobody was there. A rejection from *Kindoo* is still total — no site, no presence, no poll.

- **No Kindoo fetch had a timeout.** `fetch` waits forever, and the remote-apply tick is serialised: one hung call means no heartbeat, no stranded sweep, and — for a single-tab manager — a claimed job left `running` with nothing alive to finalise it, the one hole the sweep cannot close. `postKindoo` now arms an `AbortController` at 30s across the headers *and* the body read, surfaced under the existing `network-error` code with wording that names the timeout, because a timeout and a dropped connection leave "did this reach Kindoo?" equally unanswerable. The value is a per-**call** bound and a provision is sequential (~9 calls worst case), chosen to keep a wholly-degraded run inside `REMOTE_APPLY_STRANDED_MS` — raise it and a sibling tab starts sweeping live work.

**Copy changed with the gate.** The card's second sentence and the queue banner both had to cover a job a *sibling tab is running*, not just one waiting in the mailbox: "your desktop is picking it up" became "your desktop is handling it", and "Picking up a request you sent from your phone…" became "Your desktop is handling a request you sent from your phone…". The phase the panel threads is `'elsewhere' | 'this-tab'` for the same reason — it is a split by which surface can honestly report on the job, not by job status.

## What didn't change that you'd expect to

- **No Cloud Function.** Both ends of the mailbox are client SDK writes gated by rules, and the work the desktop does once it claims a job runs through the two callables that already existed — `getMyPendingRequests` and `markRequestComplete`. Nothing server-side participates in the transport.
- **No composite index**, through two rounds of query changes including the per-site reshape. The extension's two reads are still single-field — `where('status','==','queued')` and `where('status','==','running')`, both `limit(20)`, ordered by nothing — and the phone's job subscription has no constraints at all, which needs no index by definition. **Site routing added none either**, because it is applied client-side after the read rather than as a second `where`: the poller reads a page of queued jobs and claims the first one its own site can serve. Ordering that query by `created_at` alongside the status equality *would* need a composite index, which is why it isn't ordered. Noted explicitly in `firebase-schema.md` §5.1 so the absence reads as a decision rather than an oversight.
- **No rules change for the stranded sweep, and none for the desktop-side pickup expiry either.** A swept job takes the existing `running → failed` branch; an expired one takes the existing `queued → cancelled` branch that was written for the phone's timer. In both cases only the author and the message differ, and a rule branch was never the right place to encode which client wrote it — both are the mailbox owner and the rule cannot tell them apart. `over_caps` is the only rules widening in this round.
- **The phone's inline row is unchanged by the dialog.** The dialog is an acknowledgement layered on top, not a replacement: the row is still what the card shows at a glance, still what a reload shows for finished work, and still the only thing that speaks for a job the manager did not queue from this device.
- **The row stayed on the card when the dialog left it.** Hoisting the dialog to page level is not an argument that everything belongs there. The row is the at-a-glance state of a request that is on screen, so it *should* vanish with the card; the dialog is an acknowledgement of an event whose whole point is that it outlives the request. Two things that looked alike were split by lifetime, and only one moved.
- **No new manifest permission.** `setInterval` in the content script and Firestore writes from the service worker were both already in use. Widening `host_permissions` after the initial Web Store submission would have forced a re-review.
- **No new audit semantics.** The job doc is a transport record, not an audited entity; nothing fans an audit row for it. The audited rows are the `complete_request` and seat writes `markRequestComplete` produces — byte-identical to a desktop-initiated apply.
- **No presence on `userIndex`.** Its update rule is a strict three-key `hasOnly` allowlist the Phase 10.5 changelog already records as painful to widen, and heartbeat churn would have re-rendered the notifications page that subscribes to it.
- **No new role, and no widening of an existing one.** Remote apply changes *where* a manager can act from, never *who* may act. Everything the desktop does when it claims a job was already something that manager could do at that desktop.
- **Jobs are never deleted.** `delete: false` on both the parent opt-in doc and the jobs. At 1–2 requests/week the collection stays trivially small and the trail is useful when a provision misbehaves. `desktops` is the exception the reshape added, and for the opposite reason: those docs are liveness, not history, so retracting one promptly is the point.
- **The extension's own queue behaviour is otherwise untouched.** Reject, the add-onto-existing-seat gate, the edit-missing-seat gate, and the requester line all behave exactly as before. `RequestCard` shed 207 lines to the extraction and gained 33, with no new behaviour beyond the site-mismatch sentence.
- **No E2E coverage of the desktop half.** Playwright can drive the phone half against a seeded mailbox, and `e2e/tests/requests/queue-remote-apply.spec.ts` does — at a phone viewport, covering the four presence states, the job write, and the duplicate that must not read out as a failure. The half that claims and provisions needs a signed-in Kindoo tab and has no harness. It is covered instead by rules tests (every legal and illegal transition, the double-claim race, cross-user denial) and extension unit tests (claim/skip on a lost race, outcome → job serialisation, heartbeat suppression on an unusable session, the sweep's age and in-flight gates).

## Known issues / deferred work

- **Production is gated on Chrome Web Store review.** The web half ships first and is inert until a presence doc exists, so there is no ordering hazard; the extension half is unusable in production until the reviewed build lands. Staging is unpacked and testable immediately. See `infra/runbooks/extension-deploy.md`, which warns the review takes days to weeks.
- **Push wake-up for the extension is not built and is not planned.** Executing with Chrome closed is out of scope for the same reason: no Kindoo tab, no Kindoo write.
- **Remote *reject* is not built and would be much cheaper.** Rejection needs no Kindoo session at all, and `firestore.rules` already permits a manager's reject write — it could be a plain button on the phone with zero extension involvement. Flagged here because the asymmetry is surprising: the hard half shipped and the easy half didn't.
- **The opt-in is per Chrome profile, not per person.** A manager with two computers opts in on each. Liveness is per Kindoo *site*, not per computer, so two computers both sitting in the same site publish to the same `desktops` doc and the last heartbeat wins. Nothing anywhere lists which physical desktops are online — the phone's question is "is some tab covering this site", and that is the only question it needs answered.
- **Cross-device duplicate jobs remain possible. Accepted, not a bug.** Two of the manager's own devices tapping Apply at the same moment each write a job; neither sees the other in time, and the create rule permits it by design (tightening it would mean a query in a rule). Harmless in practice: the card displays the most conclusive job, and the desktop refuses the loser with `request_not_pending` before touching Kindoo. Do not "fix" this by making the create rule cleverer.
- **The desktop's double-provision gate has one window left, and it is the phone's to close.** Since PR #253 the gate reads the mailbox rather than only this tab's own claim, so a second Kindoo tab running the job *is* covered, as is one that could never claim it. What is not covered is the tap → claim window for a job this tab can serve — one Firestore write wide, because the poll that sees the job claims it in the same tick — which the phone closes by withholding Apply for a request with a live job. Nor is the case with no phone in it at all: two Kindoo tabs whose manager clicks **Provision & Complete** in both write no job doc, so neither tab has anything to see. That one is still the manager's own two hands.
- **A sweep can outrun a slow run.** Five minutes (ten from a tab on another site) is far outside a normal run, but a tab genuinely stuck past its threshold can have a sibling mark its job `failed` while it goes on to succeed. The wording is built for this (nothing claims the Kindoo write didn't happen) and there is no cheap way to do better without tab-unique claim identity, which `claimed_by` does not carry.
- **The extension still carries its own copy of the add-onto-existing-seat gate** (T-82). The shared predicate landed in `packages/shared/src/existingSeatGate.ts` and the web queue consumes it; `panel/QueuePanel.tsx` and `panel/RequestCard.tsx` still express it locally. The swap is mechanical and needs no prop-shape change, but it was left to the extension owner with several extension branches in flight. Until it lands, the drift that produced this fix can recur in the other direction.
- **Nothing validates the shape of an `over_caps` entry.** Rules check that the field is a list and bound its length; they cannot check further, because CEL has no way to iterate one. The writer is the desktop extension and the reader is the same manager's phone, so a malformed entry misrenders in the writer's own dialog and reaches nobody else — which is why this is accepted rather than worked around. Do not "fix" it by typing `over_caps[0]`: that errors on an empty list and denies a legitimate completion.
- **A `cancelled` dialog can't say which request it is about.** With no card behind it, the dialog carries only what the job doc holds — and `cancelled` is the one status with nothing distinguishing in it (`applied` has the provisioning note, `failed` the desktop's message). Bounded in practice rather than fixed: a job nobody picked up never touched its request, so that card is still sitting in the queue behind the modal.
- **The 500-acknowledgement cap has a residual.** A device that somehow exceeds it re-raises one old outcome per new dismissal. Reaching that takes decades at this volume, so it is left; the real fix is an acknowledgement watermark rather than a list of ids, and it is not worth building for a bound nothing will reach.
- **The App Check gap on callables is unchanged** (T-40). Remote apply drives the same two callables as the desktop button and neither widens nor narrows that gap.
